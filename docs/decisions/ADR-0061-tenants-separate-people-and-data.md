# ADR-0061: テナントで人とデータを分け、全体の管理者は中身を見ない

- 日付: 2026-10-22
- 状態: 提案

## 文脈

IdP（assay）はテナントで人を分けている（発行者 `issuer` が `https://identity…/<tenant>`）。
一方この雛形は、受け付ける発行者が 1 つ（`OIDC_ISSUER`）で、アプリの中にテナントという
区切りが無い。入った人は全員が同じ空間にいて、利用者・グループ・中身・管理画面を共有する。

そのため、この雛形から作ったアプリを複数の家族・組織に使わせるには、テナントごとに環境を
1 つ立てるしかない。1 つの環境で分けようとすると、次のことが起きる。

- 管理者（`owner`）は全権限で、ほかの家族・組織の利用者も中身も見て動かせる
- 共有相手の候補・お知らせの宛先に、ほかのテナントの人が並ぶ
- グループやロールの管理が、テナントをまたいで効く

持ち主の決定（2026-10-22）:

- 雛形にテナントを入れる（派生アプリのうち photonest には入れない）
- 立場は **全体管理者 / テナント管理者 / テナントメンバー** の 3 段
- **全体管理者はテナントの中身を見られない**
- **テナント管理者はアプリの中で指名する**（assay の管理者をトークンで受け取らない）

## 決定

**全体管理者はテナントの外側を、テナント管理者はテナントの内側を管理する。**

| | 全体管理者（外側） | テナント管理者（内側） | テナントメンバー |
|---|---|---|---|
| テナント | 登録・停止・削除、最初のテナント管理者の指名、テナントごとの人数（中身ではなく数） | 自分のテナントの名前を見る | — |
| 人 | 全体管理者どうしの付け外し | 自分のテナントの利用者・グループ・ロール（ADR-0051 の関門をテナントの中で） | 自分のプロフィール |
| 中身 | **見られない** | 自分のテナントの中身の管理 | ロールの範囲で使う |
| 設定 | 全体の設定（メール・署名鍵・通知の鍵・ログの水準など） | — | — |
| 記録 | アプリログ（`log`）、全体の操作の監査 | 自分のテナントの監査ログ | — |
| 運用 | 再起動・版の知らせ | 自分のテナントへのお知らせ | — |

1. **テナントを表 `tenants` で持つ。** 1 行が assay のテナント 1 つに当たり、発行者
   （`issuer`）・クライアント ID・表示名・URL に使う短い名前（`slug`）・状態（有効 / 停止）を
   持つ。assay のクライアントはテナントごとに登録するもので（`(tenant_id, client_id)` が一意）、
   クライアント ID はテナントごとに違う。署名鍵（`private_key_jwt`）はアプリで 1 つにし、
   同じ公開鍵を各テナントのクライアントに登録する。
2. **テナントを登録するのは全体管理者。** 登録の無い発行者のトークンは受け付けない
   （今の「発行者は 1 つ」と同じ強さを、テナントの数だけ持つ）。
3. **利用者はちょうど 1 つのテナントに属する**（`users.tenant_id`）。全体管理者だけは
   テナントに属さない（`NULL`）。同じ人がテナントの中身も使うなら、そのテナントに別の利用者を
   持つ。`(issuer, subject)` の結び付き（`federated_identities`）は今のまま使える。
   ローカル口座（ADR-0039）もどれか 1 つのテナントに属する。
4. **権限を 2 つの範囲に分ける。**
   - **全体の権限**: テナントの登録・停止、全体の設定、再起動、アプリログ。持つのは
     テナントに属さない利用者だけ
   - **テナントの権限**: 今の利用者・グループ・ロール・中身・監査ログの権限。効くのは自分の
     テナントの中だけ
   ロールの雛形は、全体の系統に `platform-admin`（全体の権限を全部。中身の権限は持たない）を
   足し、今の `owner` を「テナントの全権限」に縮める。テナントに属さない利用者にテナントの
   ロールは付けられず、テナントの利用者に全体のロールは付けられない。
5. **中身の表は全部 `tenant_id` を持ち、読み書きは必ず主体のテナントで絞る。** 絞りは
   リポジトリの入口 1 か所（主体からテナントを受け取る形）で掛け、ルーター本文で書かない。
   別のテナントの行は 404 で返す（在ることも見せない）。
6. **絞り忘れを機械で落とす。** モデルの全表を「テナントの表」「全体の表」のどちらかに
   宣言させ、宣言の無い表と、`tenant_id` の無いテナントの表を試験で落とす
   （`test_authorization_matrix` が scope の付け忘れを落とすのと同じ形）。加えて、2 つの
   テナントを作って互いの行が見えないことを、各コンテキストの API で確かめる試験を置く。
7. **テナント管理者はアプリの中で指名する。** テナントを登録するとき、全体管理者が最初の
   テナント管理者（の招待）を決める。以後はテナント管理者が自分のテナントの中で付け外しする
   （ADR-0051 の関門をテナントの中で通す。「管理の要」はテナントごとに数える）。
8. **サインインはテナントを選んでから。** 入口の URL に `slug` を持たせ（例 `/t/<slug>/login`）、
   そのテナントの発行者とクライアントで assay へ送る。テナントが 1 つだけの環境では、今の入口が
   そのまま使える。
9. **既存の環境は「既定のテナント」1 つに全員を入れて移る。** マイグレーションが今の
   `OIDC_ISSUER` / `OIDC_CLIENT_ID` から既定のテナントを作り、全利用者・全行をそこへ入れる。
   今の `owner` を持つ人は、既定のテナントの `owner`（テナント管理者）になる。全体管理者は
   移行の後に別途作る。

## 理由

- **テナント = assay のテナント**: 人の出所が assay のテナントなので、ここをずらすと
  「assay では別の組織なのにアプリでは同じ」が起きる。発行者で見分ければ、トークンから
  テナントが一意に決まり、`(issuer, subject)` の鍵もそのまま使える。
- **全体管理者が中身を見ない**: 他人の家族・組織のデータを運営者が読めないことを、運用の
  約束ではなく権限の形で保証する。障害対応で中身を見る必要が出たら、そのテナントの管理者に
  招いてもらう（招かれた事実が監査ログに残る）。
- **テナント管理者をアプリで指名**: assay の管理者は IdP を管理する人で、アプリの管理者と
  同じとは限らない。トークンに載せるには assay の改修が要り、載せてもアプリ側の「管理の要」
  の数え方と二重になる。
- **絞りをリポジトリの入口に置く**: ルーターで書くと、書き忘れても動いてしまい、気付くのは
  漏れた後になる（scope の付け忘れと同じ理由）。
- **利用者は 1 テナント**: 1 人が複数のテナントを行き来できる形（Slack のワークスペース）も
  考えたが、どのテナントとして動いているかをトークンと全リポジトリが持つことになり、絞りの
  誤りが起きる箇所が増える。今の用途（家族・組織ごとに分ける）では要らない。

### 検討して捨てた案

- **テナントごとに環境を立てる（今のまま）**: 分離は確実だが、テナントを足すたびに
  namespace・DB・宣言が増える。持ち主の決定で、1 つの環境で分ける。
- **DB をテナントごとに分ける**: 分離は強いが、マイグレーションと退避がテナントの数だけ
  要り、雛形の運用（k3s の 1 スタック）に合わない。
- **全体管理者が全テナントを見られる**: 持ち主の決定で取らない。
- **assay のテナント管理者を写す**: 上の理由で取らない。

## 影響

- 中身を持つコンテキスト（`example` の `items`・`notification`・`audit`）の表と
  リポジトリに `tenant_id` が入る。派生アプリが足す表も同じ宣言が要る（宣言しないと試験が落ちる）。
- 設定（`system_settings`）は全体のまま。テナントごとの設定は、要る派生アプリで足す
  （この ADR に含めない）。アプリログ（`log`）も全体のもので、全体管理者だけが読む。
  監査ログはテナントごとで、テナント管理者が自分のテナントの分を読む。
- 管理画面が 2 つに分かれる: 全体（テナント一覧・設定・ログ）と、テナントの中（今の利用者・
  グループ・ロール）。
- `users` に列を足すと据え付けの移行 `0002` が落ちるため、利用者のテナントは 1 対 1 の
  別表（`user_tenants`）で持つ。
- ⚠ 既存の派生アプリは、雛形を取り込んだ時点で「既定のテナント」1 つの環境になる。動きは
  今と変わらないが、`owner` が全体の設定を触れなくなる（全体管理者を作るまで設定画面に入れる人が
  いない）。取り込むときの手順を `docs/OPERATIONS.md` に書く。
- photonest はこの雛形から離れて久しく、テナントを入れない（家族の道具。photonest の ADR-0028）。
