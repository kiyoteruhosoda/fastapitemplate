# ADR-0017: アクティブロールの切り替えは JWT クレームで持ち、既定は全ロールの和集合

- 日付: 2026-08-01
- 状態: 承認

## 文脈

ユーザーは以前から複数のロールを持てる（`user_roles` は多対多）。しかし有効 scope は
常に「全ロールの権限の和集合」で、**いま使う権限を利用者が選べなかった**。

管理者と一般利用者を兼ねる運用では、次の要求が出る。

- 普段は弱いロールで操作し、必要なときだけ強いロールへ切り替えたい（最小権限）。
- 「member から画面がどう見えるか」を、別アカウントを作らずに確かめたい。

決めるべきことは 2 つ。**アクティブロールをどこに保持するか**と、
**未選択のときの既定をどうするか**。

## 決定

1. アクティブロールは **JWT の `active_role` クレーム**に持ち、切り替えは
   `POST /api/auth/switch-role` による**トークンの再発行**で行う。
   refresh トークンにも同じクレームを載せ、更新しても選択が続く。
2. `active_role` が `null` のときは**全ロールの権限の和集合**（従来どおり）。
   ロールを 1 つ選ぶと、有効 scope はその**ロール 1 つ分の権限**に絞られる。
3. 保有していないロールへは切り替えられない（403 `role_not_granted`）。
   検証時の scope は毎回 `クレームの scope ∩ アクティブロールの現在の権限` で
   取り直す。
4. `AuthenticatedPrincipal` は `active_role` を持つが、**認可の分岐には使わない**。
   認可は従来どおり scope だけで判定する（CLAUDE.md「権限管理」）。

## 理由

- **JWT に持つ（DB の `users.active_role_id` にしない）**: 切り替えはセッションの
  状態であって、アカウントの属性ではない。DB に持つと、片方のブラウザで絞った
  つもりが別の端末の権限まで変わる。マイグレーションも要らず、トークンの再発行
  だけで完結するので、既存の scope 検証の流れ（`intersection` を取り直す）に
  そのまま乗る。
- **切り替えでトークンを再発行する（既存トークンの scope を後から読み替えない）**:
  トークンの中身と実際の権限を常に一致させるため。トークンは変えずにサーバー側の
  状態で絞ると、同じトークンが時点によって別の権限を意味することになり、
  ログ・監査から「どの権限で叩いたのか」が読めなくなる。
- **既定を「全ロールの和集合」にする**: 従来の挙動と一致し、発行済みのトークンや
  ロールが 1 つだけの利用者に影響が出ない。切り替えは権限を**減らす**方向にしか
  働かない（保有ロール以外は選べない）ため、既定が広くても昇格の経路にならない。
- **`active_role` を principal に載せる**: 「いまどのロールか」の表示と選択肢の
  提示に要る。ロール名で認可を分岐しない原則は変えない — アクティブロールは
  `permissions` を絞り込んだ**結果**として既に反映されている。

## 影響

- `/api/auth/me` は `roles`（切り替え先の一覧）と `active_role` を返す。`scopes` は
  「保有権限」ではなく「**いま有効な権限**」になった。scope の一覧を「その人が
  持ちうる権限」として読んでいた画面があれば意味が変わる。
- 切り替えは監査ログへ `role.switched`（`reason=role=<ロール名>` / `role=all`）
  として残す。どの権限で操作していたかを後から追えるようにするため。
- 絞り込んだ後にそのロールを外されると、そのトークンの scope は空になる
  （権限が残らない）。利用者から見ると急に何も操作できなくなるので、ロールの
  変更は従来どおり再サインインで拾い直す前提を崩さない。
- ロールが 1 つ以下の利用者に切り替え UI は出さない（「すべて」とその 1 つが
  同じ権限になるため）。
- クレームを持たない発行済みトークンは `null`（＝全ロール）として扱う。
