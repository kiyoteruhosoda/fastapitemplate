# ADR-0024: ロールを足す投入と、初期管理者を据える操作を分ける

- 日付: 2026-09-02
- 状態: 承認

## 文脈

マスタデータの投入（`seed_master_data`）は 1 つの関数で 3 つのことをしていた ——
ロールを足す・権限を足す・**初期管理者（`admin@example.com`）が居なければ作る**。
冪等なので、何度呼んでも同じ結果になる…… はずだった。

権限を足すマイグレーション（`0005` 以降のシード）は、値の重複定義を避けるために
この関数を呼ぶ。つまり**権限を 1 つ足すたびに「初期管理者が居なければ作る」が
走る**。

2026-09-02、**この雛形から派生した `blobshare` の本番**で実際に起きた。

- 運用の初期に、本物の利用者を作ったあと **`admin@example.com` は削除されていた**
  （監査ログに `user.deleted` が 2 回。最後は 2026-08-30）
- 権限を 1 つ足すマイグレーションが走った瞬間、その利用者が
  **`id=1` / `is_active=1` で復活**した
- パスワードは `master_data.DEFAULT_ADMIN_PASSWORD_HASH` ——
  **平文はリポジトリと文書に書いてある既定値**（`admin@example.com`）
- 復活先は**公開されている**サイト（前段に認証は無い）

約 24 分後に気付いて無効化・削除した。その間の監査ログにログイン試行は無く、
`admin` を名乗る操作も記録されていない。

**雛形が持っている以上、ここから派生するアプリすべてに同じ穴が開く。**

「冪等」は**同じ関数を何度呼んでも同じ結果**という意味であって、**運用者が
下した決定（この利用者は要らない）を尊重する**という意味ではなかった。

## 決定

**`seed_master_data` からユーザーの作成を外し、`ensure_default_admin` として
別の関数にする。**

- `seed_master_data(session)` —— ロールと権限だけ。**利用者を作らない。**
- `ensure_default_admin(session, password=None)` —— 初期管理者が**居なければ**据える。

呼ぶ場所は次のとおり:

| 呼ぶ側 | `seed_master_data` | `ensure_default_admin` |
|---|---|---|
| `0002_seed_master_data`（据え付け） | ○ | ○ |
| 権限を足すマイグレーション（`0005` 以降のシードすべて） | ○ | **×** |
| `scripts/seed_master_data.py`（手で流す＝復旧） | ○ | ○ |
| テストの土台（`tests/conftest.py`） | ○ | ○ |

## 理由

**据え付けと運用は別の時間軸にある。** 初期管理者は「まだ誰も居ない DB に、
最初に入る人を 1 人置く」ための仕掛けで、据え付けの一度きりに意味がある。運用が
始まったあとの再投入は「語彙（ロールと権限）を新しい版に合わせる」操作であって、
利用者の顔ぶれには関係が無い。同じ関数に置いていたのは、たまたま両方が
「master_data.py の値を DB へ写す」形をしていたからにすぎない。

**運用者の削除は決定であって、欠損ではない。** 「居なければ作る」は、据え付けでは
親切だが、運用では**消したという判断を毎回上書きする**。しかも上書きされたことは
どこにも出ない（マイグレーションのログは成功としか言わない）。

**既定のパスワードで復活するのが致命的。** 復活そのものより、`ADMIN_INITIAL_PASSWORD`
を渡さない呼び出し（＝マイグレーション）が**公開されている既定のハッシュ**を使う
ことのほうが重い。据え付け直後に変える前提の値が、運用中の本番へ後から入る。

**「ユーザーが 1 人も居なければ作る」にしない。** それでも今回の事故は防げるが、
文書化してある復旧手順（管理者の行を消してから `scripts/seed_master_data.py` を
流す。OPERATIONS.md）が**他の利用者が居ると効かなくなる**。誰を据えるかは
呼ぶ側が決める話で、行数を数えて推測することではない。

**マイグレーション側に「作らない」と書かない。** 引数（`create_admin=False`）で
渡す形にすると、既定値がどちらであれ、書き忘れた新しいマイグレーションが
どちらかに倒れる。**関数を分ければ、呼ばなかったものは起きない。**

捨てた案:

- **`ADMIN_INITIAL_PASSWORD` を本番で必ず設定する** —— 事故は防げず（強いパスワードの
  管理者が黙って復活するだけ）、そもそも消した利用者が戻ること自体が誤り
- **シードのマイグレーションだけ `seed_master_data` を呼ばずに直接 INSERT する** ——
  値の正本を `master_data.py` に一本化した規約（CLAUDE.md）を崩す。同じ穴が次の
  マイグレーションで開く
- **復活した利用者を無効（`is_active=false`）で作る** —— 「なぜ無効な admin が
  居るのか」を毎回説明することになり、消したいものが消せない状態は変わらない

## 影響

- **既存の環境では何も起きない。** `0002` は適用済みで、以後のマイグレーションが
  利用者を触らなくなるだけ。
- **据え付けの経路は変わらない。** 新しい DB では `0002` が初期管理者を据える。
- **復旧手順も変わらない。** `scripts/seed_master_data.py` は両方を呼ぶ。
- `tests/integration/test_master_data_seeder.py` が「消した管理者が再投入で
  戻らないこと」を見張る。**新しいマイグレーションで `ensure_default_admin` を
  呼ばないこと。**
- **派生済みのアプリには自動では伝わらない。** 同じ形を当てる必要がある
  （`blobshare` は ADR-0044、`nolumiawiki` は ADR-0057 として反映済み）。
