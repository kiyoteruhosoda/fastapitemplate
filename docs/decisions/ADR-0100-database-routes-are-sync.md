# ADR-0100: DB を使う口と依存関数は def で書く

- 日付: 2026-10-31
- 状態: 承認

## 文脈

口の多くが `async def` で、SQLAlchemy の呼び出しは同期だった。確定は `get_db` の後始末で行う。同じ行を書く要求が同じプロセスで重なると、次の順で固まる（task #807）。

1. 先の要求が行のロックを持ったまま、確定の順番を待つ。
2. 後の要求がイベントループの上でそのロックを待つ。ループが止まるので、先の要求の確定が走らない。
3. MariaDB のロック待ちの上限（50 秒）で後の要求が 500 になる。待つ要求が続くと、gunicorn の `--timeout 120` がプロセスごと殺す。

stg の MariaDB で 8 本を同時に流すと、3 回とも 1 本も成功せず、4 回プロセスが殺された（数字は task #807）。SQLite の試験は順番に流れるので出ない。#793 では更新の口だけその場で確定して直した（PR #89）。

## 決定

1. **DB に届く口と依存関数は `def` で書く。** FastAPI がスレッドプールで動かすので、ロックを待つのはそのスレッドだけになり、ループは先の要求の確定を進められる。
2. **`get_db` に届かない `async def` はそのまま。** `/healthz` は k8s の確かめの先で、スレッドプールが埋まっても答える必要がある。
3. **ログと監査の文脈（`ContextVar`）を置く依存関数は `async def` のまま。** スレッドの中で置いた値はスレッドの外へ戻らず、アクセスログと監査の「誰が」が黙って消える（読むのは問題ない。スレッドへは写しが渡る）。DB も要るときは `run_in_threadpool` へ逃がし、文脈はループの上で置く（`get_app_or_web_principal`）。
4. **`await` が要る口は `async def` のまま、DB を `run_in_threadpool` へ逃がす**（`receive_backchannel_logout`）。
5. **試験で止める。** 実効の依存の木を回して、DB に届く `async def` を落とす（例外は理由と一緒に表へ）。presentation の `def` の中で `ContextVar` を置くのも落とす。どちらも破った見本で判定を確かめる。

## 理由

書き換えは `async def` の 4 文字を消すだけで、本体の処理を動かさない。依存の木から対象が機械的に決まり、派生アプリにも同じ手順で入れられる。

| 採らなかった案 | 捨てた理由 |
|---|---|
| SQLAlchemy の非同期版へ移す | 全部のリポジトリとユースケースが `async` になる。一度に書き換えると、試験で拾えない壊れ方が出る |
| 全部の口で書いたらその場で確定する（PR #89 の形） | 例外で巻き戻す前提が崩れる。書き忘れても動いて見える |
| `await` の無い `async def` を全部 `def` にする | `/healthz` がスレッドプールの待ち行列に入る。文脈を置く依存関数も `def` になって「誰が」が消える |
| ロック待ちの上限を短くする | 固まる時間が短くなるだけで、その間は全部の要求が止まる |
| 同じプロセスで書き込みを 1 本ずつに絞る | プロセスの間は絞れない。関係ない行の書き込みまで待たせる |

## 影響

- 同じプロセスの中で要求が同時に DB を使えるようになる。接続は既定で 1 プロセス 15 本（`QueuePool` の 5＋10）、スレッドは 40 本なので、接続を待つ要求は 30 秒で 500 になることがある。家の規模では届かない。届いたら `create_engine` の上限を設定へ出す。
- 口の本体がプロセスのグローバルな値を読み書きするときは、スレッドで動く前提で書く（いま書き換えた範囲には無い。キャッシュは `threading.Lock` を持っている）。
- 更新の口のその場の確定（PR #89）は残す。行のロックを持つ時間が短くなり、外す理由が無い。
