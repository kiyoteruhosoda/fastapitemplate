# ADR-0038: 「ローカルのパスワードが無い」をデータで表す（NULL であって、ランダム値ではない）

- 日付: 2026-09-14
- 状態: 承認

## 文脈

`users.password_hash` は `NOT NULL` だった。そのため SSO で作った利用者には
**誰も知らないランダム値**（`secrets.token_urlsafe(48)` のハッシュ）を入れていた。

動きはする。パスワードの口からは入れない。だが、**「パスワードが無い」と
「誰も知らないパスワードがある」が区別できない**（idp の ADR-0049 I4 / G2）。区別できないと、

- **設定画面にパスワード変更の導線が出る。** 当人は「今のパスワード」を入力できないので、
  絶対に通らないフォームを見せることになる。
- ⚠ **パスワードリセットを通すと、実質のローカル認証が生える。** SSO でしか入れない
  はずの利用者が、以後パスワードでも入れるようになる ——**誰も操作していないのに
  入り口が 1 つ増える。**
- **監査で「この利用者が入れる手段」が読めない。** 行を見ても分からない。

## 決定

**`password_hash` を NULL 許容にし、`NULL` を「ローカル認証を持たない」と定める。**
判定は `User.has_local_password` に集める。

1. **SSO で作る利用者には NULL を入れる**（ランダム値で埋めない）。
2. **パスワードでのログインを断る**（照合する相手が無い）。
3. **パスワード変更を断る**（理由は `invalid_current_password` に揃える。持っていない
   ことを教えると、入り口の有無を外から数えられる）。
4. ⚠ **パスワードリセットを発行しない・通さない。** 応答は宛先が無いときと同じにする。
5. **`/api/auth/me` に `has_password` を載せ、画面は偽なら変更フォームを出さない。**
6. **持たせるのは、管理者が明示的にパスワードを設定したときだけ**
   （`PUT /api/admin/users/{id}` の `password`）。監査に残る操作である。

## 理由

**「無い」は値である。** ランダム値は「無い」を表現するための代用で、代用だと分かるのは
書いた人だけになる。列を緩めれば、画面も監査も同じ 1 つの事実を読める。

**リセットを塞ぐのが、この決定のいちばんの中身である。** 列を NULL 許容にするだけなら
見た目が整うだけで、**入り口が黙って増える経路はそのまま残る**。リセットは「本人が
メールを受け取れる」ことしか確かめない。SSO でしか入れないと決めた利用者に対して、
それは認証手段を 1 つ増やす操作になる。

**ローカル口座を持たせる判断は、人が明示的に行う。** 「持たせない」が既定で、
持たせるなら管理者の操作として記録に残る。どちらとも決めていない状態を既定にしない。

### 検討して捨てた案

- **`credentials`（種別 + 値）テーブルへ出す**（idp の ADR-0049 I4 の第 2 案）。
  パスキー・TOTP と並べられて筋は良いが、**認証の口すべてを書き換える**話になる。
  表したいのは「無い」の 1 点なので、列を緩めるほうを採る。
- **`LOCAL_LOGIN_ENABLED` で足りるとする**（ADR-0026）。あれは**アプリ全体**の栓で、
  「この利用者には無い」は表せない。同じアプリに両方が居る構成を表現できない。
- **リセットは通す（従来どおり）。** 「本人がメールを受け取れるなら良いはず」という
  読み方もできるが、それは**利用者の入り口を増やす判断**であって、リセットという
  操作が持ってよい権限ではない。持たせるなら管理者が明示的に行う。

## 影響

- ⚠ **移行でランダム値を落とす**（`0008_password_is_optional`）。どの行がランダム値かは
  値からは分からないので、**利用者の行と IdP との結び付きが 60 秒以内に作られたか**で
  判断する（`provision` だけが両方を同じトランザクションで作る）。
  ⚠ **取り違えても入れなくなるだけで、増えることはない** ——落としすぎた利用者は
  管理者にパスワードを設定してもらう（気付ける失敗）。残した場合は黙って入り口が
  増える（気付けない）。非対称なので落とす側へ倒す。
- ⚠ **知らない DB 方言では移行が何もしない**（SQLite / PostgreSQL / MySQL / MariaDB を見る）。秒差を出す式が方言ごとに違うため。
  黙って全員のパスワードを落とすよりはましである（手当ては `docs/OPERATIONS.md`）。
- **アプリの外から `users` を作るコードは `password_hash` を省略できる**ようになった。
  省略すると「ローカル認証なし」の意味になるので、パスワードを持たせたい行では明示する。
- **G1（認証スタックの二重化）の前提が片付いた。** 「このアプリは SSO 専用か、
  ローカル口座を意図して持つか」を**行ごとに**表せるようになった（idp の ADR-0049 G1）。
