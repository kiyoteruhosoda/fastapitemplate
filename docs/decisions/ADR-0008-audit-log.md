# ADR-0008: 監査ログを `audit_log` として分け、閲覧を audit コンテキストに集約する

- 日付: 2026-07-30
- 状態: 承認

## 文脈

テンプレートには構造化ログの DB 保存（`log` テーブル）と、レベル・`requestId` だけで
絞り込める閲覧画面が既にあった。しかし運用で必要になる問い合わせのうち、次のものに
答えられなかった。

- 「このユーザーを無効にしたのは誰か」「いつ権限が変わったか」
  → `log` には INFO の 1 行（`item_created` 等）しか残らず、**実行者と対象**が無い。
- 「ログインの失敗が続いているアカウントはあるか」
  → 失敗は `HTTPException` で終わり、何も記録されない。
- 「先週の ERROR を、この時間帯のこのモジュールだけ見たい」
  → 画面の絞り込みがレベルと `requestId` だけで、期間・ロガー・本文で絞れない。

参考にした idp（Rust 製 IdP）は、この 2 つを**別のテーブル**として持っている。
`audit_log`（誰が何をしたか）と `log`（システムが何を失敗したか）で、`correlation_id`
（本テンプレートの `requestId` に相当）で突き合わせる設計である。

## 決定

1. **監査ログを `audit_log` テーブルとして分ける。** `log` に列を足して兼用しない。
2. **記録と閲覧を `bounded_contexts/audit/` に集約する。** 監査イベントの記録
   （Domain の列挙・Application のユースケース・Infrastructure の書き込み）と、
   監査ログ・アプリログ両方の検索をこのコンテキストが持つ。アプリログの
   **書き込み**は従来どおり `shared/kernel/logging`（全レイヤー横断の関心事）に残す。
3. **監査イベントは本処理とは別のトランザクションで書く。**
4. **記録する主体・対象は内部 ID のみ。** メールアドレス・ユーザー名・パスワード・
   トークン・設定値は記録しない。`reason` には「変更した項目名」「失敗の分類」を入れる。
5. **閲覧には専用 scope `audit:view` を要求する。** `log:view` では見られない。
6. リクエスト情報（`requestId`・IP・User-Agent・操作主体）は `contextvars` で伝播し、
   ルーターは追跡情報を引数で受け取らない。

## 理由

- **テーブルを分ける**: 保持したい期間と量がまったく違う。アプリログは大量・短命
  （`LOG_DB_MIN_LEVEL` で間引く対象）だが、監査ログは少量・長命で、間引いてよい行が
  無い。同じテーブルに載せると「アプリログを削る運用」が監査記録を壊す。列の意味も
  重ならない（`level` / `logger` に対して `event_type` / `result` / `actor` / `target`）。
- **別トランザクションで書く**: 最も記録したいイベントである**失敗したログイン**は
  401 で終わり、リクエストのセッションはロールバックされる。同じセッションで書くと
  記録が消える。代償として「操作は失敗したのに成功の監査行が残る」可能性が生まれるが、
  記録は `db.flush()` の後に行うため実際に起きるのは commit 時の障害のみで、
  「失敗が記録されない」ことより軽い。
- **記録の失敗で本処理を落とさない**: マイグレーション前・DB 障害時に、監査が書けない
  ことを理由にログインやユーザー管理を止める方が運用への影響が大きい。失敗はアプリ
  ログへ `ERROR` で残す（そちらの画面で気付ける）。
- **内部 ID のみを記録する**: CLAUDE.md「ログ」の PII 非記録方針を守りつつ、監査の
  目的（操作を主体へ帰属させる）を満たせる最小の情報である。`log` 側は
  `user_id_hash`（不可逆）を使うが、監査ログは**後から誰か特定できなければ意味がない**
  ため、ハッシュではなく内部の代理キー（`users.id`）を持つ。個人情報そのものは
  含まないため PII ではない。ID から人へ辿るのは管理画面のユーザー一覧の役割とする。
- **`audit:view` を分ける**: 監査ログは「誰が」を追える記録で、アプリログより取り扱いが
  重い。運用担当にエラーログを開放しつつ、操作履歴は管理者に限る運用ができる。
- **`contextvars` で伝播する**: 監査もログも横断的関心事で、`requestId`・IP を引数で
  全ルーターへ通すと本来の責務が埋もれる。認証依存関数が主体を設定するため、
  ルーターが「誰が」を渡し忘れて記録が空になることも防げる。
- **アプリログの書き込みを audit へ移さない**: すべてのモジュールが `logging` で書く
  ため、書き込み側をコンテキストに閉じ込めると全コードが audit コンテキストに依存する。
  読み取り（管理画面の機能）だけを移す方が依存が素直になる。

検討して採らなかった案:

- **`log` に `event_type` / `actor_user_id` を足して 1 テーブルにする**: 上記のとおり
  保持方針が衝突する。また、監査行だけを消さずにアプリログを削る条件が複雑になる。
- **監査を本処理と同じトランザクションで書く（原子性を優先）**: 失敗したログイン・
  失敗した権限変更が記録されない。監査の主目的を外す。
- **監査ログをファイル（stdout）だけに出す**: 管理画面から検索できず、
  「誰がいつ何をしたか」を追うのに DB へ入れ直す運用が要る。
- **`log:view` で監査ログも見せる**: 権限の粒度を落とすだけで得るものがない。

## 影響

- マイグレーションを 2 本追加する。`0004_audit_log`（`audit_log` テーブル、
  および `log` の `level` / `logger` / `user_id_hash` 索引）と
  `0005_seed_audit_permission`（`audit:view` の投入。`seed_master_data` の再実行）。
- **既存 API の互換性を破る**: `GET /api/admin/logs` の応答が配列から
  `{"total": n, "entries": [...]}` に変わる。総件数が無いとページ送りの可否を画面が
  判断できないため。同梱のフロントエンドは追随済み。
- 画面が 1 つ増える（`/admin/audit-logs`、要 `audit:view`）。サイドバーは scope で
  出し入れするため、権限の無い利用者には現れない。
- 設定キー `LOG_DB_MIN_LEVEL` を追加する（既定 `INFO` = 従来と同じ挙動）。
  DB へ書く下限を stdout と独立に上げられる。
- `audit_log` には外部キーを張らない。ユーザーを削除しても「誰が何をしたか」の行を
  残すため。削除済みユーザーの ID は一覧から辿れなくなる（そのための
  `user.deleted` イベントが残る）。
- **`audit_log` は無期限に増える。** 監査記録は勝手に消してよいものではないため、
  自動削除は入れていない。保持期間の運用は今後の課題（`docs/Progress.md` T2）。
- `AuditEventType` / `AuditTargetType` の値は DB に入る安定キーになる。一度使った値は
  変えない（`tests/unit/domain/test_audit_event.py` が値を固定して改名を落とす）。
- ログアウトは監査しない。Cookie を落とすだけの未認証エンドポイントで、操作した
  利用者を特定できないため。監査する場合は認証を要求する設計変更が必要になる。
