# ADR-0075: ログと監査

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0013（§1）・旧 ADR-0019（§2）・旧 ADR-0021（§3）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

アプリは 2 種類の記録を DB に持つ。アプリログ（`log`。システムが何を失敗したか）と
監査ログ（`audit_log`。誰が何をしたか）である。参考にした idp（Rust 製 IdP）も 2 つを別の
テーブルに持ち、`correlation_id`（本テンプレートの `requestId`）で突き合わせている。

運用では「誰がこのユーザーを無効にしたか」「ログインの失敗が続いているか」「どのエラーコードで
落ちたか」に答え、期間・ロガー・本文で絞り込める必要がある。失敗はルーターの外（例外ハンドラ）で
応答に変わるため、ルーターにログを書いても残らない。2 つのテーブルは増え続けるが、保持期間は
運用・監査の要件で決まり、テンプレートが勝手に決めてよいものではない。

## 決定

### §1 監査ログを `audit_log` として分け、閲覧を audit コンテキストに集約する

1. **監査ログを `audit_log` テーブルとして分ける。** `log` に列を足して兼用しない。
2. **記録と閲覧を `bounded_contexts/audit/` に集約する。** 監査イベントの記録
   （Domain の列挙・Application のユースケース・Infrastructure の書き込み）と、
   監査ログ・アプリログ両方の検索をこのコンテキストが持つ。アプリログの
   **書き込み**は `shared/kernel/logging`（全レイヤー横断の関心事）に残す。
3. **監査イベントは処理の途中で控えに積み、リクエストの処理が完全に終わってから
   別トランザクションでまとめて書く。** 書くのは素の ASGI ミドルウェア
   （`await self.app(...)` の後）で、`BaseHTTPMiddleware` は使わない。
4. **記録する主体・対象は内部 ID のみ。** メールアドレス・ユーザー名・パスワード・
   トークン・設定値は記録しない。`reason` には「変更した項目名」「失敗の分類」を入れる。
   **実行者（`actor_user_id`）を入れるのは認証済みのリクエストだけ**とし、未認証の
   操作（ログイン失敗・パスワードリセット）は相手を `target` として記録する。
5. **閲覧には専用 scope `audit:view` を要求する。** `log:view` では見られない。
   どのロールがどちらを持つか、どのテナントの記録が見えるかは ADR-0079 §3・§2 決定 5。
6. リクエスト情報（`requestId`・IP・User-Agent・操作主体）は `contextvars` で伝播し、
   ルーターは追跡情報を引数で受け取らない。

### §2 アプリログは失敗を中心に残し、記録の場所とレベルを 1 か所で決める

1. **失敗の記録を `presentation/fastapi/error_handling.py` に集約する。**
   `HTTPException`・`RequestValidationError`・`Exception` のハンドラをここで登録し、
   ドメイン例外のハンドラ（各コンテキストの `error_handling`）は記録だけを
   `log_failed_request()` に委ねる。ルーターに `try/except` を書き足さない。
2. **ログのレベルはステータスコードから決める**（`log_level_for_status()`）。
   5xx → ERROR、4xx → WARNING、401 と成功 → INFO。アクセスログと失敗の記録が
   同じ関数を使う。
3. **想定外の例外は `InternalErrorMiddleware`（最も内側）で応答へ変える。**
   `Exception` ハンドラは保険として残す。このミドルウェアも**素の ASGI** で書く。
4. **死活監視・メトリクスのパス（`/healthz` `/readyz` `/api/health` `/metrics`）は
   アクセスログに残さない。ただし 4xx・5xx は残す。**
5. **ログ基盤の失敗は黙らない。** `DbLogHandler` は `handleError()`（stderr）で
   知らせ、設定の DB 読み取り不能は状態が変わったときだけ 1 行警告する。

### §3 ログの保持期間を設定キーで持ち、常駐スレッドで掃除する

1. **保持期間を設定キーで持つ。** `LOG_RETENTION_DAYS` と
   `AUDIT_LOG_RETENTION_DAYS` を分けて持ち、**どちらも既定は `0`（＝削除しない）**。
   `0` と負の日数はどちらも「削除しない」。境界は `<` で比べ、ちょうど境界の行は残す。
2. **掃除は常駐スレッドで定期実行する。** 汎用の `IntervalWorker`
   （`shared/kernel/scheduling`）で、`web` プロセスの起動時から「期限切れログの削除」を
   6 時間間隔で回す。起動直後にも 1 回走る。設定は周回のたびに読む。
3. **削除は主キーで小分けにし、1 塊ごとにトランザクションを閉じる。**
   「消す ID を選ぶ → その ID を消す」の 2 段で行う。

## 理由

### §1

- **テーブルを分ける**: 保持したい期間と量がまったく違う。アプリログは大量・短命
  （`LOG_DB_MIN_LEVEL` で間引く対象）、監査ログは少量・長命で間引いてよい行が無い。
  同じテーブルだと「アプリログを削る運用」が監査記録を壊す。列の意味も重ならない
  （`level` / `logger` に対して `event_type` / `result` / `actor` / `target`）。
- **別トランザクションで書く**: 最も記録したい**失敗したログイン**は 401 で終わり、
  リクエストのセッションはロールバックされる。同じセッションで書くと記録が消える。
  代償に「操作は失敗したのに成功の監査行が残る」ことがあり得るが、起きるのは commit 時の
  障害のみで、「失敗が記録されない」より軽い。
- **書くのは処理が終わってから**: 途中で別コネクションから書くと、**SQLite では
  リクエストのセッションが握った書き込みロックと衝突する**。`db.flush()` を通る操作が
  busy timeout（5 秒）待った末に `database is locked` で失敗し、記録側が例外を握りつぶすため
  「操作は成功したのに監査ログだけ残らない」。途中は控えに積むだけ（I/O なし・失敗しない）に
  し、書き込みは 1 回にまとめる。MariaDB では競合しないが、開発・試験が SQLite
  （ADR-0071 §1）なのでバックエンドで挙動が変わる設計は採らない。
- **素の ASGI で書く**: FastAPI は `yield` を使う依存（`get_db` の commit）を
  **レスポンス送出の後**に閉じる。`BaseHTTPMiddleware` の `call_next` はレスポンスの先頭を
  受け取った時点で戻るので、まだセッションが開いており上の競合が起きる。
  `await self.app(...)` は下流を最後まで待つので、確実に commit / rollback の後になる。
- **実行者は認証済みのときだけ**: `POST /api/auth/forgot-password` はメールアドレスを
  知っていれば誰でも叩ける。持ち主を `actor_user_id` に据えると、第三者が起こした
  イベントを**本人の操作として記録してしまう**。ログイン失敗も同じで、分かっているのは
  「誰に対しての操作か」だけなので `target` に入れる。
- **記録の失敗で本処理を落とさない**: 監査が書けないことでログインや管理を止める方が影響が
  大きい。失敗はアプリログへ `ERROR` で残す。
- **内部 ID のみ**: CLAUDE.md「ログ」の PII 非記録方針を守りつつ、操作を主体へ帰属させる
  最小の情報である。`log` 側は `user_id_hash`（不可逆）を使うが、監査ログは**後から誰か
  特定できなければ意味がない**ため内部の代理キー（`users.id`）を持つ。ID から人へ辿るのは
  管理画面のユーザー一覧の役割。
- **`audit:view` を分ける**: 監査ログは「誰が」を追える記録で、アプリログより扱いが重い。
- **`contextvars` で伝播する**: 引数で全ルーターへ通すと責務が埋もれ、渡し忘れで記録が空になる。
- **アプリログの書き込みを audit へ移さない**: 全モジュールが `logging` で書くので、
  移すと全コードが audit に依存する。読み取りだけを移す。

検討して採らなかった案:

- **監査を本処理と同じトランザクションで書く**: 失敗したログイン・権限変更が残らない。
- **処理の途中でその場で別コネクションへ書く**: SQLite で書き込みロックと競合する。
  共通のフィクスチャが in-memory + `StaticPool`（全員が 1 本のコネクションを共有）だと
  検出できないため、ファイル実体の SQLite を使う統合試験
  （`tests/integration/api/test_audit_write_isolation.py`）で落とす。
- **監査ログを stdout だけに出す**: 管理画面から検索できない。

### §2

- **失敗はルーターの外側で起きる**ので、記録をハンドラへ置けば漏れが構造的に無くなり、
  レベルと項目（`error_code` / `invalid_fields` / `status_code`）も揃う。ルーターごとに
  書くと、書き忘れた経路だけが静かに消える。
- **想定外の例外の受け皿を内側に置く**: Starlette の `ServerErrorMiddleware`（最も外側）に
  任せると traceback が DB に残らず、まとめ書き（`DeferredLogWriteMiddleware`）も飛ばされて
  そのリクエストのログ行ごと失われる。
- **`InternalErrorMiddleware` を素の ASGI で書く**: `BaseHTTPMiddleware` は下流を
  **別のタスク**で走らせ、そこで設定された `contextvars` が `dispatch` 側へ伝わらない。
  認証依存関数が設定する `user_id_hash` がそれで、500 の行だけ「誰のリクエストか」が空になる
  （§1 のまとめ書きと同じ事情）。
- **`RequestLoggingMiddleware` も素の ASGI で書く**（task #808）: 同じ理由で `http_request` の行の
  `user_id_hash` が空だった。行を出すのは下流が終わった後でなく**応答の先頭を送るとき**にする。
  `call_next` が戻るのと同じ時点なので `duration_ms` の意味が変わらず、大きなファイルの流し読みで
  途中で接続が切れても行が残る。
- **レベルの方針を 1 か所に置く**: アクセスログと失敗の記録で判断が割れると、WARNING で
  絞ったとき片方だけ出てくる。401 だけ INFO に落とすのは、トークンの期限切れ・未ログインでの
  呼び出しがふつうに起き、WARNING の大半が正常系で埋まるため。
- **プローブを残さない**: 数十秒おきの成功したプローブは情報を持たないのに、見たい行を
  押し流す。`LOG_DB_MIN_LEVEL` を上げる案は他の INFO（`login_succeeded` 等）まで消える。
  **失敗したプローブは残す**——プローブが落ちていること自体が知りたい情報である。
  除外するパスを設定キーにはしない。アプリが自分で公開している口で、環境ごとに変わらない。
- **入力検証の記録には項目名と理由だけを入れる**（`body.email:missing`）。`ctx` や
  `input` を入れるとメールアドレス・パスワードがログへ移る（CLAUDE.md「ログ」）。
- **ログ基盤の失敗を黙らせない**: `pass` で捨てると「ログが出ない」「設定が効かない」という
  症状だけが残り、原因（DB 未接続・移行前）が分からない。

### §3

- **設定キーにする**: 保持期間は環境ごとに違う。手順書だと実行が人に依存する。既定 `0` なので
  **何も決めないうちに消し始める**ことは無い。
- **2 つのキーに分ける**: §1 でテーブルを分けた理由そのもの。監査ログに保持期間を持たせない案は、
  保持期間が法令・社内規程で決まる環境で手動 SQL に戻る。
- **負の日数も「削除しない」**: 打ち間違い（`-30`）が未来の境界になり直近の行まで消す事故を防ぐ。
- **常駐スレッドにする**: 起動時 1 回だけでは長く動くプロセスで掃除されない。外部の
  cron に任せると「配っただけでは効かない設定」が増える。
- **スケジューラのライブラリ（APScheduler 等）を入れない**: 要るのは「一定間隔で 1 つの
  仕事」だけ。`RestartWatcher`（ADR-0074 §2）と同じ形の常駐スレッドで揃えられる。
- **二重実行の排他を持たない**: Gunicorn は複数ワーカーで動くので掃除はプロセスの数だけ
  走るが、「期限より古い行を消す」は冪等で結果は変わらない。排他のためのロックや専用表は、
  壊れたとき「掃除が永久に走らない」影響の方が大きい。**渡す仕事を冪等なものに限る**。
- **設定を周回のたびに読む**: 画面で日数を変えたら次の周回から効く。設定定義に
  `restart_scopes` を付けていないのはこのため（再起動が要る設定と区別する。ADR-0074 §2）。
- **小分けにする**: 初回は数十万行が対象になり得る。1 文の `DELETE` は MariaDB では長い
  トランザクションに、SQLite では DB 全体の書き込みロックを握り続け、リクエストを待たせる。
  `DELETE ... LIMIT` はバックエンド依存（Python 同梱の SQLite で使えない）なので 2 段にする。
- **消した行数をアプリログへ残す**: 掃除が効いているかを画面で確かめるため。何も消さなかった
  回は書かない。数えるのは**実際に消えた行数**（`DELETE` の影響行数）で、選んだ ID の数では
  ない（同時に走るワーカーが同じ ID を選ぶと件数が膨らむ）。一方、**次の塊へ進むかは選んだ
  件数で判断する**。消せた数で判断すると、先を越された塊で「もう対象が無い」と打ち切る。

## 影響

### §1

- 移行 `0004_audit_log`（`audit_log` と、`log` の `level` / `logger` / `user_id_hash` 索引）と
  `0005_seed_audit_permission`（`audit:view` の投入）。
- `GET /api/admin/logs` の応答は `{"total": n, "entries": [...]}`（総件数でページ送りを判断する）。
- 画面 `/admin/audit-logs`（要 `audit:view`）。サイドバーは scope で出し入れする。
- 設定キー `LOG_DB_MIN_LEVEL`（既定 `INFO`）で、DB へ書く下限を stdout と独立に上げられる。
- 設定キー `TRUSTED_PROXY_HOPS`（既定 `0`）。`ip_address` は監査ログに残る値だが、
  `X-Forwarded-For` は送信元が自由に付けられ、nginx の `$proxy_add_x_forwarded_for` は受け取った
  値の後ろに実際の接続元を足す。左端を採ると任意の IP を記録させられるため、**信頼する段数を
  宣言したときだけ**右から数えてその位置の値を採り、既定ではヘッダーを見ずに TCP の接続元を使う。
  同梱の docker-compose では `TRUSTED_PROXY_HOPS=1`。
- ⚠ **サーバー層（Gunicorn / Uvicorn）の転送ヘッダー処理は切ってある。** 既定では
  `X-Forwarded-For` の**左端**で `scope["client"]` を書き換えるため（Uvicorn の既定は
  `forwarded_allow_ips=127.0.0.1`）、アプリの判定より先に詐称値が入る。`scripts/entrypoint.sh` の
  `--forwarded-allow-ips=""` と `main.py` の `proxy_headers=False` を外さない。
- `audit_log` には外部キーを張らない。ユーザーを消しても行を残すため（`user.deleted` が残る）。
  削除済みユーザーの ID は一覧から辿れなくなる。
- `AuditEventType` / `AuditTargetType` の値は DB に入る安定キー。一度使った値は変えない
  （`tests/unit/domain/test_audit_event.py` が値を固定して改名を落とす）。
- ログアウトは監査しない。Cookie を落とすだけの未認証の口で、利用者を特定できないため。
- 機械が利用者として操作したときの帰属は ADR-0082 §1 決定 4。

### §2

- 成功したプローブの行は残らない。死活は Pod の状態か `/metrics` で見る。
- 404・409・422 が WARNING として残るので、「WARNING が出ている＝障害」ではない。障害の判定は ERROR で行う。
- 監査ログとは重ならない。監査は「誰が何をしたか」、アプリログの失敗記録は「どの呼び出しが
  どのコードで落ちたか」で、突き合わせは `requestId`。
- 新しいドメイン例外ハンドラを足すときは `log_failed_request()` を呼ぶ。呼ばないとその例外だけ記録が抜ける。

### §3

- 既定のままなら何も消えない。手動 SQL（`docs/OPERATIONS.md`）も引き続き使える。
- 定期実行を足したくなったら `start_interval_worker(name, job, interval_seconds)` を呼ぶ。
  ⚠ **渡す仕事は冪等でなければならない**（複数ワーカーで同時に走る）。
- 掃除の間隔（6 時間）は定数で、設定にしない。運用者が決めるのは「何日残すか」である。
- ⚠ 監査ログを消す設定を入れると、**消した記録は復元できない**。監査の要件を満たすかの判断は運用側に残る。
- `TESTING` のときワーカーは起動しない。掃除そのものは `purge_expired_logs_once()` を直接呼んで確かめる。
