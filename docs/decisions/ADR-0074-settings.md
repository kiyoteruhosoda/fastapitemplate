# ADR-0074: 設定

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0034（§1）・旧 ADR-0004（§2）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

システム設定は `ApplicationSettings`（`shared/kernel/settings/settings.py`）が値を解決し、
管理画面から保存できる。保存した値がどの順で効くかと、起動時にしか読まれない設定を保存したとき
どう反映させるかを決める必要があった。

## 決定

### §1 画面で保存した設定は環境変数より強い

派生アプリ（nolumiadeck）で、compose に 1 行書いてあった鍵（`RELEASE_MACHINE_CLIENTS`）を運用中に
足そうとしたところ、管理画面の入力欄が「環境変数で固定されています」と無効化されて触れなかった。
直すには compose を編集して配り直すしかなかった。運用中に決め直すための画面が、配るときに 1 行
書いたせいで使えなくなるのは順序が逆である。

1. **解決順は DB（`system_settings`）> 環境変数 > デフォルト値とする。**
2. **環境変数は「配るときの初期値」である。** compose や宣言に書くのは、まだ誰も画面で決めていない鍵に
   初期値を与えるため。
3. **運用中に決め直す場所は画面である。** 保存した値がいちばん強い。
4. 画面で**消す**と環境変数へ戻り、環境変数も無ければ既定値へ戻る。
   ⚠ **既定値へ飛ばさない。** 「配ったときの姿へ戻る」が期待に合う。
5. 入力欄は無効化しない。画面には `env_fallback`（**消すと環境変数へ戻る**という案内）を出す。

⚠ **ブートストラップの鍵はこの順序の外。** `DATABASE_URI` などは `ApplicationSettings` の別の節で
環境変数を直接読む（解決に DB 接続が要る鍵を DB から読むと再帰する）。

### §2 起動時にしか読まれない設定は、DB 経由の再起動要求で反映する

保存した設定は DB 上書きキャッシュを捨てれば即時に効くが、アプリケーションファクトリ（`create_app`）で
一度だけ評価されるものは効かない（`LOG_LEVEL` / `LOG_TO_DATABASE` は `setup_logging()`、
`CORS_ALLOWED_ORIGINS` は `CORSMiddleware` の登録時に確定する）。保存しても何も変わらないのに
画面上は成功と出る状態だった。

1. 設定定義に `restart_scopes` を持たせ、保存 API の応答で「どの設定の反映にどのサービスの再起動が
   要るか」を返す。
2. 再起動は DB（`system_settings` の `app.restart_request`）に要求を置き、各プロセスが監視スレッド
   （`RestartWatcher`）で拾って**自分自身を終了**させる。復帰はコンテナの再起動方針に任せる
   （compose は `restart: unless-stopped`、k3s は Pod の既定の再起動）。
3. 再起動の口は `POST /api/admin/system/restart` 1 つにする（`POST /api/admin/maintenance/shutdown` は
   削除した）。

## 理由

### §1

- 運用中に触りたい鍵は実際にあり、そのたびに配り直すのは重い。画面を持つ以上、画面が勝たなければ
  画面の意味が無い。
- 採らなかった案:
  - **環境変数だけを正にする**（画面を読み取り専用にする） —— 筋は通るが、管理画面の設定機能そのものが
    要らなくなる。
  - **鍵ごとにどちらが強いかを選べるようにする** —— 一貫性が消える。「この鍵はどっちで決まるんだったか」を
    毎回調べることになり、同じ罠が形を変えて残る。
  - **環境変数が強いまま、画面に「効きません」と出す** —— ⚠ 出ていても直せないことに変わりはない。

### §2

- **DB 経由にする。** 管理 API を処理したプロセスと、再起動すべきプロセスは別である。Gunicorn は複数ワーカーで
  動き、サービスを分ければ別コンテナになる。DB に置けば、docker socket や k8s の API に触れずに全プロセスへ届く。
- **時刻ではなく token の変化で判定する。** 「保存時刻が起動時刻より後なら再起動」にすると、アプリと DB の
  時計がずれている環境で再起動ループに陥る。起動時に読んだ token と違うかどうかだけを見る。
- **スコープごとに要求を保持する。** 単一レコードを上書きすると、ポーリング間隔の内側に 2 件入ったとき、
  先の要求を読む前に消える。サービスを足したときに壊れない形にしておく。
- **`maintenance/shutdown` を消した。** あれは自プロセスへ SIGTERM を送るもので、Gunicorn 配下ではワーカーが
  1 つ落ちてアービターが同じ環境で作り直すだけで、設定は反映されない。「終了方法はプロセス構成で変わる」という
  知識を `build_process_terminator()` に集約し、入口も 1 つにする。

## 影響

### §1

- ⚠ **締め出しからの戻り道は `scripts/unset_setting.py`** で、保存を 1 鍵だけ消す（手順は `docs/OPERATIONS.md`）。
  `LOCAL_LOGIN_ENABLED=false` で締め出されても、環境変数を書き換えるだけでは戻らない（ADR-0076 §3）。
  ⚠ **行ごと消さない** —— `system_settings` の 1 行に全部の鍵が入っているので、他の設定まで既定へ戻る。
- ⚠ **この順序に入れ替えると、DB に入っている値の意味が変わる。** 「保存したが効かなかった」値が効き始める。
  入れ替える派生アプリは、配る前に DB に保存されている鍵と環境変数の重なりを見ること（重なりが無ければ
  挙動は変わらない）。
- ⚠ **派生アプリにも同じ入れ替えが要る。** この雛形から作った 5 本（nolumiadeck / nolumiawiki / blobshare /
  mp3play / rewardpointsweb）は同じ `_get` を持つ。既定の秘密を弾く類の判定は「解決を通した後の値」で
  行っているので、順序が変わっても結論は変わらない。

### §2

- 再起動要求から実際の再起動まで最大 10 秒（`DEFAULT_POLL_INTERVAL_SECONDS`）かかる。応答が返った時点では
  まだ再起動していない。
- コンテナが再起動方針無しで動いている場合、終了したまま戻らない。
- `TESTING` のときウォッチャーは起動しない（テストが自分を落とさないため）。
- 起動時にだけ読まれるのではなく毎回読む設定には `restart_scopes` を付けない（ADR-0075 §3）。
