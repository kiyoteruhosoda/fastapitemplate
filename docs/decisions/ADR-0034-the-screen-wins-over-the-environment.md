# ADR-0034: 画面で保存した設定は環境変数より強い

- 日付: 2026-09-10
- 状態: 承認

## 文脈

`ApplicationSettings` は長らく **環境変数 > DB > デフォルト値** の順で値を解決して
いた。文書にもそう書いてあり（`ARCHITECTURE.md` / `ER.md` / `OPERATIONS.md` /
`README.md` / `CLAUDE.md`）、ADR-0026 はこの順序に頼った復旧手順まで書いていた。

⚠ **これは「決めた」というより「そう書いたから、そういうことになっていた」に近い。**
順序を選んだ理由はどこにも残っていない。

実際に困ったのは 2026-09-10 である。派生アプリ（nolumiadeck）で、compose に
1 行だけ書いてあった鍵を運用中に足そうとしたところ、**管理画面の入力欄が
無効化されていて触れなかった**。画面には出ている。値も見えている。だが変えられない。

```
compose.yaml:  - RELEASE_MACHINE_CLIENTS=ab0b1c9b…
画面:          RELEASE_MACHINE_CLIENTS  [ab0b1c9b…]  環境変数で固定されています
```

⚠ **直すには、その鍵を渡している compose を編集して、配って、起こし直すしか
なかった。** 運用中に決め直すための画面が、**配るときに 1 行書いたせいで
使えなくなる**。これは順序が逆である。

## 決定

**解決順を DB > 環境変数 > デフォルト値にする。**

- **環境変数は「配るときの初期値」**である。compose に書くのは、まだ誰も画面で
  決めていない鍵に初期値を与えるため
- **運用中に決め直す場所は画面**である。保存した値がいちばん強い
- 画面で**消す**と環境変数へ戻り、環境変数も無ければ既定値へ戻る
  ——⚠ **既定値へ飛ばさない。** 「配ったときの姿へ戻る」が期待に合う
- `env_locked`（保存を止める印）をやめ、`env_fallback`（**消すと環境変数へ
  戻る**という案内）にする。入力欄はもう無効化しない

⚠ **ブートストラップの鍵はこの順序の外。** `DATABASE_URI` などは
`ApplicationSettings` の別の節で環境変数を直接読む（解決に DB 接続が要る鍵を
DB から読むと再帰する）。

## 影響

- ⚠ **締め出しからの戻り道が変わる。** ADR-0026 は
  「`LOCAL_LOGIN_ENABLED=false` で締め出されたら環境変数で戻す」と書いていたが、
  **もう効かない**。代わりに `scripts/unset_setting.py` で**保存を 1 鍵だけ消す**
  （`docs/OPERATIONS.md` に手順を書いた）。⚠ **行ごと消さない** ——
  `system_settings` の 1 行に全部の鍵が入っているので、他の設定まで既定へ戻る
- ⚠ **入れ替えると、いま DB に入っている値の意味が変わる。** それまで「保存
  したが効かなかった」値が効き始める。**配る前に、DB に保存されている鍵と
  環境変数の重なりを見ること**（重なりが無ければ挙動は変わらない）
- ⚠ **派生アプリにも同じ入れ替えが要る。** この雛形から作った 5 本
  （nolumiadeck / nolumiawiki / blobshare / mp3play / rewardpointsweb）は
  同じ `_get` を持つ。⚠ **既定の秘密を弾く類の判定は「解決を通した後の値」で
  行っているので、順序が変わっても結論は変わらない**（派生側の同種の ADR も同じ）

## 検討したが採らなかった案

**env だけを正にする**（画面を読み取り専用にする）。筋は通るが、**管理画面の
設定機能そのものが要らなくなる**。運用中に触りたい鍵は実際にあり、そのたびに
配り直すのは重い。

**鍵ごとにどちらが強いかを選べるようにする。** 一貫性が消える。「この鍵はどっちで
決まるんだったか」を毎回調べることになり、いま踏んだ罠が形を変えて残る。

**env が強いまま、画面に「効きません」と出す。** いまと同じである
（実際 `env_locked` はそう出していた）。⚠ **出ていても直せないことに変わりはない。**
