# ADR-0018: ロール一覧の取得は `user:manage` でも許可する（変更は `role:manage` のまま）

- 日付: 2026-08-01
- 状態: 承認

## 文脈

`GET /api/admin/roles` はロール管理 API の一部として `role:manage` で守られていた。
一方でユーザー管理画面（`user:manage`）は、ユーザーへロールを割り当てるために
**どんなロールがあるか**を知る必要がある。

`user:manage` だけを持つロール（「ユーザー係」）を作ると、ユーザー管理画面から
ロール一覧の取得が 403 になる。画面はロール一覧を空として扱うため、割り当ての
選択肢が消え、既存の割り当ても表示できなくなる。

## 決定

- `GET /api/admin/roles` は `role:manage` **または** `user:manage` のいずれかで通す。
- ロールの作成・更新・削除は従来どおり `role:manage` のみ。
- 「いずれか 1 つ」を宣言する依存関数 `require_any_permission()` を追加する
  （`presentation/fastapi/dependencies/auth.py`）。**読み取りにのみ使う**。

## 理由

- 「ユーザーにロールを割り当てられる（`user:manage`）」ことは、「どんなロールが
  あるか読める」ことを前提にしている。前提が権限として表現されていないと、
  画面が成立しない権限の組み合わせが作れてしまう。
- 一覧が漏らすのはロール名と割り当て済みの権限コードで、いずれも PII ではなく、
  `user:manage` を持つ者はユーザーのロールを通じて同じ情報に触れられる。
  読み取りを許しても新たに増える情報は無い。
- 代替案「ユーザー管理向けに読み取り専用のロール一覧エンドポイントを別途足す」は
  採らなかった。同じ資源に 2 つの入口ができ、`RoleResponse` の変更が二重管理になる。
- 代替案「ユーザー管理画面を `role:manage` も要求する形にする」も採らなかった。
  ユーザー係にロールの**編集**権限まで渡すことになり、最小権限に反する。
- `require_any_permission()` を書き込みに使わないのは、権限を足す操作の条件が
  「いずれか」になると、どの scope で許されたのかが監査から読み取りにくくなるため。

## 影響

- `require_permission()`（全て必要）と `require_any_permission()`（いずれか）の
  2 種類が並ぶ。新しいエンドポイントは原則として前者を使い、後者は
  「複数の職掌が同じ資源を読む」場合に限る。
- ロール一覧が読める範囲が広がるため、ロール名には秘匿情報を入れない前提を保つ。
- 画面側は、それでも一覧を取得できない場合（さらに絞ったロール）に備えて、
  ユーザーに既に割り当てられているロール名から列を補う（割り当ての表示を失わない）。
