# ADR-0027: 入力はダイアログに出し、狭い画面では幅いっぱいのシートにする

- 日付: 2026-09-04
- 状態: 承認

## 文脈

ADR-0011 で狭い画面への対応（ブレークポイント 1 つ・ドロワー・表の横スクロール・
指で押せる大きさ）を入れたが、**画面が扱うデータへ届くまでの距離**は手つかずだった。
390px 幅で開くと次の状態になる。

| 画面 | 最初の 1 画面に出るもの | 一覧の 1 件目までの距離 |
|---|---|---|
| ユーザー管理（S8） | 追加フォーム 5 項目 | 約 900px スクロール |
| ロール管理（S9） | 追加フォーム | 約 350px |
| 監査ログ（S13） | 絞り込み 8 項目 | 約 1,300px |
| システムログ（S12） | 絞り込み 6 項目 | 約 1,200px |

いずれも「その画面でいちばんよく行う操作」ではない入力が先に来ている。
一覧を見に来た人は毎回それを読み飛ばし、たまに使う追加フォームは常に場所を取る。

同時に、権限・ロールの対応表（S8・S9）は**広い画面でも収まっていなかった**。
列見出しが `admin:system-settings` のような値そのもので、横に並べると 1 列で
12rem を超える。カードの上限（62rem）と相まって、1920px の画面でも表が横スクロールし、
行の見出し（ユーザー名・ロール名）が画面の外へ流れて「どの行のチェックを触って
いるのか」が分からなくなっていた。`RolesPage` の `<th className="vertical">` は
**その対処を意図した痕跡だが、`index.css` に `.vertical` の定義が無かった**。

## 決定

**入力の面を 3 つの形に分ける。**

1. **追加（作成）フォームは `<dialog>` に出す。** 画面には「追加」ボタンだけを置き、
   一覧を先頭に出す。狭い画面（768px 以下）では画面の下から**幅いっぱい**の
   シートとして開き、広い画面では中央のダイアログとして開く。
   共通部品は `components/FormDialog.tsx`。
2. **ログの絞り込みは畳めるようにする。** 狭い画面では既定で畳み、「絞り込み」で
   開く。広い画面では開閉ボタンごと消して常に見せる（今までどおり）。
   共通部品は `components/FilterPanel.tsx`。
3. **対応表は列見出しを縦組みにし、行の見出しを左端に固定する**（`.matrix`）。
   カードの幅の上限も外す。

**どの形で出すかは `index.css` が決める。** コンポーネントは今までどおり画面幅を
判定せず、「開いているか」だけを状態として持つ（ADR-0011 を引き継ぐ）。

## 理由

- **狭い画面では、重ねる面を幅いっぱいに使うのがいちばん素直。** 左右に余白を
  残したダイアログは、1 行あたりの文字数を減らすだけで得るものが無い。
  下端に寄せると、決定と取り消しが親指の届く位置に来る。
- **`<dialog>` + `showModal()` を使い、モーダルを自前で組まない。** フォーカスの
  閉じ込め・Esc での取り消し・背後の不活性化・重ね順（top layer）がブラウザの
  実装で済む。自前で組むと、ヘッダー（`position: sticky`）やドロワーとの重ね順、
  閉じたあとのフォーカスの戻し先を画面ごとに間違える（ADR-0011 の「影響」で
  ドロワーに対して同じ手当てを書いたが、面が増えるたびに写経することになる）。
- **絞り込みはモーダルにしない。** 広い画面では畳まずに見せたいが、`role="dialog"` や
  `aria-modal` は CSS で外せない（属性は幅に追随できない）。開閉する区画
  （`aria-expanded` + `aria-controls`）にしておけば、**広い画面では開閉ボタンを
  `display: none` にするだけで**「常に開いている区画」として正しい意味になる。
- **表はカード表示に変えない**（ADR-0011 の判断を維持）。どの列を落とすかは画面
  ごとの決めごとになる。代わりに、横スクロールのまま読めるようにする
  （行の見出しを固定し、列見出しを縦組みにして 1 列 2.5rem 前後まで詰める）。
  実測では、ロール管理の 11 列が 390px 幅で 2 列しか見えなかったのが 4 列になり、
  1280px 幅では横スクロールが消えた。
- 捨てた代替案:
  - **追加フォームを一覧の下へ移すだけ** — 一覧は先に来るが、フォームは相変わらず
    常に場所を取る。画面を離れずに追加できる利点も無い。
  - **絞り込みも `<dialog>` に入れる（両方の幅で）** — 部品が 1 つで済む代わりに、
    広い画面で「検索条件を変えるのに毎回開く」ことになる。**利用者が求めたのは
    狭い画面の改善**であり、広い画面を悪くする理由が無い。
  - **`matchMedia` で幅を判定し、狭い画面だけ別の部品を描く** — ADR-0011 で
    退けたとおり、CSS のブレークポイントと二重管理になる。
  - **列見出しを省略形にする（`admin:system-settings` → `sys-set`）** — 画面の値と
    API・監査ログに出る値が食い違う。ユビキタス言語を画面の都合で言い換えない。
  - **`<details>` / `<summary>` で絞り込みを畳む** — `open` 属性は CSS から操作
    できないため、広い画面で「常に開いた状態」にする方法が無い。

## 影響

- **一覧の画面に追加フォームを直接置かない。** 追加は「追加」ボタン + `FormDialog`
  にする。`FormDialog` は**開いているあいだだけ描画する**（`{open && <FormDialog …>}`）。
  閉じた `<dialog>` を DOM に残すと、中の入力欄が読み上げとテストの検索対象として
  一覧側の同名の項目と二重に見つかる。
- **引き金・見出し・決定のボタンで言い方を揃える。** 「ユーザーを追加」を押すと
  見出しが「ユーザーを追加」のシートが開き、決定は「追加」。
- **jsdom は `<dialog>` の開閉メソッドを実装していない。** `vitest.setup.ts` が
  `open` 属性の付け外しだけを肩代わりする。フォーカスの閉じ込め・Esc・top layer は
  ブラウザの実装であり、テストでは検証しない（検証できるのは `data-open` と
  `aria-expanded` の遷移まで。ADR-0011 と同じ制約）。
- **新しく対応表を置くときは `<table className="matrix">` にし、行の見出しを
  `<th scope="row">`、値そのものの列見出しを `<th className="vertical">` にする。**
  縦組みの見出しの高さは 10.5rem 固定（いちばん長い scope の
  `admin:system-settings` が入る長さ）。長い名前を足すと**黙って末尾が切れる**。
- 画面の左右の余白を `--gutter` にまとめ、`env(safe-area-inset-*)` と併せて使う
  （`index.html` に `viewport-fit=cover` を足した）。切り欠きのある端末を横向きに
  しても文字が隠れない。高さは `100dvh` にして、アドレスバーの伸縮でフッターが
  画面外へ出ないようにした。
- 一覧の中の `<code>`（`requestId`・イベント名）は狭い画面で折り返さない。
  折り返すと 1 行のログが 4 行分の高さになる。**読むには横になぞる**。
