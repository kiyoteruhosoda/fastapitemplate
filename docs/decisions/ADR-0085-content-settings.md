# ADR-0085: コンテンツ設定は、定義をコードに、テナントが変えた値だけを DB に持つ

- 日付: 2026-10-30
- 状態: 承認

## 文脈

ADR-0084 で設定を 2 層に分け、テナントの中の決まり（コンテンツ設定）に権限 `content-settings:view` / `:write` と
ロール `content-admin` を置いた。受け皿（表・API・画面）が無く、権限を持っていても使い道が無かった。
システム設定（ADR-0074 §1）は全体に 1 組の値を持ち、DB > 環境変数 > 既定値で解決する。コンテンツ設定は
テナントごとに値が要り、環境変数で配る理由は無い。

## 決定

1. **項目の定義はコードに置く**（`bounded_contexts/content_settings/domain/definitions.py`）。定義はキー・型
   （選択 / 真偽 / 整数）・既定値・選べる値・範囲を持つ。項目を足すのはここだけ。
2. **DB（`content_settings`）はテナントが変えた値だけを持つ**（`tenant_id` と `key` で一意、値は JSON）。
   行の無い項目は既定値で読む。保存した値が定義に合わなくなった（選べる値を減らした等）ときも既定値で読む。
3. API は `GET|PUT /api/admin/content-settings`。`PUT` は `{"values": {キー: 値}}` で、`null` は既定値へ戻す（行を消す）。
   1 つでも誤りがあれば何も変えずに 422（`unknown_content_setting` / `invalid_content_setting`）。
4. 変えたら監査ログに `content_settings.updated` を残し、`reason` には変えた項目名だけを入れる（値は入れない）。
5. 読む側は、自分のコンテキストの値オブジェクトへ写して使う。見本は `item_list_order`
   （アイテムの一覧の並び順。`bounded_contexts/example` が `ItemListOrder` に写して並べる）。

## 理由

- **定義をコードに**: 型・選べる値・既定値は、それを読むコードと一緒に変わる。DB に定義を持つと、
  コードの知らない項目や型の違う値が入り込み、読む側が毎回確かめることになる。システム設定も定義はコード
  （`system_settings_definitions.py`）にある。
- **変えた値だけを持つ**: 既定値を全テナントへ書き込むと、既定値を変えたときに移行で書き換えが要る。
  行が無ければ新しい既定値がそのまま効く。
- **環境変数を挟まない**: テナントごとの値を環境変数では配れない。
- **値を監査ログに入れない**: 派生アプリの項目に何が入るかは雛形からは分からない（CLAUDE.md「ログ」の方針）。

| 採らなかった案 | 捨てた理由 |
|---|---|
| `system_settings` に `tenant_id` を足して兼ねる | 全体の表（`GLOBAL`）とテナントの表が 1 つになり、絞り忘れが全テナントへ漏れる。解決の順（環境変数）も違う |
| 項目ごとに列を持つ表（1 テナント 1 行） | 項目を足すたびに移行が要る。派生アプリの項目数が読めない |
| 定義も DB に持ち、画面から項目を足す | 読むコードの無い項目は効かない。型の確かめが読む側に散る |

## 影響

- 派生アプリは見本の項目（`item_list_order`）を消し、自分の項目を `definitions.py` に並べる。表示の文言は
  `i18n` の `contentSettings.field.<キー>`（選択肢は `contentSettings.choice.<キー>.<値>`）に足す。訳が無ければキーをそのまま出す。
- 文字列の自由入力の項目はまだ無い。要るときは型を足し、長さの上限を定義に持たせる。
- 値を読むたびにそのテナントの行を引く（項目数ぶんの小さな表で、主キーと索引で引ける）。
