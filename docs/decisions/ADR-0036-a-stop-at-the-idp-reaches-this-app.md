# ADR-0036: IdP で止めた利用者は、このアプリでも止まる（back-channel logout の受け口）

- 日付: 2026-09-14
- 状態: 承認

## 文脈

IdP（assay）は **back-channel logout の送り手**を持っている。ログアウトが起きると
`logout_token`（署名済み JWT）を、`backchannel_logout_uri` を登録した RP へ POST し、
届かなければ再送する（idp の ADR-0024。配信キューつき）。

**受け口を持つ RP が 1 本も無かった。** 9 本を走査して `backchannel` に当たったのは
この雛形の設定コメント 1 行だけだった（idp の ADR-0049 G3）。つまり、

> IdP で利用者を止めても、RP のセッションはそれぞれの寿命が尽きるまで生きている。

しかもこの雛形のセッションは**サーバーに控えの無い JWT** なので、
「届いた通知でセッションを消す」ことが**そもそもできない形**になっている
（`docs/Progress.md` の T5 が指しているのと同じ制約）。

ADR-0033 で決めたのは**こちらから IdP へ**サインアウトを通すかどうか（既定は通さない）
で、**向きが逆**である。混同しないこと。あちらは利用者が押した操作の波及範囲の話、
こちらは**管理者が止めたことが届くか**の話で、後者に「既定で届かない」という選択肢は無い。

## 決定

`POST /api/auth/sso/backchannel-logout` を**設定なしで常に受ける**。効かせ方は、
セッションを消すのではなく**「止まった」を記録して、次にトークンが提示されたときに弾く**。

1. 届いた `logout_token` を JWT として確かめる（署名・発行者・対象者・`exp` / `iat` 必須）。
   そのうえで「ログアウトの通知であること」を確かめる ——`events` にイベントがあり、
   `nonce` が**無く**、`sub` か `sid` があり、`jti` がある。
2. `federated_session_revocations` に 1 行残す（`jti` が主キー ＝ 再送はそのまま重複で弾く）。
   `sid` がある通知はそのセッションだけ、無い通知はその利用者のすべてに効く。
3. このアプリのトークンに `fed_iss` / `fed_sub` / `sid` / `fed_iat`（セッションが
   **始まった**時刻）を刻み、トークンを検証するたびに記録と突き合わせる。
4. ローカルのログインで発行したトークンには何も刻まない ＝ 停止の伝播は届かない。

**新しい設定項目は作らない。** 通知を送るかどうかは IdP 側の登録
（`backchannel_logout_uri`）が決めるので、RP 側に開閉の栓を置くと
**「登録したのに効かない」という 2 か所目の原因**を作るだけになる。

## 理由

**記録で弾く形にしたのは、消せるものが無いため。** トークンはステートレスで、発行済みの
JWT はこちらの手元に無い。「いつ止まったか」を残し、検証のたびに突き合わせるのが、
いまの作りに足せる最小の仕組みになる。記録はリフレッシュトークンの寿命だけ持てばよい
——それを過ぎれば、記録より前に始まったセッションのトークンは自力で期限切れになる。

**比べるのはトークンの `iat` ではなく、セッションが始まった時刻である。** 2 つ理由がある。

- `iat` は**秒までしか持たない**。止めた直後の同じ秒に入り直した利用者を巻き添えにする。
- ⚠ **`iat` はトークンを出し直すたびに新しくなる。** 更新（`POST /api/auth/refresh`）と
  ロールの切り替えで新しいトークンが出るので、`iat` で見ていると
  **更新を 1 回通すだけで停止をすり抜けられる**。始まった時刻なら、何回出し直しても動かない。

**`jti` で再送を弾くのは、止めた範囲が広がらないようにするため。** 送り手は再送でも同じ
`jti` を使う。弾かずに毎回記録すると、**古い通知の再送で「いま生きているセッション」を
落とせる**（`sid` の無い通知ならその利用者ごと落ちる）。

**`nonce` を持つものを断るのは、それが ID トークンだから。** logout token と ID トークンは
署名鍵も発行者も対象者も同じで、**両者を分けるのはこの 1 点だけ**である。見落とすと、
正規に受け取った ID トークンを送り返すだけで他人のセッションを落とせる。

### 検討して捨てた案

- **設定で開閉する（ADR-0033 と同じ形）。** 停止が届かない状態を「既定」にすることになる。
  IdP 側で `backchannel_logout_uri` を登録しなければ 1 通も来ないので、受け口を常に
  開けておく実害が無い。
- **サーバー側にセッション表を持ち、通知が来たら消す。** 筋は良いが、トークンの持ち方
  そのものを変える話（T5）になる。停止の伝播だけを先に塞ぎたいので、そこには手を付けない。
- **`sub` だけで失効させ、`sid` を見ない。** 同じ利用者の別の端末まで落ちる。`sid` は
  ID トークンに載っている（idp の ADR-0024）ので、使わない理由が無い。
- **`Form()` で本文を受ける。** FastAPI の `Form` は `python-multipart` を要求する。
  1 フィールドのために雛形の依存を増やすので、本文を自分で読む。

## 影響

- **`sso_login_tickets` に 4 列増える**（`issuer` / `subject` / `session_id` /
  `session_started_at`）。移行時に既存の券は消える（寿命 60 秒なので実害は無い）。
- **`federated_session_revocations` が増える。** 掃除は通知を受けるたびに行う
  （期限切れの行を消す）ので、定期ジョブは要らない。
- **新しいトークンを出す口は、入り口をそのまま引き継ぐ義務を負う。** 落とすと、その
  トークンだけ停止が効かなくなる。いまの口は更新とロールの切り替えの 2 つ。
- **IdP 側に登録が要る。** `backchannel_logout_uri` を登録しないと 1 通も届かない
  （手順は `docs/OPERATIONS.md`）。
- **これだけでは「止めたら届く」は完成しない。** idp の ADR-0049 I7 は 3 つを挙げている
  ——受け口・**短命のアクセストークン**・**定期照合**。この ADR が入れるのは 1 つ目で、
  残り 2 つは `docs/Progress.md` の T12 に置く。⚠ **いまの assay は「利用者を止めた」
  ときには通知を送らない**（送るのはログアウトのときだけ）ので、受け口だけでは
  管理者による停止は届かない。
