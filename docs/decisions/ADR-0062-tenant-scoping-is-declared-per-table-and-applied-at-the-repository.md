# ADR-0062: テナントの絞りは表ごとに宣言し、リポジトリの入口で掛ける

- 日付: 2026-10-22
- 状態: 承認

## 文脈

ADR-0061 でテナントを入れると決めた。決定 5・6 は「中身の表は `tenant_id` を持ち、絞りは
リポジトリの入口 1 か所で掛け、全表を『テナントの表 / 全体の表』に宣言させて漏れを試験で落とす」
としている。実装するにあたって、ADR-0061 が決めていない細部がいくつかある。

- 二択だと置き場の無い表がある。パスキー・二要素の鍵・端末の購読・ロールの割り当てなどは
  **利用者 1 人に付く**もので、テナントは利用者を通して決まる。`tenant_id` を持たせると
  利用者の所属と二重になり、ずれる余地ができる
- アクセストークンの検証は DB を引かない（ADR-0041）。主体のテナントをどこから知るか
- 監査ログは誰の記録として残すか（テナントの管理者が読む）。システム管理者がテナントの人に
  触れた記録や、未認証のログイン失敗はどこへ置くか
- テナントに属さない主体（システム管理者）が中身の口を叩いたとき、何を返すか

## 決定

1. **表の区分は 3 つ。** テナントの表（`TENANT`。`tenant_id` を持つ）・利用者に付く表
   （`PERSONAL`。`user_id` で利用者に従う。`users` 自身もここ）・全体の表（`GLOBAL`）。
   宣言は `__table_args__` の `info` に置き（`shared/infrastructure/models/tenancy.py`）、
   `tests/integration/test_table_tenancy.py` が「宣言の無い表」「`tenant_id` の無いテナントの表」
   「`user_id` の無い利用者の表」「`tenant_id` を持つのにテナントの表でない表」を落とす。
2. **主体のテナントはトークンに載せる**（クレーム `tenant`。テナントに属さない人は `null`）。
   クレームの無いトークン（テナントより前のもの）は `token_outdated` で 401 にする。
   `null` と読むと、寿命まで「どの中身も見えない」まま過ごすことになるため。更新は DB を
   引いて、いまの所属で出し直す。
3. **リポジトリはテナントをコンストラクタで受け取る**（見本は `SqlItemRepository`）。
   メソッドの引数にはしない。共有の表（利用者・グループ）は `TenantMembers`
   （`shared/infrastructure/tenant_scope.py`）を入口にし、ルーターで `select(User)` を書かない。
   テナントは依存関数（`presentation/fastapi/dependencies/tenant.py`）が主体から取り出す。
4. **テナントに属さない主体が中身の口を叩いたら 403（`tenant_required`）。**
   `None` を「全部のテナント」と読む経路を作らない。
5. **監査ログのテナントは、書くときに決める。** 実行者のテナント。実行者がテナントに
   属さない（システム管理者・未認証）ときは対象の利用者のテナント。どちらも無ければ全体の
   記録（`NULL`）。システム管理者がテナントの人に触れた事実は、そのテナントの管理者に見える。
   読むときは読む人のテナントの記録だけ（テナントに属さない人には全体の記録だけ）。
6. **止めたテナントの人にはトークンを出さない。** 入口は全部 `establish_session` を通るので
   そこで断り（403 `tenant_suspended`）、更新（`verify_refresh_token`）でも断る。
   手元のアクセストークンは寿命（既定 5 分）まで通る（ADR-0041 と同じ割り切り）。
7. グループの名前の一意はテナントの中へ狭める（`(tenant_id, name)`）。

## 理由

- **3 区分**: 利用者に付く表に `tenant_id` を持たせると、利用者の所属と食い違う行が作れて
  しまう。所属の正本を `user_tenants` の 1 か所に置き、ほかは利用者を通して辿る。
- **トークンに載せる**: ADR-0041 で認可の材料は全部クレームに載せると決めている。テナントも
  認可の材料（どの行が見えるか）なので同じ扱いにする。
- **コンストラクタで受け取る**: 引数にすると、呼び側が渡し忘れる余地と「`None` を渡したら
  全件」という抜け道ができる。組み立てた時点で絞りが決まる形なら、ルーターは何も書かない。
- **監査のテナント**: 記録の主体（実行者）が属するテナントの管理者が読むのが素直。ただし
  システム管理者の操作が全体の記録だけに沈むと、テナント管理者から見えない。ADR-0061 は
  「招かれた事実が監査ログに残る」ことを中身を見ない約束の担保にしているので、対象の側にも残す。

## 影響

- 派生アプリが表を足すときは区分の宣言が要る（無いと試験が落ちる）。テナントの表の
  リポジトリはテナントを受け取る形で書く。
- 利用者のメールアドレスは、いまはアプリ全体で一意のまま（`users.email`）。別のテナントに
  同じメールアドレスの人を作ると 409 になる。サインインのテナント選択（ADR-0061 決定 8）と
  合わせて見直す。
- 既存の環境では、配った直後のアクセストークン（クレーム無し）は 1 回だけ 401 になり、画面が
  更新して入り直す。
