# ADR-0021: ログの保持期間を設定キーで持ち、常駐スレッドで掃除する

- 日付: 2026-08-02
- 状態: 承認

## 文脈

`log`（アプリログ）も `audit_log`（監査ログ）も無期限に増える。ADR-0013 は
「保持期間の運用は今後の課題」としたままで、`LOG_DB_MIN_LEVEL` で**これから書く量**を
間引けるようにはなったが、**既に入った行**を減らす手立てが無い。現状の手段は
`docs/OPERATIONS.md` に載せた手動 SQL（`DELETE FROM log WHERE created_at < ...`）だけで、
運用者が思い出したときにしか実行されない。

判断が要ったのは、保持期間が運用・監査の要件で決まるもので、テンプレートが既定値を
勝手に決めてよいものではないためである。とくに監査ログは「誰が何をしたか」の記録で、
アプリログのように「多いから削る」と同じ扱いにはできない。

## 決定

1. **保持期間を設定キーで持つ。** `LOG_RETENTION_DAYS` と
   `AUDIT_LOG_RETENTION_DAYS` を分けて追加し、**どちらも既定は `0`（＝削除しない）**。
2. **掃除は常駐スレッドで定期実行する。** 汎用の `IntervalWorker`
   （`shared/kernel/scheduling`）を 1 つ足し、`web` プロセスの起動時に
   「期限切れログの削除」を 6 時間間隔で回す。起動直後にも 1 回走る。
3. **削除は主キーで小分けにし、1 塊ごとにトランザクションを閉じる。**

## 理由

- **設定キーにする**: 保持期間は環境ごとに違い、運用中に変わる。手順書に留めると
  実行するかどうかが人に依存し、「増えすぎてから気付く」現状が変わらない。既定を `0`
  にしてあるので、テンプレートから作ったプロジェクトが**何も決めないうちに消し始める**
  ことはない。日数を入れた時点で掃除が有効になる。
- **2 つのキーに分ける**: ADR-0013 でテーブルを分けた理由そのもの。アプリログは
  多い・短命、監査ログは少ない・長命で、保持したい期間が違う。1 つのキーで兼ねると
  「アプリログを削る運用」が監査記録を巻き込む。監査ログだけを既定で消さないのではなく
  **どちらも既定で消さない**が、期間を別に決められることに意味がある。
- **`0` と負の日数を同じ「削除しない」にする**: 打ち間違い（`-30`）が未来の境界に
  なって直近の行まで消す事故を防ぐ。境界は `<` で比べ、ちょうど境界の行は残す。
- **常駐スレッドにする**: 起動時 1 回だけでは、長く動き続けるプロセスで掃除されない
  期間が伸びる。逆に外部の cron に任せると、コンテナの外に手順が漏れて
  「デプロイしただけでは効かない設定」が増える。プロセスの中で回せば、
  `docker compose up` した時点で有効になる。
- **スケジューラのライブラリを入れない**: 必要なのは「一定間隔で 1 つの仕事」だけで、
  cron 式・ジョブストア・分散ロックは要らない。`RestartWatcher`（ADR-0004）が既に
  同じ形の常駐スレッドで、依存を増やさずに揃えられる。
- **二重実行の排他を持たない**: Gunicorn は複数ワーカーで動くので、同じ掃除が
  プロセスの数だけ走る。だが「期限より古い行を消す」は冪等で、二重に走っても結果は
  変わらない。排他のために DB のロックや専用テーブルを持ち込む方が、壊れたときの
  影響（掃除が永久に走らない）が大きい。**渡す仕事を冪等なものに限る**という制約に
  置き換えている。
- **設定を実行のたびに読む**: 管理画面で日数を変えたら次の周回から効く。
  設定定義に `restart_scopes` を付けていないのはこのため（ADR-0004 の再起動要求が
  要る設定と区別する）。
- **削除を小分けにする**: 溜まった行を初めて消すときは数十万行が対象になり得る。
  1 文の `DELETE` は MariaDB では長いトランザクションになり、SQLite では DB 全体の
  書き込みロックをその間握り続ける。どちらもリクエストの処理を待たせる。
  `DELETE ... LIMIT` はバックエンド依存（Python 同梱の SQLite では使えない）なので、
  「消す ID を選ぶ → その ID を消す」の 2 段で行う。
- **削除した行数をアプリログへ残す**: 掃除が効いているかを管理画面から確かめられる
  ようにする。何も消さなかった回は書かない（定期実行のたびに同じ行が積み上がらない）。
  数えるのは**実際に消えた行数**（`DELETE` の影響行数）で、選んだ ID の数ではない。
  ワーカーが同時に走ると同じ ID を選び得るが、実際に消せるのは先着の 1 つだけで、
  選んだ数で数えると全ワーカーが同じ行を「消した」と報告して件数が実態より膨らむ。
  一方、**次の塊へ進むかどうかは選んだ件数で判断する**。消せた数で判断すると、
  他のワーカーに先を越された塊で「もう対象が無い」と誤って打ち切ってしまう。

検討して採らなかった案:

- **手順書と削除スクリプトに留める**: 実行するかどうかが人に依存する。手動 SQL は
  引き続き使えるので（`docs/OPERATIONS.md`）、失うものは無い。
- **起動時に 1 回だけ消す**: 再起動しない限り掃除されない。常駐スレッドは起動直後にも
  走るので、この案の利点は取り込んである。
- **監査ログをアプリログと同じ期間で消す**: キーが 1 つで済むが、ADR-0013 でテーブルを
  分けた理由を設定側で台無しにする。
- **監査ログには保持期間を持たせない（自動削除しない）**: 既定の挙動としては正しいが、
  保持期間が法令・社内規程で決まっている環境では結局手動 SQL に戻る。既定 `0` で
  同じ安全性を保ちつつ、必要なら設定できる形にした。
- **外部の cron / systemd timer に任せる**: 掃除の設定がアプリの外に出る。Synology DSM
  上のコンテナ運用（想定環境）ではタスクスケジューラの登録が別作業になり、
  デプロイに追随しない。
- **APScheduler 等を導入する**: この 1 つの仕事のために依存とプロセス構成の知識
  （どのワーカーが実行するか）が増える。

## 影響

- 設定キーが 2 つ増える（`LOG_RETENTION_DAYS` / `AUDIT_LOG_RETENTION_DAYS`、
  どちらも既定 `0`）。既定のままなら**従来と同じ挙動**（何も消えない）。
- `shared/kernel/scheduling` が増える。定期実行を足したくなったら
  `start_interval_worker(name, job, interval_seconds)` を呼ぶ。**渡す仕事は冪等で
  なければならない**（複数ワーカーで同時に走る）。
- 掃除の間隔（6 時間）は定数で、設定にしていない。運用者が決めるのは「何日残すか」
  であって「何秒ごとに見るか」ではないため。
- 監査ログを消す設定を入れると、**消した記録は復元できない**。監査の要件を満たすか
  どうかの判断は運用側に残る。既定で消さないのはこのため。
- `TESTING` のときワーカーは起動しない（テストが知らないうちに DB を触らない）。
  掃除そのものは `purge_expired_logs_once()` を直接呼んで検証する。
- マイグレーションは不要（スキーマを変えない）。
