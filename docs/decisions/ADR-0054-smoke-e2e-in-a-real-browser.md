# ADR-0054: 実ブラウザの E2E は煙試験に絞って雛形に置く

- 日付: 2026-10-17
- 状態: 承認

## 文脈

フロントエンドの試験は Vitest（jsdom）だけだった。jsdom には Service Worker が無く、
実際に起きた壊れ方——SW が認証の内側に入って更新が止まる、API の道の改名で PWA が壊れる、
新しい版の知らせが出ない——は CI で捕まらない。ADR-0035 の通し確認も、開発のときに手で
Playwright を動かしただけで、試験として残っていなかった。

このリポジトリは雛形なので、ここに置いた試験は派生アプリに最初から付いていく。
一方で、e2e は重く揺らぎやすい。本数が増えるほど CI の時間と、赤の原因探しの手間が増える。
派生アプリが画面を作り替えれば、雛形の画面に合わせた試験は合わなくなる。

## 決定

Playwright の E2E を `frontend/e2e/` に置く。中身は、どのアプリにも共通する部分の
**煙試験**だけにする。ログイン・ログアウト、Service Worker の下でも API が SPA に
飲まれないこと、新しい版の知らせ（ADR-0035）。CI では ci.yml とは別の workflow
（`.forgejo/workflows/e2e.yml`）で回す。

## 理由

- **本物のサーバーを立てる。** API を偽物にすると、SW と配り方（`spa.py` の受け皿と
  `Cache-Control`）が試験の外に出てしまう。DB は使い捨ての SQLite、画面はその場でビルドし、
  FastAPI がそのまま配る。本番と同じ道を通る。
- **入り口はローカルのログイン（初期管理者）。** 雛形の既定で開いている口で、idp を
  立てずに済む。パスワードは試験が決めて `ADMIN_INITIAL_PASSWORD` で渡す
  （既定のパスワードには頼らない）。
- **新しい版は、配った `sw.js` を書き換えて起こす。** 版を 2 つビルドするより速く、
  ブラウザから見れば「新しい版が配られた」と同じになる。
- **別の workflow にする。** 画面のビルドとブラウザの分だけ遅いので、Backend / Frontend の
  速い検査の結果を待たせない。
- **Playwright 公式の像で回す**（photonest と同じ版と digest）。ブラウザと OS 側の依存を
  毎回入れずに済む。`@playwright/test` は版をきっちり固定し、像の版とずれたら最初に落とす。
- 採らなかった案:
  - 画面を全部回る網羅試験（photonest の fullstack）。派生アプリの画面に合わなくなり、
    雛形の試験が各アプリで消されるか、赤のまま放置される。
  - Vitest の browser mode。SW のライフサイクル（登録・待機・入れ替え）とページの
    読み込み直しは、1 枚のページの中で部品を描く仕組みでは通せない。
  - API を偽物にした軽い E2E。上のとおり、見たいものが偽物の側に入ってしまう。

## 影響

- PR ごとに E2E のジョブが 1 本増える（画面のビルドとブラウザの起動の分、数分かかる）。
- `@playwright/test` を上げるときは、`e2e.yml` の像（タグと digest）と `PLAYWRIGHT_VERSION` も
  同じ版へ上げる。片方だけだと照合の段で落ちる。
- 派生アプリでログインの入り口を変えたら（パスワードのログインを閉じるなど）、
  `frontend/e2e/sign-in.spec.ts` もその入り口に合わせて直す。
- 試験を足すのは、どのアプリにも共通して壊れうる道に限る。アプリ固有の画面の試験は、
  派生アプリの側で別のファイルとして足す。
