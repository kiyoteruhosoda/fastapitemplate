# ADR-0071: DB とデータの持ち方

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0001（§1）・旧 ADR-0010（§2）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

刷新前のテンプレートは SQLite 単独だった。参照元の photonest は MariaDB 10.11 を本番 DB とし、
SQLite をテストで併用している。テンプレートとしてどちらに揃えるか、また DB へどこから到達できる
ようにするかを決める必要があった。

デプロイ先は k3s で、compose はローカル開発だけのものである（ADR-0073 §1）。

## 決定

### §1 本番は MariaDB、開発・テストは SQLite の二本立てにする

1. 本番（k3s の `db` Deployment。ローカル開発の compose でも同じ）は MariaDB 10.11、
   ローカル開発・テストは SQLite とする。
2. スキーマは Alembic で一元管理し、`sa.BigInteger().with_variant(sa.Integer(), "sqlite")`
   等で両バックエンドの互換を保つ。

### §2 DB のポートを外へ出さず、保守も DB のコンテナの中で行う

compose の `db` は保守用にホストへポートを公開していた（`DB_BIND_ADDR` / `DB_HOST_PORT`）が、
アプリの動作には要らない。`app` は内部の `db:3306` へつなぐ（`DATABASE_URI` の host は `db`）。

1. compose の `db` サービスは `ports` を持たず、`expose: ["3306"]` だけにする。
   k3s では `db` の Service をクラスタ内だけのもの（ClusterIP）にし、NodePort を割り当てない。
2. DB へ到達できるのは同じネットワーク（compose のネットワーク・k3s の namespace）の中だけとする。
3. 保守作業（対話シェル・SQL の流し込み・ダンプ）は DB のコンテナの中から行う。
   ローカルは `docker compose exec db …`、デプロイ先は `kubectl exec deploy/db` で Pod の中へ入ってから
   叩く（手順は `docs/OPERATIONS.md`）。
4. 設定キー `DB_BIND_ADDR` / `DB_HOST_PORT` は廃止する。

## 理由

### §1

- photonest と同一構成にすることで、マイグレーション運用などをそのまま流用でき、
  テンプレートから実プロダクトへの移行コストが最小になる。
- SQLite を開発・テストに残すことで `uv run pytest` が外部依存なしで動き、CI がシンプルに保てる。
- SQLite 単独案は db サービスを消せる簡潔さがあるが、本番想定の RDBMS 運用
  （マイグレーション・バックアップ）をテンプレートで示せなくなるため採らなかった。

### §2

- **外へ出す口は front（nginx）の 1 つだけになる。** 公開面が小さいほど、前段だけを見れば
  到達経路を把握できる。
- **既定の資格情報が開発向けである。** `MARIADB_ROOT_PASSWORD` 等は `.env` 未設定でも DB が初期化
  されるよう既定値を持つ。ポートが開いていると、上書きを忘れた環境で「既定パスワードのまま到達
  可能な DB」が生まれる。ループバック限定でも、ホストに入れる者・ホスト上の他コンテナからは届く。
- **「書き換えると外へ開く」設定キーが存在すること自体が、誤って開ける経路になる。**
- **保守作業に機能低下が無い。** コンテナの中から対話シェル・SQL ファイルの流し込み・
  `mariadb-dump` はすべて実行でき、ホスト側にクライアントを入れる必要も無い。
- 捨てた代替案:
  - **ループバック限定のまま残す** —— 到達経路が残るうえ、既定の資格情報と組み合わさると
    「開けたまま忘れる」事故が起きうる。
  - **compose の `profiles` で保守時だけ公開する** —— `profiles` はサービス単位であり、同じサービスの
    `ports` だけを出し入れできない。`db` を二重定義することになる。

## 影響

### §1

- モデル定義は MariaDB / SQLite 両対応が必須（DB ネイティブ ENUM 禁止、`with_variant` の使用。
  CLAUDE.md「DB モデリング」参照）。バックエンドで挙動が変わる設計は採らない。
- `db` には healthcheck（k3s では `--protocol=tcp` 付きの readinessProbe）を持たせ、
  起動時にマイグレーションを流す。

### §2

- **ホストから直接 DB へつなぐ運用は使えない。** GUI クライアントを一時的につなぎたい場合は、
  その場限りのポートフォワード用コンテナを立てる（手順は `docs/OPERATIONS.md`
  「DB へホストのツールから一時的につなぎたいとき」）。`docker-compose.yml` は変えない。
  作業が終わったらコンテナを消せば公開ポートも消える。
- ⚠ 資格情報は必ずコンテナの中で展開させる（`sh -c '…'` のシングルクォート、または Pod に入ってから
  叩く）。ホストのシェルで展開すると空文字になり、パスワードなしで接続を試みて失敗する。
- DB への到達権限が、ホスト（デプロイ先では nolumialab と k3s）へ入れる権限と一致する。
