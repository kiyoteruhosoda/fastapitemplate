# ADR-0015: デプロイの名前は配置場所から決め、テンプレート名のままでは動かさない

- 日付: 2026-07-31
- 状態: 廃止（ADR-0023 で置き換え）

## 文脈

このリポジトリはテンプレートである。ところが `deploy.sh` はアプリ名を
`APP_NAME="fastapitemplate"` と直書きしていたため、**テンプレートから作った
プロジェクトが元テンプレートと同じ名前を名乗り続ける**状態になっていた。

この名前からは次のすべてが導かれる。

| 導かれるもの | 例（旧） |
|---|---|
| イメージタグ | `fastapitemplate:prod` / `fastapitemplate-db:prod` |
| compose プロジェクト名 | `fastapitemplate`（stg は `fastapitemplate-stg`） |
| DB コンテナ名（`container_name`） | `fastapitemplate-mariadb` |
| ネットワーク名 | `fastapitemplate-prod` |

つまりテンプレート由来の別プロジェクトを同じホストで動かすと、`container_name` と
ホストポートを丸ごと取り合う。ADR-0014 で扱った 2 回のデプロイ失敗
（ネットワークの重複 / 他プロジェクトのコンテナの切り離し）は、いずれもこの衝突の
症状だった。

名前を 1 か所書き換えるだけでは「衝突しうる構造」が残る。次に名前が当たれば同じことが
起きるし、テンプレートから作る限り**書き換え忘れが常に起こりうる**。

## 決定

1. デプロイの名前（アプリ名）を `deploy.sh` の**配置場所**から決める。
   優先順位は `.env` の `APP_NAME` ＞ 親ディレクトリ名 ＞ `BUILD_APP_NAME`。

   ```
   /volume1/docker/rewardpointsweb/prod/deploy.sh   → アプリ名 rewardpointsweb・環境 prod
   /volume1/docker/kaimono/stg/deploy.sh            → アプリ名 kaimono・環境 stg
   ```

2. 解決した名前が**テンプレートの名前（`fastapitemplate`）ならデプロイを中断する**。
   テンプレートから作ったプロジェクトは名前を変えなければ動かせない。

3. 旧名から移行するため、旧アプリ名の compose プロジェクトを一度だけ畳み、
   自動生成した `.env` の旧既定名を書き換える。

## 理由

- **配置場所は構造的に衝突しない。** 別のアプリは別のディレクトリに置かれる。環境名を
  ディレクトリ名（`basename`）で決めていたのと同じ考え方をアプリ名（`dirname` の
  `basename`）へ広げただけで、運用側に新しい約束事は増えない。
- **名前を変えるのを人の注意力に任せない。** テンプレートから作った直後は必ず旧名を
  名乗っている。警告では見落とされるため、テンプレート名を検出したら中断する
  （直し方は 2 通りとも同じエラーに出す）。
- **ディレクトリ名は正規化する。** docker の識別子として使うため、小文字英数と `-` `_`
  へ変換する（`RewardPoints Web` → `rewardpoints-web`）。運用者に命名規則を課さずに
  済ませるための変換であり、値そのものを拒否はしない。ただしこの変換は**多対一**
  （`foo.bar` も `foo--bar` も `foo-bar` になる）で、正規化後が同じなら結局同じ名前を
  共有してしまう。名前を変換したときは変換前後を必ず出力し、運用者が気付けるようにする
  （非正規な名前を拒否する案は採らない。`RewardPoints Web` のようなディレクトリ名を
  そのまま置けることのほうが、まれな衝突より日常的に効く）。
- **出所を必ず出す。** 「なぜこの名前になったか」が分からないと、ディレクトリを移した
  ときに追えない。実際に使われた名前と出所を起動時に 1 行で出力する。
- **`BUILD_APP_NAME` は別物として残す。** これは「デプロイの名前」ではなく
  「`image.tar` の中身がどう tag されているか」（`scripts/build.sh` の `app_name`）で、
  `manifest.env` が無いときの `docker load` 後の参照先にだけ使う。役割が違うので
  同じ値でも別の定数にしてある。
- **旧プロジェクトを畳む条件を厳しくする。** 畳むのは、対象プロジェクトのコンテナが
  `com.docker.compose.project.working_dir` ラベルでこの環境ディレクトリと一致するもの
  だけで構成されているときに限る。プロジェクト名ラベルでの絞り込みは docker デーモン
  全体を見るため、それだけを根拠にすると**同じ旧名を使う別のアプリを停止・削除して
  しまう**（ADR-0014 で「別プロジェクトは消さない」と決めたのと同じ理由）。
- **`.env` の書き換えは旧既定値と完全一致する行だけ。** 運用者が選んだ値には触れない。
  永続データはホスト側の `HOST_DATA_ROOT` にあるため、名前が変わっても消えない。
- **移動前のパスも見分ける。** 推奨の移行手順はディレクトリごとの改名だが、そうすると
  旧コンテナの `working_dir` ラベルと自動生成された `.env` の `HOST_DATA_ROOT`
  （絶対パス）は**移動前のパスを指したまま**残る。前者を見落とすと旧デプロイを畳めず
  ホストポートを握られたままになり、後者を見落とすと消えたパスを `mkdir -p` が作り直して
  **空の DB で MariaDB が初期化される**。どちらも移動前のパス
  （`<親の親>/fastapitemplate/<env>`）ちょうどと一致し、**そこが実在しない**ときだけ
  自分のものとして扱う。まだディレクトリがあるなら別のデプロイが現役でいるということ
  なので触れない。`HOST_DATA_ROOT` が別ディスク・共有フォルダを指している場合にも触れない
  （一時的にマウントが外れているだけの可能性があり、付け替えると空の DB で起動してしまう）。
- **採らなかった案:**
  - *`deploy.sh` の `APP_NAME` を書き換えてもらう* — テンプレートから作るたびに
    書き換えが要り、忘れれば衝突する。`deploy.sh` は `dist/` 経由で毎回上書きされる
    ため、書き換えても次のビルドで元に戻る。
  - *`.env` の `APP_NAME` を必須にする* — 初回デプロイで `.env` を自動生成する
    ゼロコンフィグの利点（ADR-0008）を失う。
  - *コンテナ名にランダムな接尾辞を付ける* — 衝突は避けられるが、
    `docker compose exec db …`（ADR-0010）のような名前を前提にした運用手順が壊れる。

## 影響

- 配置は `<app>/<stg|prod>/` の 2 階層が前提になる（`build-remote-container.sh` が
  既に同じ前提でプロジェクト名を解決しており、そちらと解決結果が揃う）。
- テンプレートそのもの（`fastapitemplate/prod/` 等）はデプロイできない。テンプレートを
  そのまま動かして試したい場合も、ディレクトリ名を変えるか `.env` に `APP_NAME` を書く。
- 旧名で動いていた環境は、次のデプロイで旧プロジェクトが 1 度だけ畳まれ、コンテナ名・
  ネットワーク名が新しい名前へ移る。DB のデータ（`mnt/db_data`）はホスト側に残るため
  引き継がれる。
- 別のアプリが旧名のまま動いている場合は畳まず、警告（各コンテナの `working_dir` と
  手で畳むコマンド）を出して進む。名前が実際に衝突すれば ADR-0014 の判定に従って
  デプロイが中断する。移動先が元と別の親ディレクトリになる移行（`/volume1/…` →
  `/volume2/…`）も同じ扱いになるため、その場合は手で畳む（手順は `docs/OPERATIONS.md`）。
- 正規化後の名前が同じになるディレクトリ名（`foo.bar` と `foo-bar` 等）を同一ホストで
  併用すると、名前を分けたつもりでも共有してしまう。防げないので、変換した事実を
  出力して運用者に判断させる。
- `docker-compose.yml` の `${DB_CONTAINER_NAME:-…}` 等の既定値はテンプレート名のままで、
  ローカル開発（リポジトリ直下の `docker compose up`）でしか効かない。デプロイでは
  `deploy.sh` が解決した値を `export` して必ず上書きする。
