# ADR-0102: IdP で止めた記録は、今あるログインより先に消さない

- 日付: 2026-11-02
- 状態: 承認
- 関係: ADR-0077 §3 の「記録はリフレッシュトークンの寿命だけ持てばよい」と、ADR-0101 影響の「IdP からの停止を覚えておく長さは今の期間に従う」を置き換える

## 文脈

停止の記録（`federated_session_revocations`）は「今の期間」だけ残し、期限を過ぎた行は次の停止が届いたときに消していた。期間を短くしても発行済みのログインの期限は縮まない（ADR-0101 決定 4）ので、記録のほうが先に消えると、止めたはずのログインが更新できるようになる。stg の MariaDB で、延長あり・なしの両方で再現した（task #829）。

## 決定

1. **記録の `expires_at` は、今の期間と `refresh_sessions` の最も遅い `expires_at` の遅いほうにする。** 受け口の通知と定期照合（ADR-0077 §7）の両方に効くよう、保存（`SqlSessionRevocationRepository.record`）の 1 か所で決める。
2. **最も遅い値は全ログインから取る。** 止めた人のログインに絞らない。
3. **今の期間は最低限として残す。** 停止と同時に進んでいる更新が、ログインの期限をそのぶん延ばすことがあるため。
4. **既に書かれた行の期限は延ばさない。** 移行も足さない。

## 理由

- **全ログインから取る**: `refresh_sessions` は IdP 側の宛名を持たない。結び付きから利用者を引く形では、連携を外した後に残るログインを取りこぼす。止める側を広げる誤りは行が長く残るだけで、狭める誤りは止めたログインが生き返る。
- **`record` で決める**: 署名を確かめた通知にしか走らない。組み立ての段で読むと、未認証で叩ける口で毎回読むことになる。
- **決定 4**: 本番では期間を短くしていないので、延ばす相手が無い。

| 採らなかった案 | 捨てた理由 |
|---|---|
| 記録を消さない | 期間を短くしない環境でも行が増え続ける（ADR-0077 §7 が避けた形） |
| 掃除の時に「まだ生きているログインがあれば残す」と判断する | 延長ありで使い続ける人が 1 人でも居ると、どの行も消えなくなる |
| 過去で最長の期間を覚えておく | 設定の履歴という新しい状態が要る。控えの行を読めば足りる |
| 期間を短くしたときに今のログインの期限も縮める | 設定を変えただけで今のログインが切れる（ADR-0101 で捨てた案） |
| `refresh_sessions` に IdP 側の宛名を足し、止めるときに行を消す | 表の形とトークンの持ち方を変える話になり、この不具合の幅に対して大きい |

## 影響

- 期間を短くした後は、古いログインが終わるまで記録が残る。長さの上限は期間の上限（10 年）で、行が増えるのは停止が届いたときだけ。
- 期間を短くしていなければ、最も遅い値は「今から期間ぶん」を超えないので、動きは変わらない。
- 停止を記録するたびに `refresh_sessions` の `expires_at` の索引を 1 回読む。
- `rotate` と `SET` の順番には触らない（ADR-0091 決定 4）。
- ⚠ 派生アプリには取り込んでいない。
