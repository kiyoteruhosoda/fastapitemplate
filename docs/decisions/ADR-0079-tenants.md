# ADR-0079: テナント

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0061（§1）・旧 ADR-0062（§2）・旧 ADR-0063（§3）・旧 ADR-0064（§4）・旧 ADR-0065（§5）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

IdP（assay）はテナントで人を分けている（発行者 `issuer` が `https://identity…/<tenant>`）。アプリに
テナントの区切りが無いと、複数の家族・組織に使わせるにはテナントごとに環境を立てるしかなく、1 つの環境で
分けようとすると、`owner` がほかの家族・組織の利用者も中身も動かせ、共有相手やお知らせの宛先にほかの
テナントの人が並び、グループやロールの管理がテナントをまたいで効く。

持ち主の決定（2026-10-22）: 雛形にテナントを入れる（photonest には入れない）。立場は **システム管理者 /
テナント管理者 / テナントメンバー** の 3 段で、システム管理者とテナント管理者は兼ねない。**システム管理者は
テナントの中身を見られない。** **テナント管理者はアプリの中で指名する**（assay の管理者をトークンで受け
取らない）。**テナントの内側は今の作りそのもの**で、足すのはテナント管理者という位置づけと外側の管理。

## 決定

### §1 テナントで人とデータを分け、システム管理者は中身を見ない

**今の作りをそのまま「テナントの内側」にし、その外側に「テナントの管理」を足す。** テナント管理者は
`owner` で、内側のロール・権限・画面・関門（ADR-0078 §4）は変えない。

| | システム管理者（外側） | テナント管理者（内側） | テナントメンバー |
|---|---|---|---|
| テナント | 登録・停止・削除、最初のテナント管理者の指名、テナントごとの人数（中身ではなく数） | 自分のテナントの名前を見る | — |
| 人 | システム管理者どうしの付け外し | 自分のテナントの利用者・グループ・ロール（ADR-0078 §4 の関門をテナントの中で） | 自分のプロフィール |
| 中身 | **見られない** | 自分のテナントの中身の管理 | ロールの範囲で使う |
| 設定 | 全体の設定（メール・署名鍵・通知の鍵・ログの水準など） | — | — |
| 記録 | アプリログ（`log`）、全体の操作の監査 | 自分のテナントの監査ログ | — |
| 運用 | 再起動・版の知らせ | 自分のテナントへのお知らせ | — |

1. **テナントを表 `tenants` で持つ。** 1 行が assay のテナント 1 つに当たり、発行者（`issuer`）・
   クライアント ID・表示名・URL に使う短い名前（`slug`）・状態（有効 / 停止）を持つ。assay のクライアントは
   テナントごとに登録するもので（`(tenant_id, client_id)` が一意）、クライアント ID はテナントごとに違う。
   署名鍵（`private_key_jwt`）はアプリで 1 つにし、同じ公開鍵を各テナントのクライアントに登録する。
2. **テナントを登録するのはシステム管理者。** 登録の無い発行者のトークンは受け付けない。
3. **利用者はちょうど 1 つのテナントに属する。** システム管理者だけは属さない（`NULL`）。同じ人が中身も
   使うなら、そのテナントに別の利用者を持つ。`(issuer, subject)` の結び付き（`federated_identities`）は
   そのまま使う。ローカル口座（ADR-0076 §7）もどれか 1 つのテナントに属する。所属は 1 対 1 の別表
   `user_tenants` で持つ（⚠ `users` に列を足すと据え付けの移行 `0002` が落ちる）。
4. **システム管理者（`system-admin`）とテナント管理者（`owner`）は別のロールで、兼ねない。**
   `system-admin` は全体の権限（§3 決定 2）を持ち、持てるのはテナントに属さない利用者だけ。`owner` は
   全体の権限を持たない。内側のほかのロール（`user-admin`・`auditor`・`manager`・`member`・`guest`）は
   自分のテナントの中でだけ効く。守り方は §3 決定 3。
5. **中身の表は全部 `tenant_id` を持ち、読み書きは必ず主体のテナントで絞る。** 絞りはリポジトリの入口
   1 か所で掛け、ルーター本文で書かない（§2 決定 3）。別のテナントの行は 404（在ることも見せない）。
6. **絞り忘れを機械で落とす。** 全表に区分を宣言させ、宣言の無い表と区分に合わない表を試験で落とす
   （§2 決定 1。`test_authorization_matrix` が scope の付け忘れを落とすのと同じ形）。加えて、2 つの
   テナントを作って互いの行が見えないことを、各コンテキストの API で確かめる試験を置く。
7. **テナント管理者はアプリの中で指名する。** 最初のテナント管理者はシステム管理者が招待で決め（§5）、
   以後はテナント管理者が自分のテナントの中で付け外しする（ADR-0078 §4 の関門をテナントの中で通す。
   「管理の要」はテナントごとに数える）。
8. **サインインはテナントを選んでから。** 入口の URL に `slug` を持たせ（`/t/<slug>/login`）、その
   テナントの発行者とクライアントで assay へ送る。テナントが 1 つだけの環境では、名前の無い入口が
   そのまま使える。細部は §4。
9. **既存の環境は「既定のテナント」1 つに全員を入れて移る。** 移行 0015 が `OIDC_ISSUER` /
   `OIDC_CLIENT_ID` から既定のテナントを作り、全利用者・全行をそこへ入れる。`owner` を持つ人は既定の
   テナントの `owner` になる。ロールの移り方は §3 決定 4。

### §2 テナントの絞りは表ごとに宣言し、リポジトリの入口で掛ける

1. **表の区分は 3 つ。** テナントの表（`TENANT`。`tenant_id` を持つ）・利用者に付く表（`PERSONAL`。
   `user_id` で利用者に従う。パスキー・二要素の鍵・端末の購読・ロールの割り当てなど。`users` 自身もここ）・
   全体の表（`GLOBAL`）。宣言は `__table_args__` の `info` に置き（`shared/infrastructure/models/tenancy.py`）、
   `tests/integration/test_table_tenancy.py` が「宣言の無い表」「`tenant_id` の無いテナントの表」
   「`user_id` の無い利用者の表」「`tenant_id` を持つのにテナントの表でない表」を落とす。
2. **主体のテナントはトークンに載せる**（クレーム `tenant`。テナントに属さない人は `null`）。クレームの
   無いトークン（テナントより前のもの）は `token_outdated` で 401 にする。更新は DB を引いて、いまの
   所属で出し直す。
3. **リポジトリはテナントをコンストラクタで受け取る**（見本は `SqlItemRepository`）。メソッドの引数に
   しない。共有の表（利用者・グループ）は `TenantMembers`（`shared/infrastructure/tenant_scope.py`）を
   入口にし、ルーターで `select(User)` を書かない。テナントは依存関数
   （`presentation/fastapi/dependencies/tenant.py`）が主体から取り出す。
4. **テナントに属さない主体が中身の口を叩いたら 403（`tenant_required`）。** `None` を「全部のテナント」と
   読む経路を作らない。
5. **監査ログのテナントは、書くときに決める。** 実行者のテナント。実行者がテナントに属さない（システム
   管理者・未認証）ときは対象の利用者のテナント。どちらも無ければ全体の記録（`NULL`）。読むときは読む人の
   テナントの記録だけ（テナントに属さない人には全体の記録だけ）。
6. **止めたテナントの人にはトークンを出さない。** 入口は全部 `establish_session` を通るのでそこで断り
   （403 `tenant_suspended`）、更新（`verify_refresh_token`）でも断る。手元のアクセストークンは寿命
   （既定 5 分）まで通る（ADR-0076 §5 と同じ割り切り）。
7. グループの名前の一意はテナントの中へ狭める（`(tenant_id, name)`）。

### §3 ロールはテナントの中に閉じ、システム管理者の席は別にする

ロールの表（`roles`）はアプリ全体で 1 つで、付け外しの口は管理画面のほかに SSO の既定ロール・ロールの
同期（ADR-0077 §1）もある。

1. **雛形のロール（`master_data.ROLES`）は全テナントが共有し、テナントの管理者からは中身を変えられない**
   （変更・削除は 403 `shared_role`）。中身を変えたいテナントは自分のロールを作る。作ったロールは
   `role_tenants` で作ったテナントに結び、ほかのテナントからは見えない（404）。
2. **全体の権限は 4 つ**（`SYSTEM_PERMISSIONS` = `admin:system-settings`・`system:manage`・`log:view`・
   `tenant:manage`）。`system-admin` 以外のどのロールにも持たせない（`owner`・`manager`・`auditor`・自作の
   ロールにも）。`system-admin` は加えて `audit:view` を持ち、全体の操作の記録（§2 決定 5）を読む。
3. **「兼ねない」は 2 か所で守る。**
   - 付ける口: テナントの中で選べるロールは、雛形のうちシステムのロール（`SYSTEM_ROLES`）でないものと
     自分のロールだけ（`TenantMembers.roles`）。管理画面・SSO の既定ロール・同期のどれもここを通る。
   - 効く口: トークンに載せる権限を座る場所で絞る（`within_the_seat`）。テナントの人には全体の権限が、
     テナントに属さない人にはシステムのロールの権限しか効かない。付け方を誤っても効かない。
4. **既存の環境の移り方**（移行 0016）: 自作のロールは既定のテナントのものにし、全体の権限を外す。
   テナントに居る `system-admin` の持ち主は、ほかのロールも持っていれば `system-admin` を外し、
   `system-admin` だけなら既定のテナントから出してシステム管理者にする。

### §4 サインインはテナントの入口から始め、連携先はテナントの行が持つ

1. **連携先の発行者とクライアント ID はテナントの行が正本**（`tenants.issuer` / `client_id`）。全体の
   設定に残すのはテナントをまたいで同じもの（クライアントの鍵・戻り先・要求する強度・名乗り方）だけ。
   `OIDC_ISSUER` / `OIDC_CLIENT_ID` は既定のテナントを作るときの初期値（移行 0015）。
2. **どのテナントの連携先を使うかは、経路ごとに 1 通りに決める。**
   - 入口（`/login`・`/provider`・`/logout`）: `?tenant=<slug>`。無ければ、テナントが 1 つだけの環境では
     それ、2 つ以上なら無し（SSO のボタンを出さない）
   - 戻り（`/callback`）: 送り出したときに往復状態（署名付き Cookie）へ書いた発行者。⚠ URL から決め直さない。
     往復状態の発行者と受ける連携先が違えば断る
   - 連携（ADR-0077 §5）: 入っている利用者のテナント
   - 停止の通知・アプリのトークン: トークンの `iss`。署名を確かめる前に読むが、使うのは鍵を選ぶことだけで、
     登録の無い発行者なら連携先が無く断る
3. **メールアドレスの一意は同じ席の中だけ**（同じテナントの中、テナントに属さない人の中）。DB の一意制約は
   外し（移行 0017）、作る・変える口でアプリが確かめる（`shared/infrastructure/sign_in_directory.py`）。
4. **パスワードの入口の決め方**: `/t/<slug>/login` はそのテナントの中で探す。名前の無い `/login` は、まず
   テナントに属さない人、居なければテナントが 1 つだけのときのそのテナント。パスワードの再設定の申し込みも
   同じ決め方をする。
5. 画面は入った入口を覚えておき（端末の `localStorage`）、サインアウトや期限切れのあとはそこへ戻す。
   権限には関わらない。

### §5 テナント管理者は招待で指名し、システム管理者はパスワードを知らない

1. **指名は「席を作って招待する」。** システム管理者はメールアドレスと表示名だけを決める。席はその
   テナントの `owner` で、パスワードを持たない（ADR-0076 §6）。本人に招待のメールが届き、リンクから自分で
   パスワードを決める（`password_reset_tokens.purpose = invitation`、有効 7 日）。⚠ リンクは応答にも画面にも
   出さない。
2. **SSO のテナントでは、席はその IdP で初めて入ったときにも受け取れる。** 入り口を 1 つも持たない利用者
   （パスワードも IdP との結び付きもパスキーも無い）は「指名された席」で、検証済みのメールアドレスが一致
   すれば、寄せる設定（`OIDC_LINK_BY_EMAIL`。既定で閉じている、ADR-0077 §4）とは別に結び付ける。入り口を
   持っている利用者は席ではないので、寄せる設定に従う。
3. **テナントの削除は、止めてからでないとできない**（409 `tenant_not_suspended`）。画面では短い名前を
   打たせてから消す。消すのは人・中身・自作のロールで、監査ログは残す。消す表は表の宣言（§2 決定 1）から
   機械的に決める。
4. **テナントの外側の API は `/api/system/*`。** テナントの台帳は `tenant:manage`、システム管理者どうしの
   付け外しは `system:manage`。足すときは招待（決定 1 と同じ）、自分は外せず、有効なシステム管理者を
   0 人にはできない。
5. システム管理者が指名した事実は、対象の利用者のテナントの監査ログにも残る（§2 決定 5）。

## 理由

### §1

- **テナント = assay のテナント**: ずらすと「assay では別の組織なのにアプリでは同じ」が起きる。発行者で
  見分ければトークンからテナントが一意に決まり、`(issuer, subject)` の鍵もそのまま使える。
- **システム管理者が中身を見ない**: 他人のデータを運営者が読めないことを、運用の約束ではなく権限の形で
  保証する。障害対応で中身が要るときは、そのテナントの管理者に招いてもらう（招かれた事実が監査ログに残る）。
- **テナント管理者をアプリで指名**: assay の管理者は IdP を管理する人で、アプリの管理者と同じとは限らない。
  トークンに載せるには assay の改修が要り、載せても「管理の要」の数え方と二重になる。
- **利用者は 1 テナント**: 複数のテナントを行き来できる形（Slack のワークスペース）は、どのテナントとして
  動いているかをトークンと全リポジトリが持つことになり、絞りの誤りが起きる箇所が増える。

| 捨てた案 | 理由 |
|---|---|
| テナントごとに環境を立てる | テナントを足すたびに namespace・DB・宣言が増える |
| DB をテナントごとに分ける | マイグレーションと退避がテナントの数だけ要り、k3s の 1 スタックの運用に合わない |
| システム管理者が全テナントを見られる／assay のテナント管理者を写す | 持ち主の決定と上の理由で取らない |

### §2

- **3 区分**: 利用者に付く表に `tenant_id` を持たせると、所属と食い違う行が作れる。所属の正本は
  `user_tenants` の 1 か所に置き、ほかは利用者を通して辿る。
- **トークンに載せる**: 認可の材料は全部クレームに載せる（ADR-0076 §5）。クレームの無いトークンを `null` と
  読むと、寿命まで「どの中身も見えない」まま過ごすので 401 にする。
- **コンストラクタで受け取る／入口で絞る**: ルーターや引数で渡すと、書き忘れても動き、気付くのは漏れた後に
  なる。「`None` を渡したら全件」という抜け道もできる。
- **監査のテナント**: システム管理者の操作が全体の記録だけに沈むとテナント管理者から見えない。中身を見ない
  約束（§1）の担保として、対象の側にも残す。

### §3

- **雛形を共有にする**: テナントごとに複製すると、移行が権限を足すたびに全テナントの複製へ配る仕組みが要る。
  共有のまま変えさせなければ正本は `master_data` の 1 つで済み、差は自分のロールで表せる。
- **`log:view` を内側から外す**: アプリログにはほかのテナントの利用者の動き（パス・時刻・利用者のハッシュ）も
  入る。
- **2 か所で守る**: 付ける口だけだと DB を直に触った・移行を誤ったときに兼ねてしまい、効く口だけだと
  「付いているのに効かないロール」が画面に出る。

### §4

- **テナントの行を正本にする**: クライアント ID はテナントの数だけある。全体の設定に 1 組持つと正が 2 か所に分かれる。
- **戻りで URL から決め直さない**: 決め直せると、あるテナントで始めた往復を別のテナントのクライアントで
  完了させられる。往復状態は署名付きで書き換えられない。
- **一意を席の中に狭める**: 全体で一意だと、2 つ目のテナントで初めて入った人を作れない（SSO の自動作成が
  一意制約に当たる）。テナント管理者が「その人は別のテナントに居る」ことを 409 で知れてしまうのも避ける。
- **名前の無い入口はテナントに属さない人を先に探す**: システム管理者は `/t/<slug>/login` から入れない。
  テナントが 1 つだけの環境で今の入口を変えないことと両立する。

### §5

- **招待にする**: 初期パスワードを決めて渡すと、システム管理者がそれでテナント管理者として入れてしまい、
  中身を見ない約束が権限の形にならない。リンクを応答に載せないのも同じ理由。
- **SSO の席の受け取り**: 席には誰の入り口も無いので、結び付けても誰かの口座を奪わない。メールを止めてある
  環境でも指名が届く。⚠ assay の `email_verified` は「テナント管理者がそう主張している」の意味
  （ADR-0077 §4）なので、受け取れるのは、そのテナントの IdP がそのメールアドレスを名乗らせた人である。
- **止めてから消す**: 止めるのは戻せるが、消すのは戻せない。2 段なら押し間違いでは消えない。
- 既存の利用者をテナント管理者に上げる口はシステム管理者に持たせない（テナントの中の人事に外から手を
  入れることになる）。管理者が居なくなったときは新しい席の指名で立て直す。

## 影響

### §1

- 中身を持つコンテキスト（`example` の `items`・`notification`・`audit`）の表とリポジトリに `tenant_id` が入る。
- 設定（`system_settings`）とアプリログ（`log`）は全体のもので、システム管理者だけが扱う。テナントごとの
  設定は要る派生アプリで足す。監査ログはテナントごとで、テナント管理者が自分の分を読む。
- 管理画面が 2 つに分かれる: 全体（テナント一覧・設定・ログ）と、テナントの中（利用者・グループ・ロール）。
- ⚠ 雛形を取り込んだ既存の派生アプリは「既定のテナント」1 つの環境になる。動きは変わらないが、`owner` が
  設定・再起動・アプリログの画面に入れなくなり、システム管理者を作るまで入れる人はいない（手順は
  `docs/OPERATIONS.md`）。
- photonest はテナントを入れない（家族の道具。photonest の ADR-0028）。

### §2

- 派生アプリが表を足すときは区分の宣言が要る（無いと試験が落ちる）。テナントの表のリポジトリはテナントを
  受け取る形で書く。
- 既存の環境では、配った直後のアクセストークン（クレーム無し）は 1 回だけ 401 になり、画面が更新して入り直す。

### §3

- 雛形のロールを変える手段は `master_data` と移行だけ（画面からは変えられない）。
- ロール名はアプリ全体で一意（`roles.name`）。別のテナントが使っている名前のロールは作れない（409）。
- 派生アプリで全体に効く権限を足すときは `SYSTEM_PERMISSIONS` に入れる（入れないと、テナント管理者が配れてしまう）。

### §4

- テナントが 2 つ以上になったら、テナントの利用者に入口の URL（`/t/<slug>/login`）を知らせる。
- 定期照合（ADR-0077 §7）は `OIDC_ISSUER` のテナントだけを照合する。照合のサービスアカウント
  （`MACHINE_CLIENT_ID`）は assay のテナントごとに要るので、1 つの設定では 1 テナントしか聞けない。ほかの
  テナントの停止は停止の通知（ADR-0077 §3）で届く。
- アプリのトークン（ADR-0081 §1）で受けるクライアントは `APP_CLIENT_IDS` の一覧（テナントをまたいで 1 つ）。
- ログイン試行の回数制限（ADR-0076 §9）の宛名はメールアドレスのままなので、同じメールアドレスの人は
  テナントが違っても数えられ方を共有する。

### §5

- メールを止めてある環境で SSO を使わないテナントを作ると、指名した人に入り口が届かない（画面に「送れな
  かった」と出る）。メールの設定を済ませてから指名し直す。
- 招待のリンクは本人のメールにだけ届く。届かなかったときの再送は、指名し直し（新しい席）になる。
