# ADR-0082: 機械の口

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0029（§1）・旧 ADR-0069（§2）（2026-10-30 に統合。元の文面は git の履歴にある）
- 関連: Assay（idp）側のトークンの宛名（`resources`）の決定・task #715（機械のトークンを最小権限に）・
  #717（§2 の判断）・#718（宛名の必須化）・#721（雛形への実装）・#722（各アプリの許可簿）

## 文脈

「機械の口」は、`client_credentials` で得たトークンでこのアプリの API を叩く**受け口**である。
⚠ こちらから Assay を呼ぶときの名乗り（`MACHINE_CLIENT_ID`。ADR-0077 §7）とは別の話で、
このテンプレートは今、機械として呼ばれる口をまだ持っていない。

Assay の `client_credentials` トークンについて、次のことが前提になる。

- **宛名（`aud`）は使える。** Assay がクライアントの `resources` を宛名に刻むので、受け側は「自分宛か」を
  判定できる。それ以前は `aud` が全員 `{issuer}/userinfo` 固定で、blobshare は `aud` の検証を諦めて
  `client_id` の照合だけで認可している。
- **`scope` は載らない（いつも空）。** `sub` は利用者ではなくクライアント自身である。
  「どのクライアントが何をしてよいか」は受け側で決めるしかない。

AI のエージェント（Claude）が機械のトークンで各アプリを呼ぶようになった。エージェントはプロンプト
インジェクションで騙され得るので、**騙されたときに届く範囲＝そのトークンでできること全部**になる
（OWASP API Top 10 の API5、LLM Top 10 の Excessive Agency）。

## 決定

### §1 機械の口をテンプレートに入れる基準と、外せない検証

1. **テンプレートへ入れるのは、同じものが 2 つ以上の派生で書かれたとき。** 機械の口はこの条件を満たした
   （nolumiatask・nolumiawiki・toeic など）ので、許可簿（§2）つきで取り込む（#721）。
2. **取り込むときは `acts_as`（機械を利用者として振る舞わせる）を採る。** 機械のために人間用と同じ形の
   ロール・権限表を別に作らない。操作を絞るのは §2 の許可簿で行う。
3. **外せない検証は 4 つ。** ドメイン層に 1 か所で持ち、実装ごとに覚えさせない。
   - `sub_type == "client"`
   - `sub == client_id`
   - `aud` が、このアプリが `resources` に登録した名前と一致すること（§2 決定 4）
   - 署名・発行者・期限（通常の ID トークン検証と同じ）
4. **監査には「機械 X が利用者 Y として」を残す。** 実行者を Y にするだけでは嘘になる。

### §2 機械に何をしてよいかは、idp ではなくアプリの許可簿で決める

受け側の作りは 3 つ混ざっている。acts_as 型（nolumiatask・nolumiawiki・toeic など。`MACHINE_CLIENTS` に
「誰として振る舞うか」を書き、できることはその利用者のロールと同じで操作単位では絞れない）、
貸し出し型（blobshare。`client_id` ごとに使えるバケットを決める）、許可簿型（nolumiadeck。機械ごとの許可を
DB に持つ）。絞る仕組みを idp とアプリのどちらに置くかを決めた。

1. 機械に何をしてよいかは、**呼ばれる側のアプリが `client_id` ごとの許可簿で決める**。idp は今のまま
   `scope` を載せず、宛名だけを刻む。
2. 許可簿は「使ってよい操作」の一覧で、**書いていない操作は通さない（既定は拒否）**。acts_as 型では、
   利用者のロールと許可簿の**両方**を満たすときだけ通す。
3. 操作の名前（例: `issues:create`）はアプリごとに決める。このテンプレートには、許可簿の仕組みと書き方
   だけを入れる（#721）。
4. 宛名の確かめは許可簿の前提とする。`MACHINE_AUDIENCE` が空なら、機械の口は閉じる（#718）。

## 理由

### §1

- **基準を「2 回目」にするのは、SSO で使った物差しをそのまま当てるため。** SSO を取り込んだ根拠は
  「同じ判断が 3 回書かれ、3 回目で食い違った」ことだった（ADR-0077 §1）。「要りそうだから」で入れ始めると、
  テンプレートは使われない入口で膨らみ、「とりあえず有効にしてみる」を誘う。
- **`acts_as` を採るのは、語彙を増やさないため。** 認可はすべて scope で決めている（ADR-0076 §1）。機械が
  「ある利用者として振る舞う」なら、ロールと権限の仕組みがそのまま使える。人間用と機械用で同じモデルを
  二重に持たない。
- **`sub_type` の確認を落とすと素通しになる。** 利用者主体のトークンと機械のトークンを分ける唯一の印で、
  見落とすと**誰かのログイン用トークンで機械の口が通る**。`sub == client_id` も要る —— idp は 2 つを別々の
  材料から組み立てているので、確かめないと「利用者の `sub` + 登録済みの `client_id`」を持つトークンが通る。
  **この 2 つは実装が忘れうる種類のもの**なので、ドメインの 1 か所に閉じる。
- **`aud` を主にするのは、`client_id` の照合より素性が良いから。** 宛名は発行の時点で認可サーバが確かめており、
  受け側は自分の名前と比べるだけで済む。`client_id` の照合は「知っている相手か」しか見ておらず、
  **別のアプリ向けに出したトークンでも通ってしまう**（blobshare が今そうなっている）。
- **監査の帰属を分けるのは ADR-0075 §1 の続き。** 機械の操作を利用者本人の操作として残すと、後から区別できない。

### §2

| 案 | 中身 | アプリを足すときの手間 | 騙されたときに届く範囲 | 止め方 |
|---|---|---|---|---|
| A | idp に宛名ごとの scope を登録し、トークンに載せる | idp の登録とアプリの両方を直す | scope の分だけ | idp で scope を外す |
| **B（採用）** | idp は今のまま。アプリが許可簿で決める | アプリだけ | 許可簿の分だけ | アプリの設定を直す。全部止めるなら idp でクライアントを止める |
| C | idp は粗い区分、アプリが細かい判定 | 両方 | 許可簿の分だけ | 両方 |

- 操作の単位はアプリの作りそのもので、アプリを直すたびに変わる。それを idp に写すと、2 か所を同時に揃える
  運用になる（2026-09-02 に scope を足さないと決めた理由と同じ）。
- 絞れる範囲は A でも B でも同じ。判定するのはどのみちアプリなので、B は「どこに書くか」の違いでしかない。
- nolumiadeck の許可簿と blobshare のバケットという、すでに動いている手本がある。
- C は A と B の手間を両方負う割に、B より狭く絞れるわけではない。

## 影響

### §1

- **参照実装は nolumiawiki** の `bounded_contexts/identity_federation/`（`machine_client` /
  `exchange_machine_token` / `machine_router` と `OidcProviderGateway.verify_machine_token`）。
  ⚠ あちらは宛名が使えるようになる前の実装で、`aud` の確認が任意になっている —— 写すときは決定 3 に合わせて
  `aud` を必須にする。
- #721 で決めること: `acts_as` と許可簿の登録をどこに持つか（設定か表か）と、監査の帰属の表し方。
  決めたらこの ADR に書き足す。

### §2

- 機械の口を持つアプリは、それぞれ許可簿を持つ（#722）。deploy-repo の `MACHINE_CLIENTS` の各行に、
  使ってよい操作の欄が増える。
- 「この機械はどのアプリで何ができるか」は、idp を見ても分からない。棚卸しの表（#716）で一覧にする。
- 受け側が増えたら、idp の宛名の登録とアプリの許可簿の両方が要る（宛名は idp、操作はアプリ）。
