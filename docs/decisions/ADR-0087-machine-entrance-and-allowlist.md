# ADR-0087: 機械の口は許可簿の操作（権限コード）だけを scope に載せ、scope で守った口だけを通す

- 日付: 2026-10-30
- 状態: 承認
- 関連: ADR-0082（機械の口の基準と、許可簿で決めること）・ADR-0076 §5（トークンは DB を引かずに確かめる）・
  ADR-0078（認可は scope）・ADR-0075 §1（監査）・task #718（宛名の必須）・#721（雛形への実装）・#722（各アプリへ）

## 文脈

ADR-0082 で、機械の口をテンプレートに入れること、何をしてよいかはアプリの許可簿で決めること（既定は拒否・
利用者のロールと許可簿の両方を満たすときだけ通す）、宛名（`MACHINE_AUDIENCE`）が空なら口を閉じることを決めた。
残っていたのは、許可簿をどこに持つか、「操作」を何で表すか、どこで確かめるか、監査にどう残すかである
（ADR-0082 §1 の影響）。

## 決定

1. **口は `POST /api/machine/token`。** assay の `client_credentials` のトークン（`Authorization: Bearer`）を、
   このアプリのアクセストークンへ換えて本文で返す。リフレッシュトークンは出さない。Cookie は読まず、載せない。
2. **許可簿は環境変数 `MACHINE_CLIENTS`（JSON の配列）に持つ。** 1 行は
   `{"client_id", "name", "acts_as", "operations": [...]}`。`client_id` か `acts_as` の無い行は捨てる。
   画面からは変えられない。
3. **操作は権限コード（scope）で書く**（`item:view`・`note:write` など）。機械のために別の語彙を作らない。
   細かい操作を分けたい派生アプリは、権限コードを分ける。
4. **機械に出すトークンの scope は、振る舞う利用者の全ロールの権限と `operations` の重なりだけ。** トークンには
   名乗った機械の `client_id` を `machine_client` クレームで載せる。`auth_time` は「ずっと前」にする
   （入り直したばかりを要る操作は、機械は通れない。ADR-0076 §10）。
5. **機械の主体が通るのは、scope で守った口だけ**（`require_permission` / `require_any_permission` と、主体の
   テナントを取り出す依存関数）。人だけの口（`get_current_principal` を直に使う口。本人の情報・ロールの切り替え・
   資格情報の作り替え・管理の関門など）は、機械のトークンを `403 machine_not_allowed` で断る。
6. **受け取るトークン**: 発行者はこのアプリに登録された有効なテナントのもの（ADR-0079 §4）、宛名は
   `MACHINE_AUDIENCE`、主体は `sub_type == "client"` かつ `sub == client_id`（ADR-0082 §1 決定 3）。
   `acts_as` は発行者のテナントの中で、有効な利用者を引く（ここで利用者を作らない）。
   `MACHINE_AUDIENCE` か `MACHINE_CLIENTS` が空なら口は閉じる（どのトークンも 401）。許可簿があるのに宛名が
   空なら、起動のログに `machine_entrance_closed_audience_missing` を出す。
7. **断るときは理由を言わない 401**（`machine_authentication_required`）。IdP に届かないときだけ 502。
8. **監査**（実行者は振る舞う利用者、対象は `machine_client:<client_id>`。ADR-0082 §1 決定 4）:
   - `machine_token.issued` —— トークンを出した
   - `machine_token.refused` —— 換える段で断った（理由はエラーコード）
   - `machine_operation.performed` —— 機械が書く操作を通した（理由は `POST /api/items` のような経路の型。読むだけの操作は残さない。task #724）
   - `machine_operation.refused` —— 機械の操作を断った（理由は `not_in_allowlist` / `role_lacks_permission` /
     `person_only` と、その操作）

## 理由

- **許可簿を環境変数に置くのは、機械に何をさせるかの変更をレビューの段に通すため。** 画面や表で持つと、設定を
  書ける人が機械に何でもさせられる。deploy-repo の宣言に書けば、変更は PR として残る（`APP_CLIENT_IDS` と同じ扱い）。
- **操作を権限コードで書くのは、確かめる仕組みを 1 つにするため。** scope に載せてしまえば、確かめるのは今の
  `require_permission`（DB を引かない。ADR-0076 §5）で、機械用の判定を別に書かずに済む。語彙を分けると、
  権限コードと操作名の対応を 2 か所で持つことになる。
- **重なりにするのは、ADR-0082 §2 決定 2 の「両方を満たすときだけ」をそのまま形にしたもの。** 利用者が権限を
  失えば、次に換えたトークンから機械も失う。
- **人だけの口を既定で断るのは、scope で守っていない口は許可簿で絞れないから。** 開けたままにすると、許可簿が
  空の機械でも利用者として本人の設定やロールの切り替えを叩ける。断る側を既定にすれば、口を足し忘れても
  閉じたままになる（機械に開けたい口は scope で守る）。
- **リフレッシュトークンを出さないのは、機械は assay から取り直せるから。** 長命な資格情報を増やさない。

採らなかった案:

| 案 | 捨てた理由 |
|---|---|
| 許可簿を DB の表に持ち、画面で編集する（deck の形） | 画面から機械の権限を広げられる。テンプレートの規模では宣言で足りる |
| 操作に専用の名前（`issues:create` など）を使い、権限コードと対応表を持つ | 確かめる仕組みと対応表が 2 系統になる |
| 人だけの口を明示して、それ以外は機械も通す | 口を足すたびに付け忘れが起き、付け忘れは「開いたまま」になる |
| 機械にもリフレッシュトークンを出す | 長命な資格情報を増やすだけで、得るものが無い |

## 影響

- 派生アプリへ取り込むときは、`MACHINE_CLIENTS` の各行に `operations` を書いてから入れる。書かない行の機械は、
  どの操作もできなくなる（#722）。
- 派生アプリで、scope で守っていない口を機械に叩かせていた場合は、その口を `require_permission` で守る。
  守らないままだと `403 machine_not_allowed` になる。
- 機械のトークンの scope は換えた時点のもので、寿命（5 分）まで効く。許可簿を狭めた・利用者の権限を外したことは、
  次に換えたときから効く。
- 書き方は `docs/OPERATIONS.md`「機械に API を叩かせたいとき」。
