# ADR-0072: 開発の仕組み（品質ゲート・CI・文書）

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0006（§1）・旧 ADR-0007（§2）・旧 ADR-0009（§3）・旧 ADR-0012（§4）・旧 ADR-0030（§5）・旧 ADR-0054（§6）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

長期保守を前提にする以上、レビューの注意力に頼る部分を機械へ寄せる必要がある。整形・型・試験・
層の依存方向・設計の定量基準は CI で落とし、機械で検査できない「現在の仕様」の文書は変更と同じ
コミットで更新する義務として持つ。CI そのものの走らせ方（いつ走るか・action の版・ブラウザの試験）も
ここで決める。

このリポジトリは雛形なので、ここに置いた検査・試験・ワークフローは派生アプリに最初から付いていく。

## 決定

### §1 品質は CI の必須ゲートで守る（整形・静的解析・型・テスト）

整形・静的解析・型・試験を CI の**必須**ゲートにする。落ちたらマージできない。

| 対象 | ゲート | コマンド |
|---|---|---|
| Backend | 整形 | `uv run ruff format --check .` |
| Backend | 静的解析 | `uv run ruff check .` |
| Backend | 型 | `uv run mypy` |
| Backend | テスト | `uv run pytest` |
| Frontend | 整形 | `npm run format:check`（Prettier） |
| Frontend | 静的解析 | `npm run lint`（ESLint） |
| Frontend | 型 | `npm run type-check`（`tsc --noEmit`） |
| Frontend | テスト | `npm run test`（Vitest） |

設定の要点:

- Ruff: `line-length = 120`、`select = [E, F, I, B, UP, SIM, C4, ARG, N, RET, PTH, RUF]`（設計の定量基準の
  ルールは §4 で足す）。`RUF001`〜`RUF003`（紛らわしい Unicode 文字）は除外する。
- MyPy: `strict = true` に加えて `warn_unreachable` / `implicit_reexport = false`。対象はテストを含む全ソース
  （`[tool.mypy] files`）。型なし関数を許す per-module override（`disallow_untyped_defs = false`）は置かない。
- ESLint: `typescript-eslint` の `strictTypeChecked` を土台に、`no-floating-promises` / `no-explicit-any` /
  `consistent-type-imports` / `react-hooks/*` / `sonarjs/cognitive-complexity`（15）を明示的に error にする。
  `restrict-template-expressions` は `allowNumber: true`。
- TypeScript: `strict` に `noUncheckedIndexedAccess` / `exactOptionalPropertyTypes` / `noImplicitOverride` /
  `noFallthroughCasesInSwitch` を足す。
- DDD の依存方向は `tests/unit/test_layer_dependencies.py` が AST で検査する（Domain は Application /
  Infrastructure / Presentation を import しない、など）。`Presentation → Infrastructure` は禁止しない。

CI の各ステップは `if: always()` を付け、前段が落ちても後段を流す。手元では `make check` が同じ順序・
同じコマンドを流す。pre-commit フックは任意の補助（`make format`）で、砦は CI に置く。

### §2 画面仕様・ER 図・ADR・Progress は変更と同じコミットで更新する

「現在の仕様」を示す 2 つの文書を置き、CLAUDE.md に**変更と同じコミットで更新する義務**として書く。

| 文書 | 内容 | 更新の引き金 |
|---|---|---|
| `frontend/README.md` | 画面遷移図（Mermaid）・画面一覧・画面仕様・操作マニュアル | 画面の追加・削除、ルート変更、遷移変更、必要 scope の変更、操作手順の変更 |
| `docs/ER.md` | ER 図（Mermaid）・テーブル定義・モデリング規約 | テーブル・カラム・リレーション・制約の変更 |

あわせて CLAUDE.md に次を書く。

- **タスク管理**: `Progress.md` を唯一のタスク一覧とし、着手前に行を足し、状態を進め、完了時に消す
  （「✅完了」の状態を作らない）。完了報告の前に更新する。
- **設計判断**: 選択肢のある決定は必ず `docs/decisions/ADR-NNNN-*.md` に残す。採番は最大値 + 1
  （欠番と重複を作らない）。承認済みの ADR は書き換えず新しい ADR で置き換える。実装と同時に足す。

図はコードから自動生成せず手で書く。API の形は書かない（Swagger UI / `openapi.json` が唯一の出所で、
`frontend/README.md` は「どの画面がどのエンドポイントを使うか」だけを持つ）。

### §3 CI は main への push と pull_request でだけ走らせ、古い実行は取り消す

1. `push` の対象は `main` だけにし、フィーチャーブランチは `pull_request` 側だけで検査する。
2. `concurrency` を設定し、同じ枝（PR）へ続けて push したら古い実行を取り消す（`cancel-in-progress: true`）。
3. ⚠ **`main` も取り消す。** 間のコミットの合否は残らず、最後まで走ったコミットだけが緑・赤を残す。
4. 副作用のあるワークフロー（版上げの commit を push する・イメージを registry へ押す・配る）は途中で
   止めると壊れるので、2・3 の取り消しを当てない。

`branches` を指定したワークフローはタグ push に一致しない（`v*` タグは `release.yml` の担当）ので、
`tags-ignore` は書かない。

### §4 設計品質の定量基準を Ruff と AST テストで機械検証する

基準どおりの閾値で入れ、違反している既存コードは直す（緩い値で入れて段階的に締めることはしない）。
検査は 2 か所に分ける。

- **Ruff**（`pyproject.toml`）: `C901`（複雑度 10）/ `PLR0912`（分岐 8）/ `PLR0913`（引数 4）/
  `PLR0915`（文 30）。
- **AST テスト**（`tests/unit/test_design_metrics.py`）: ネスト深度 3・クラス長 200 行。対応する Ruff の
  ルールが無いため、`test_layer_dependencies.py` と同じ方式で検査する。

基準と機械検証の閾値をずらすのは 2 点だけ。

- **引数は 3 ではなく 4 で検査する**（レビュー上の基準は 3 のまま。機械は「5 個以上を止める」線）。
- **関数長は行数ではなく文の数（`PLR0915` 30）で検査する。**

試験コードの引数は対象外にする（`per-file-ignores`）。例外は試験内の `_CLASS_LENGTH_EXEMPTIONS` に
理由文とともに集め（いまは `ApplicationSettings`）、**消えたクラスが例外に残らないことも**試験で
検査する。`make check` / CI のコマンドは変わらない（`ruff check` と `pytest` に相乗りする）。

Frontend は `sonarjs/cognitive-complexity`（15）が別の尺度で見ており、Backend の閾値には揃えない
（揃えるかは別に判断する）。

### §5 Actions は Node 24 で動く版を使い、動く major タグが無いものだけ完全な版で固定する

Node 20 を要求する action は使わない。動く major タグがあるものはそれを使い、無いものだけ完全な版で
固定する。

| action | 版 | 固定の仕方 |
|---|---|---|
| `astral-sh/setup-uv` | `@v10.0.1` | **完全な版**（上流が v8 以降 major タグを出していない） |
| `docker/setup-buildx-action` | `@v4` | 動く major タグ |
| `docker/build-push-action` | `@v7` | 動く major タグ |
| `actions/checkout` / `actions/setup-node` | `@v6` | 動く major タグ |

`setup-uv` の行には、**なぜここだけ書き方が違うのか**をワークフローにコメントで残す（派生側が「揃って
いない」と見て直してしまわないように）。

### §6 実ブラウザの E2E は煙試験に絞って雛形に置く

1. Playwright の E2E を `frontend/e2e/` に置く。中身はどのアプリにも共通する道の**煙試験**だけ:
   ログイン・ログアウト、Service Worker の下でも API が SPA に飲まれないこと、新しい版の知らせ
   （ADR-0080 §7）。
2. CI では `ci.yml` とは別のワークフロー（`.forgejo/workflows/e2e.yml`）で回す。
3. 本物のサーバーを立てる。DB は使い捨ての SQLite、画面はその場でビルドし、FastAPI がそのまま配る。
4. 入り口はローカルのログイン（初期管理者）。パスワードは試験が決めて `ADMIN_INITIAL_PASSWORD` で
   渡す（既定のパスワードには頼らない）。
5. 新しい版は、配った `sw.js` を書き換えて起こす。
6. Playwright 公式の像（タグと digest で固定）で回し、`@playwright/test` は版をきっちり固定する。
   像の版（`PLAYWRIGHT_VERSION`）とずれたら最初の段で落とす。

## 理由

### §1

- **整形はツールに一本化する。** 差分から「好み」を消すと、レビューが設計の話だけになる。
- **MyPy を試験にも掛ける。** 試験の型付けを免除すると、フィクスチャの取り違えやシグネチャのずれが
  本番コードの型情報を空洞化させる（試験を型付けした結果、`RestartWatcher` が具象の
  `RestartRequestStore` に依存していた DIP 違反が見つかり、`RestartRequestReader` Protocol を切り出した）。
- **依存方向を ADR と試験の二重で持つ。** 文章だけの規約は必ず腐る。AST で検査すれば違反した時点で落ちる。
- **`Presentation → Infrastructure` は禁止しない。** 最も外側の層が具体実装を組み立てて `Depends()` に
  渡すのは正しい向きで、DI の配線はどこかで行う必要がある。禁止するなら組み立て責務を Application 層へ
  移す別の設計判断が要る。
- **`if: always()`** は 1 回の CI で全部の指摘を受け取るため。fail-fast だと「整形を直す → 型で落ちる →
  また直す」で往復が増える。
- `RUF001`〜`RUF003` を外すのは、コメント・docstring が日本語で、全角括弧・読点に誤検知しかしないため。
  `allowNumber: true` は、ID を URL に埋める数値の文字列化が安全で、規則の主眼がオブジェクト・`null` の
  混入にあるため。

| 採らなかった案 | 理由 |
|---|---|
| pre-commit フックだけで済ませる | 手元で `--no-verify` を通されると意味が無い |
| `import-linter` で依存方向を検査する | 依存が 1 つ増える。検査したい規則は数本で、AST で 150 行に収まる |

### §2

- **図はコードから自動生成しない。** 自動生成（`eralchemy` 等）はツールと CI の実行環境を要求する一方、
  「なぜこのテーブルが FK を持たないか」「どの画面がどの scope を要求するか」を出せない。手書き + 更新義務の
  ほうが情報量あたりの費用が低い。
- **Mermaid を使う。** forge・GitHub がそのまま描画し、差分がテキストとしてレビューできる。
- **API の形を二重に書くと必ず乖離する**ので、`openapi.json` を唯一の出所にする。
- 文書と画面一覧の差分を CI で検査する案は、自然言語の部分（操作手順・テーブルの意味）を検査できず形式だけを
  守らせる仕組みになるので、いまは採らない（要るときに別の ADR にする）。

### §3

- **重複の原因はトリガーの重なりそのもの。** `push` を全ブランチにすると、PR のある枝では同じコミットが
  `push` 側と `pull_request` 側で 2 回検査される。`concurrency` では消せない（両者は `github.ref` もイベント名も
  違い、同じグループに入れる自然なキーが無い）ので、片方の対象を狭める。
- **`main` も取り消すのは、ランナーが全リポジトリで 1 つの列を共有しているため**（deploy-repo の
  `host/runner-burst`）。マージや版の書き戻しで `main` への push が続くと、意味の無い古いコミットの検査が
  列を塞ぎ、後ろの実行を待たせる。PR 側の検査（マージ前に必ず緑）とマージ後の最新コミットの検査は残るので、
  どこで壊れたかの切り分けは PR 単位で行う。

| 採らなかった案 | 理由 |
|---|---|
| `pull_request` をやめて `push` だけにする | フォークからの PR が検査されない |
| `push` 側のジョブを `if` で PR のときだけ飛ばす | 実行自体は立ち上がりチェック欄に残る。PR の有無を知る API 呼び出しも要る |

### §4

- **引数 4。** Ruff は `Depends()` の依存注入・FastAPI のクエリパラメータ・キーワード専用の任意引数も
  1 個と数える。3 で強制すると `webauthn_relying_party`（暗号パラメータ 4 個）のような妥当な署名まで落ちる。
  導入時の実測で 5 個以上は 2 件だけで、どちらも直すべき状態だった。
- **関数長は文の数で代える。** 行数だと日本語の docstring・複数行の型注釈・折り返した引数リストが違反に
  なり、説明を削る圧力になる（移行スクリプトの `upgrade` は 86 行でも文は数個）。文 30 は導入時に違反 0 で、
  「30 行の関数はおおむね文 30 個以下」と対応する。
- **試験の引数を外す**のは、pytest の関数引数がフィクスチャの注入であって設計上の引数の多さではないため
  （`ARG001` / `ARG002` の除外と同じ理由）。
- **`ApplicationSettings` を例外にする**のは、設定キーの数に比例して伸びる `@property` の集まりで、分割すると
  「設定は `settings.py` の `@property` 経由」という規約の出所が散るため（CLAUDE.md「設定管理」）。

| 採らなかった案 | 理由 |
|---|---|
| `PL` ルール群をまとめて有効にする | `PLR2004`（マジックナンバー）など基準と無関係なルールが大量に入る |
| 緩い閾値（複雑度 15・引数 5）で入れて段階的に締める | 実測がほぼ 0 件なのに、基準を満たさないコードの入る余地をわざわざ作る |
| `radon` / `xenon` を足す | ツールと CI のステップが増える。Ruff で足りない 2 項目は AST 試験で書ける |

### §5

- **Node 20 の強制実行は仕様ではなく猶予。** ランナーは `node20` を要求する action を Node 24 で強制的に
  動かしているが、猶予が切れれば止まり、予告は注釈にしか出ない（チェックは緑のまま）。
- **上流が major タグを出していないものを無理に揃えない。** `setup-uv` は、動くタグが差し替えられて
  サプライチェーン攻撃（`tj-actions` の事件のような）の入口になるのを避けて major タグをやめた。こちらで
  タグを作れば上流が避けたものを復活させ、古い版に留まれば Node 20 のままになる。**書き方の不揃いは固定の
  強さが違うという事実の反映**で、直すべき乱れではない。
- **全部を完全な版で固定しない。** `checkout` や `setup-node` まで手で追うことになり、派生アプリに月次の
  追随作業を押し付ける。動く major タグを出す上流はパッチを自動で配る運用を選んでいるので、それに乗る。

### §6

- **jsdom（Vitest）には Service Worker が無い。** SW が認証の内側に入って更新が止まる、API の道の改名で
  PWA が壊れる、新しい版の知らせが出ない——実際に起きた壊れ方は jsdom では捕まらない。
- **本物のサーバーを立てる。** API を偽物にすると、SW と配り方（`spa.py` の受け皿と `Cache-Control`）が
  試験の外に出る。
- **入り口をローカルのログインにする**のは、雛形の既定で開いている口で、idp を立てずに済むため。
- **`sw.js` を書き換える**のは、版を 2 つビルドするより速く、ブラウザから見れば「新しい版が配られた」と同じだから。
- **別のワークフローにする**のは、画面のビルドとブラウザの分だけ遅く、Backend / Frontend の速い検査の結果を
  待たせないため。公式の像はブラウザと OS 側の依存を毎回入れずに済む。

| 採らなかった案 | 理由 |
|---|---|
| 画面を全部回る網羅試験 | 派生アプリの画面に合わなくなり、雛形の試験が消されるか赤のまま放置される |
| Vitest の browser mode | SW のライフサイクル（登録・待機・入れ替え）とページの読み込み直しを通せない |
| API を偽物にした軽い E2E | 見たいもの（SW と配り方）が偽物の側に入る |

## 影響

### §1

- 新しいコードは 8 ゲートすべてを通す必要がある。
- 「関数長・引数・複雑度・クラス長」の定量基準は §4 で Backend も機械検証している。

### §2

- 画面またはテーブルを変える作業には、対応する文書の更新が含まれる。レビューでは差分に該当ファイルが
  含まれているかを見る（機械検証はしない）。
- `docs/ER.md` と `frontend/README.md` は**コードに追従する側**で、正本ではない。食い違ったときは
  モデル・マイグレーション・`App.tsx` が正しい。
- ADR の採番規則があるので、`NNNN` の欠番・重複はレビューで指摘できる。

### §3

- **PR を作っていない枝への push では CI が走らない。** PR を作ればその時点で全ゲートが走る。手元では
  `make check` が CI と同じ順序・同じコマンドを流す。
- `main` の間のコミットには合否が残らない。
- 必須ゲートの中身（§1 の 8 種）は §3 では変えない。§3 は実行の条件だけを決める。

### §4

- **これから足すコードは、5 個以上の引数・複雑度 11 以上・文 31 個以上・ネスト 4 段・200 行を超えるクラスを
  書けない。** 分けられない事情があるときは `# noqa: <rule>` に理由を添えるか、例外リストへ理由付きで加える。
- 検査の範囲は mypy の `files` と同じ（試験自身も含む）。新しいトップレベルのパッケージを足したら、
  `pyproject.toml` の `files` と AST 試験の `_SOURCE_ROOTS` の両方に足す。

### §5

- **`setup-uv` の版を上げるのは手作業になる。** `@v10.0.1` は自分では動かない。上げ忘れてもすぐには壊れない。
- `setup-uv` v9 から `prune-cache` の既定が `false`。キャッシュ使用量は増えるが、リポジトリ単位で上限まで
  LRU で回るだけなので明示の設定は足さない。
- `setup-uv` の v10 は `pull_request_target` / `workflow_run` / `release` でキャッシュを自動で無効にするが、
  §3 のとおりこれらのトリガーは使っていない。新しく使うときは確かめる。
- ⚠ **`docker/setup-buildx-action@v4` / `docker/build-push-action@v7` は Actions Runner v2.327.1 以降を要求する。**
  セルフホストのランナーへ載せるときは、先にランナーを更新する。

### §6

- PR ごとに E2E のジョブが 1 本増える（画面のビルドとブラウザの起動の分、数分かかる）。
- ⚠ `@playwright/test` を上げるときは、`e2e.yml` の像（タグと digest）と `PLAYWRIGHT_VERSION` も同じ版へ上げる。
  片方だけだと照合の段で落ちる。
- 派生アプリでログインの入り口を変えたら（パスワードのログインを閉じるなど）、`frontend/e2e/sign-in.spec.ts` も
  その入り口に合わせて直す。
- 試験を足すのは、どのアプリにも共通して壊れうる道に限る。アプリ固有の画面の試験は、派生アプリの側で別の
  ファイルとして足す。
