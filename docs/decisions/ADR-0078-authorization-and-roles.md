# ADR-0078: 認可とロール

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0017（§1）・旧 ADR-0018（§2）・旧 ADR-0024（§3）・旧 ADR-0051（§4）・旧 ADR-0052（§5）・旧 ADR-0070（§6）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

認可は scope（権限コード）だけで判定し、ロール名で分岐しない（CLAUDE.md「権限管理」）。
ユーザーは複数のロールを持てる（`user_roles` は多対多）。アクセストークンは DB を引かずに
検証し、寿命は既定 5 分（ADR-0076 §5）。ロールと権限はテナントの中に閉じる（ADR-0079 §1・§3）。
その上で、いま使うロールの選び方・ロール一覧を読める権限・初期管理者の据え方・ロールの分け方と
権限を動かす関門・全権限のロールの名前・資源 1 件ずつの可否の確かめ方を決める。

## 決定

### §1 アクティブロールは JWT クレームで持ち、既定は全ロールの和集合

普段は弱いロールで操作し、必要なときだけ強いロールへ切り替えたい（「member からどう見えるか」を
別アカウント無しで確かめることも含む）。

1. アクティブロールは **JWT の `active_role` クレーム**に持ち、切り替えは
   `POST /api/auth/switch-role` による**トークンの再発行**で行う。
   refresh トークンにも同じクレームを載せ、更新しても選択が続く。
2. `active_role` が `null` のときは**全ロールの権限の和集合**。
   ロールを 1 つ選ぶと、有効 scope はその**ロール 1 つ分の権限**に絞られる。
3. 保有していないロールへは切り替えられない（403 `role_not_granted`）。scope は**発行・更新の
   時点で** `保有の権限 ∩ アクティブロールの現在の権限` として取り直す。⚠ **発行済みのトークンは
   切り詰められない**——ロールを外しても効くのは次の更新からで、上限はアクセストークンの寿命
   （既定 5 分。ADR-0076 §5）。
4. `AuthenticatedPrincipal` は `active_role` を持つが、**認可の分岐には使わない**。

### §2 ロール一覧の取得は `user:manage` でも許可する（変更は `role:manage` のまま）

ユーザー管理画面（`user:manage`）はロールを割り当てるために一覧が要る。`user:manage` だけの
ロールでは一覧が 403 になり、割り当ての選択肢も既存の割り当ての表示も消えていた。

1. `GET /api/admin/roles` は `role:manage` **または** `user:manage` で通す（返すのはそのテナントで
   選べるロール。ADR-0079 §3）。
2. ロールの作成・更新・削除は `role:manage` のみ。
3. 「いずれか 1 つ」の依存関数 `require_any_permission()`（`presentation/fastapi/dependencies/auth.py`）を
   置く。**読み取りにのみ使う。**

### §3 ロールを足す投入と、初期管理者を据える操作を分ける

2026-09-02、派生アプリ `blobshare` の本番で、運用者が削除した `admin@example.com` が、権限を足す
マイグレーションで `id=1` / `is_active=1` のまま復活した。パスワードは
`master_data.DEFAULT_ADMIN_PASSWORD_HASH`（平文がリポジトリと文書にある既定値）で、前段に認証の無い
公開サイトだった（約 24 分後に削除。ログイン試行は無し）。投入の関数が「初期管理者が居なければ作る」
まで抱えていたためである。

1. `seed_master_data(session)` —— ロールと権限だけ。**利用者を作らない。**
2. `ensure_default_admin(session, password=None)` —— 初期管理者が**居なければ**据える。
3. 呼ぶ場所は次のとおり。⚠ **新しいマイグレーションで `ensure_default_admin` を呼ばない。**

| 呼ぶ側 | `seed_master_data` | `ensure_default_admin` |
|---|---|---|
| `0002_seed_master_data`（据え付け） | ○ | ○ |
| 権限を足すマイグレーション（`0005` 以降のシードすべて） | ○ | **×** |
| `scripts/seed_master_data.py`（手で流す＝復旧） | ○ | ○ |
| テストの土台（`tests/conftest.py`） | ○ | ○ |

### §4 ロールは系統で分け、権限は自分の範囲でしか動かせない

scope の検査（`require_permission`）は「その画面を使えるか」までしか見ない。そのままでは
`user:manage` だけの人による昇格や格上のパスワードの書き換え、管理者自身の締め出しができた。

1. ロールの雛形を**扱うものの系統**で分ける。`system-admin`（システム）・`user-admin`（人）・
   `auditor`（監査。読むだけ）を置き、`manager` / `member` / `guest` はコンテンツの系統とする。
   全権限の持ち主は `owner`（§5）。系統をまたぐロールは雛形に置かない。
   `owner` はテナント管理者でテナントの中の全権限を持ち、`system-admin` はテナントの外の席で、
   全体の権限（`SYSTEM_PERMISSIONS`）はこれだけが持つ（ADR-0079 §1 決定 4・§3 決定 2）。
2. 管理 API で権限を動かす操作に、scope とは別の関門を掛ける
   （`presentation/fastapi/routers/admin/authority_guard.py`）。関門はテナントの中で通す。
   - **自分が持っていない権限は、配ることも取り上げることもできない**（ロールの付け外し・
     ロールの中身の変更。付けたものと外したものの両方を見る）
   - **自分より多くの権限を持つ利用者には触れない**（パスワード・名前・有効状態・削除）
   - **自分のロール・有効状態・存在は変えられない**（名前とパスワードは変えてよい）
   - **「管理の要」（`user:manage` と `role:manage` の両方）を持つ有効な利用者を 0 人に
     する変更は 409 で戻す**。数えるのはテナントごと（ADR-0079 §1 決定 7）
3. 比べる「自分の権限」は、いま有効な scope（アクティブロールで絞った後。§1）。

### §5 全権限のロールは `owner` と呼ぶ

1. 全権限のロールの名前は `owner`（id 1）。系統ごとの係は `<系統>-admin` と呼ぶ。
2. 既存の DB はマイグレーション 0012 で名前の列だけを `admin` から `owner` へ書き換える（付与はそのまま）。
3. 既定の管理者の利用者名・メールアドレス（`admin` / `admin@example.com`）は利用者の名前なので変えない。

### §6 機能の権限はトークンで、資源 1 件ずつの可否は DB で確かめる

scope は機能単位で、今は 15 個・約 250 バイト（Cookie の 4KB に届くのは 100 個前後）。膨らむのは
資源 1 件ずつの可否（`note:42:edit`）を入れたときで、グループ（ADR-0081 §3）で共有する見本が要った。

1. 認可を 2 段に分ける。
   - **機能を使えるか**（何ができるか）は、トークンの `scope` で確かめる。DB は引かない（ADR-0076 §5）。
   - **この 1 件を扱えるか**（どれに対してか）は、持ち主・所属などの**データで、リクエストのたびに DB で**確かめる。
2. `scope` に資源の ID や資源ごとの可否を入れない。グループの所属もトークンに入れない。
3. 読めない資源には 404 を返す（在ることを教えない）。読めるが変えられない資源には 403 を返す。
4. 画面は 2 段を両方見る。機能のボタンは scope で、行ごとのボタンはサーバーが返す可否（`can_change`）と scope の両方で出し分ける。
5. 見本として、共有メモ（`bounded_contexts/notes`）を置く。
   - 機能の scope は `note:view`（読む）と `note:write`（書く）。
   - メモ 1 件の可否は、持ち主なら読めて変えられる、共有先のグループの一員なら読むだけ。
   - 共有先に選べるのは、自分が入っているグループだけ。

## 理由

### §1

- **JWT に持つ（`users.active_role_id` にしない）**: 切り替えはセッションの状態で、アカウントの
  属性ではない。DB に持つと、片方のブラウザで絞ったつもりが別の端末の権限まで変わる。
- **切り替えで再発行する（発行済みの scope を後から読み替えない）**: 同じトークンが時点によって
  別の権限を意味すると、ログ・監査から「どの権限で叩いたのか」が読めなくなる。
- **既定を和集合にする**: 切り替えは権限を**減らす**方向にしか働かないので、既定が広くても
  昇格の経路にならない。`active_role` は表示と選択肢の提示のためにあり、絞った結果は既に
  `permissions` に反映されている。

### §2

- 「ロールを割り当てられる」は「どんなロールがあるか読める」を前提にしている。一覧が漏らすのは
  ロール名と権限コードで PII ではなく、`user:manage` を持つ者はユーザーのロールを通じて同じ情報に触れられる。
- 採らなかった案: 読み取り専用の一覧を別に足す（入口が 2 つになり `RoleResponse` が二重管理になる）。
  ユーザー管理画面に `role:manage` も要求する（ロールの**編集**まで渡し、最小権限に反する）。
- 書き込みに「いずれか」を使うと、どの scope で許されたのかが監査から読み取りにくくなる。

### §3

- **据え付けと運用は別の時間軸にある。** 初期管理者は空の DB に最初の 1 人を置く仕掛けで、運用中の
  再投入は語彙（ロールと権限）を新しい版に合わせる操作である。
- **運用者の削除は決定であって、欠損ではない。** 「居なければ作る」は消した判断を黙って上書きし、
  しかも `ADMIN_INITIAL_PASSWORD` を渡さない呼び出しは公開されている既定のハッシュを使う。
- **「1 人も居なければ作る」にしない**: 復旧手順（管理者の行を消して `scripts/seed_master_data.py` を
  流す。`docs/OPERATIONS.md`）が、他の利用者が居ると効かなくなる。
- **引数（`create_admin=False`）にしない**: 書き忘れた新しいマイグレーションがどちらかに倒れる。
  関数を分ければ、呼ばなかったものは起きない。
- 採らなかった案: `ADMIN_INITIAL_PASSWORD` を本番で必須にする（強いパスワードの管理者が黙って
  復活するだけ）。シードのマイグレーションだけ直接 INSERT する（値の正本を `master_data.py` に
  一本化した規約を崩す）。復活した利用者を無効で作る（消したいものが消せないまま）。

### §4

- **系統で分ける**: システム・人・中身は、触れてよい人も誤ったときの被害も違う。監査を読むだけの
  ロールは、変える人と確かめる人を分ける（職務の分離）ために要る。`manager` の名前は既存の派生
  アプリと発行済みのトークンが持っているので変えない。
- **配れるのは自分の範囲まで**（Kubernetes の RBAC が `escalate` / `bind` を別にしているのと同じ考え）:
  `role:grant` のような専用の権限では、それ 1 つが実質の全権限になり、何を配れるかが画面から読めない。
- **格上に触れない**: パスワードを書き換えられれば、その人の権限は丸ごと取れる。
- **自分は変えられない**: 締め出しを防ぎ、権限の変更に必ず別の人の手を通すため。
- **最後は DB で数える**: 外された人の古いアクセストークンでも範囲の関門は通り抜けうる。数える対象を
  ロール名にしないのは、ロール名で認可を分岐しない原則に従うため。

### §5

- `owner` は「全部を持つ・最後の責任者」と読め、`〜-admin` の係とは別格だと分かる（GitHub・
  Google Cloud・Slack も「Owner ＞ 各種 Admin」）。`superadmin` は `〜-admin` の延長に見える。
- 名前の書き換えにするのは、`seed_master_data` が名前でロールを探すため。先に書き換えずに流すと
  `owner` を新しい行として作り、`admin` が付与ごと残る。

### §6

- Azure RBAC も AWS IAM も、資源ごとの可否をトークンに載せずサーバー側で決めている。Azure は
  グループの所属を載せる形で実際にトークンの大きさの上限に当たっている（JWT では 200 件で打ち切り）。
- 資源ごとの可否はもともとデータで、トークンへ写すとグループを抜けても寿命まで読めてしまう。
  DB で見れば次のリクエストから効く。
- 一覧は SQL で絞り、1 件の可否はエンティティ（`Note.readable_by` / `changeable_by`）が答える。
  決まりが 2 か所になるが、食い違えば統合試験が落とす。

| 採らなかった案 | 捨てた理由 |
|---|---|
| 資源ごとの可否を scope に入れる（`note:42:edit`） | 資源の数だけトークンが膨らむ。外したことが寿命まで効かない |
| 全部を DB で確かめる（ADR-0076 §5 を戻す） | 機能単位の判定まで毎回 DB に頼る。得るものが無い |
| トークンにはロール名だけを載せ、ロール→権限の表をアプリのメモリに持つ | 権限が 100 個に近づいたときの逃げ道として残す |
| テナント管理者（`owner`）にはどのメモも読ませる | 個人のメモを管理者が読めると困る用途がある。要るアプリは別の scope（例 `note:moderate`）を足す |

## 影響

### §1

- `/api/auth/me` は `roles`（切り替え先）と `active_role` を返し、`scopes` は「**いま有効な権限**」である。
- 切り替えは監査ログへ `role.switched`（`reason=role=<ロール名>` / `role=all`）として残す。
- 絞った後にそのロールを外されると、更新の時点で scope は空になる。ロールの変更は再サインインで
  拾い直す前提を崩さない。
- ロールが 1 つ以下の利用者に切り替え UI は出さない。クレームを持たないトークンは `null` として扱う。

### §2

- `require_permission()`（全て必要）が原則で、`require_any_permission()` は「複数の職掌が同じ資源を
  読む」場合に限る。ロール名には秘匿情報を入れない。
- 画面は一覧を取得できない場合に備えて、ユーザーに割り当て済みのロール名から列を補う。

### §3

- 据え付け（新しい DB では `0002` が据える）と復旧の手順は変わらない。
- `tests/integration/test_master_data_seeder.py` が「消した管理者が再投入で戻らないこと」を、
  `tests/unit/test_migrations_do_not_seat_an_admin.py` がマイグレーションからの呼び出しを見張る。
- 本番で既定のパスワードのままの管理者を入れないのは ADR-0073 §4。
- 派生済みのアプリには自動では伝わらない（`blobshare` は自身の ADR-0044、`nolumiawiki` は自身の
  ADR-0057 として反映済み）。

### §4

- `user-admin` は `member` と同じ閲覧の権限を持ち、`member`・`guest`・`user-admin` を配れる。`manager`・
  `owner` への引き上げは、それを持つ人の仕事になる。派生アプリでロールを組み替えるときも、人の係に
  何を配らせたいかに合わせて閲覧の権限を持たせる。
- 誤りの応答: 403 `beyond_your_permissions`（`permissions` に足りない権限）、
  403 `cannot_change_yourself`、409 `last_administrator`。
- 雛形の 3 ロールはマイグレーション 0011 で足す（§3 の `seed_master_data`）。固定の id（5〜7）が
  埋まっていれば採番に任せる。
- 含めないもの: 資源ごとの範囲でのロール付与、グループへのロールの付与、期限付きの昇格。
  資源 1 件ずつの可否は §6。

### §5

- 派生アプリで「作成者だけが直せる」を足すときは、資源の側を「作成者」と呼び、`owner` とぶつけない。
- `active_role` に `admin` を持つ発行済みのトークンは、更新の時点で権限が空になる（§1）。サインインし直す。
- 派生アプリが自前で `owner` を作っていたときは、マイグレーションは書き換えない（`admin` が残る）。手で寄せる。

### §6

- 「誰の・どの範囲の」資源かを分けたい派生アプリは `bounded_contexts/notes` に倣う（エンティティが
  可否を答え、ユースケースで確かめ、一覧はリポジトリが SQL で絞る）。
- 所属を引く DB の読み取りが、資源を扱うリクエストのたびに 1 回増える（主キーと索引で引ける）。
- 権限が 100 個に近づいたら、ロール名だけを載せる案を新しい ADR で検討する。
