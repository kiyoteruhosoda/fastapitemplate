# ADR-0046: アプリへ戻る案内は、認可コードが付いていれば「タップで開き直す」ボタンを出す

- 日付: 2026-09-28
- 状態: 承認
- 関連: [ADR-0045](ADR-0045-the-app-signs-in-to-assay-directly.md)

## 文脈

Android アプリは assay でログインし、戻り先 `https://<このホスト>/app/oauth2redirect` を
App Links でアプリへ渡してもらう（ADR-0045）。2026-09-28 に flutterbase から作った試しの
アプリ（ssotrialapp）で、**端末の App Links の結び付けはオンなのに、ログイン後の戻り先が
アプリの中のタブ（Custom Tab）の中でこの案内ページとして開き、アプリへ渡らなかった**。

assay の記録ではログインは成功し認可コードも出ているが、アプリはコードを引き換えに来ていない。
Chrome は、利用者のタップの直後でない移動（ログインのあとに自動で戻り先へ送る流れ）では、
ほかのアプリを開かずにタブの中で表示する（AppAuth-Android でも同じ報告が多い）。

## 決定

案内ページ（S16）は、URL に `code` と `state` が付いていれば、**同じ URL をもう一度開くボタン**
（「アプリに戻ってログインを終える」）を出す。利用者のタップで開き直すので、Chrome が App Links
どおりアプリへ渡す。

## 理由

- **危なくない。** ボタンが開くのはいま開いている URL そのもので、認可コードは PKCE で
  アプリしか引き換えられない。PC など App Links の無いところで押しても、同じ画面に戻るだけ。
- **アプリ側だけでは直せない。** 移動を起こすのは assay と Chrome で、アプリはタブを開いて
  待つことしかできない。戻り先の画面はこちらが持っているので、ここで利用者の操作を 1 回もらう。
- 採らなかった案: Chrome の Auth Tab（https の戻り先を正式に扱う新しい仕組み）へ移る
  ——正しい方向だが、アプリ側の部品（AppAuth / flutter_appauth）の対応が要る。先にこの画面で
  確実に戻れるようにし、Auth Tab は別に検討する。

## 影響

- アプリのログインは、タブの中で止まったときに利用者が 1 回タップすれば完了する。
- 派生のアプリ（foodexpiryweb など）も、雛形を取り込めば同じ振る舞いになる。
