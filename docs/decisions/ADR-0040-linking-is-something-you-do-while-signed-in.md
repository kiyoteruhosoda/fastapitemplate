# ADR-0040: 結び付けるのは**入っている本人**（設定画面から連携する）

- 日付: 2026-09-14
- 状態: 承認

## 文脈

ADR-0037 で `OIDC_LINK_BY_EMAIL` の既定を倒した。以来、**同じメールアドレスの
ローカル口座を持つ人が初めて SSO で入ると断られる**（`sso_account_not_linked`）。
残っていた逃げ道は 2 つだけで、どちらも筋が悪い。

- **設定を開ける** —— 倒した理由（IdP の `email_verified` は本人の証明ではない）が
  そのまま戻る。
- **管理者が `federated_identities` を直接整える** —— 手で行を入れる運用になる。

idp の ADR-0049 は I9 としてこう書いている ——**本人がログイン済みの状態で、
設定画面から連携する**。**誰と誰を結び付けるかを、メールアドレスという
「同じ値かもしれないもの」ではなく、2 つの認証の結果で決める。**

- このアプリ側の認証 —— いまセッションを持っていること
- IdP 側の認証 —— いま認可の往復を通ってきたこと

**両方を同時に満たしているのは本人だけである。** ここに推測は要らない。

## 決定

### 1. 連携は「入っている状態で始め、戻ってきて完了する」

設定画面（`/profile/security`）に区画を置き、`POST /api/auth/sso/link/start` で
往復を始める。戻りは**ログインと同じ** `GET /api/auth/sso/callback` で受ける。

⚠ **戻り先の URI は 1 つに保つ。** 連携用にもう 1 本増やすと、IdP 側のクライアント
登録が 2 本になり、片方だけ登録し忘れて「連携のときだけ通らない」が起きる。
どちらの後始末をするかは、**往復状態（署名付き Cookie）の `purpose`** で決める。

⚠ **目的をクエリで渡さない。** 戻りの URL を書き換えるだけで、ログインのつもりで
始めた往復を連携に化けさせられる。

### 2. 始めるのは XHR、遷移するのは画面自身

`POST /link/start` は 303 を返さず、認可要求の URL を JSON で返す。画面が
`location.assign` する。

理由は 2 つある。

- **認証が切れていれば 401 を返せる。** 画面遷移で始めると、切れていた場合に
  利用者へ JSON の生文字列が見えるだけで、やり直す導線を出せない。
- **CSRF の守りがそのまま効く。** Cookie で認証する POST なので `CsrfMiddleware`
  の対象になり、よその頁からは起こせない。サインアウト（`GET /logout`）のように
  `Sec-Fetch-Site` を見る必要が無い。

### 3. 結び付ける相手は**往復を始めた利用者**で、戻ってきたときのセッションではない

往復状態に `user_id` を入れ、戻ってきたときのセッションと突き合わせる。違えば
`sso_link_session_mismatch` で断る。

⚠ **これが無いと、往復の途中で入れ替わったブラウザが別人の口座へ結び付ける。**
「戻ってきたときに入っている人」を見て決めると、サインアウト → 別の利用者で
ログイン、を挟むだけで結び付け先がずれる。

### 4. 既に埋まっている結び付きは断る

- その `(issuer, subject)` が**別の利用者**のものなら `sso_identity_taken`。
  ⚠ **横取りになる。** 付け替えを許すと、IdP 側で口座を共有している相手が、
  後からこのアプリの別人の入り口を奪える。
- その利用者に**同じ IdP の別の `subject`** が既にあるなら `sso_already_linked`。
  黙って差し替えると、前の結び付きで入っていた経路が予告なく消える。解除してから
  結び直す。
- **同じ相手をもう一度押した場合は断らない。** 利用者から見て結果が変わらない。

### 5. 解除は「入り口が残るときだけ」通す

`DELETE /api/auth/sso/link`。残る入り口が無ければ `sso_last_entrance` で断る。

⚠ **数えるのはパスワードとパスキーで、二要素認証は数えない。** TOTP は
パスワードの後ろに置く second factor なので、それだけでは入れない。

⚠ **数えるのは呼び出し側（Presentation 層）である。** 第二要素を持っているのは
`account_security` コンテキストで、ID 連携の側から境界を越えて引きに行かない
（ADR-0039 の棚卸しと同じ組み立て方）。ユースケースは `has_other_entrance` を
受け取るだけにする。

## 理由

**「連携してよいか」の判断材料は、往復を始める時点で全部揃っている。** 戻りで
やることは「始めたときの決定をそのまま実行してよいか」の確認だけになる。
決め直す余地を残さないほうが、間違える余地も残らない。

### 検討して捨てた案

- **連携専用の戻り先 URI を作る**（`/api/auth/sso/link/callback`）。経路の見た目は
  はっきりするが、IdP のクライアント登録が 2 本に増える。⚠ **登録の漏れは
  「連携のときだけ通らない」という形で出る**ので、原因がこちらのコードに見える。
- **`GET /link/start` で 303 を返す。** `<a href>` で書けるが、認証が切れていた
  ときに出せるものが無い（上記 決定 2）。
- **管理画面から結び付ける口を作る。** 「誰と誰を結び付けるか」を管理者の目視に
  委ねることになり、**メールアドレスで寄せるのと同じ弱さ**が管理者の手作業として
  残る。本人の 2 つの認証で決める、という筋から外れる。
- **解除のとき、入り口が無ければ自動でパスワードの再設定へ誘導する。** 締め出しは
  避けられるが、**パスワードを持たない利用者にリセットで入り口を生やす**ことに
  なり、ADR-0038 で閉じたばかりの経路をここで開け直す。

## 影響

- **経路が 3 つ増える** —— `GET /link`・`POST /link/start`・`DELETE /link`。
  `GET /callback` は**ログインと連携の両方**を受けるようになった。
- **監査ログに `sso_identity.unlinked` が増える。** 結び付けたときの
  `sso_identity.linked` は既にある（ログイン中の自動結び付けと同じ種類を使う）。
- **画面に区画が 1 つ増える**（S? セキュリティ）。SSO が無効な環境では出ない。
- ⚠ **往復状態の Cookie の形が変わった**（`purpose` と `user_id` が増えた）。
  移行の前に発行された Cookie は `purpose` を持たないので**ログインの往復として
  読む** ——連携が入る前に始まった往復は、必ずログインだからである。
- **`ADR-0037` の影響が和らぐ。** ローカル口座を持つ人は、自分の操作で入り口を
  増やせるようになった。⚠ **まだ結び付いておらず、かつローカルの入り口も無い人**
  （このアプリで利用者を作らない構成の場合）は、依然として管理者に頼むしかない。
