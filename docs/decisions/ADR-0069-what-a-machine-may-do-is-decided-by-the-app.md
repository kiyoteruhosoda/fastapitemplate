# ADR-0069: 機械に「何をしてよいか」は、idp ではなくアプリの許可簿で決める

- 日付: 2026-10-29
- 状態: 承認
- 関連: Assay の ADR-0042（トークンの宛名）・task #715（機械のトークンを最小権限に）・#717（この判断）・#721（雛形への実装）

## 文脈

Assay（idp）の `client_credentials` トークンには `scope` が載らない（いつも空）。載るのは宛名（`aud`）だけで、
何をしてよいかは呼ばれる側のアプリが `client_id` で決めている。

AI のエージェント（Claude）が機械のトークンで各アプリを呼ぶようになった。エージェントはプロンプトインジェクションで騙され得るので、
**騙されたときに届く範囲＝そのトークンでできること全部**になる（OWASP API Top 10 の API5、LLM Top 10 の Excessive Agency）。
いまの受け側には次の 3 つの作りが混ざっている。

- acts_as 型（nolumiatask・nolumiawiki・toeic など）: `MACHINE_CLIENTS` に「誰として振る舞うか」を書く。できることはその利用者のロールと同じで、操作単位では絞れない
- 貸し出し型（blobshare）: `client_id` ごとに使えるバケットを決める
- 許可簿型（nolumiadeck）: 機械ごとの許可を DB に持つ

絞る仕組みを idp に置くか、アプリに置くかを決める必要があった。

## 決定

1. 機械に何をしてよいかは、**呼ばれる側のアプリが `client_id` ごとの許可簿で決める**。idp は今のまま `scope` を載せず、宛名だけを刻む。
2. 許可簿は「使ってよい操作」の一覧で、**書いていない操作は通さない（既定は拒否）**。acts_as 型では、利用者のロールと許可簿の**両方**を満たすときだけ通す。
3. 操作の名前（例: `issues:create`）はアプリごとに決める。このテンプレートには、許可簿の仕組みと書き方だけを入れる（#721）。
4. 宛名の確かめは許可簿の前提とする。`MACHINE_AUDIENCE` が空なら、機械の口は閉じる（#718）。

## 理由

比べた案:

| 案 | 中身 | アプリを足すときの手間 | 騙されたときに届く範囲 | 止め方 |
|---|---|---|---|---|
| A | idp に宛名ごとの scope を登録し、トークンに載せる | idp の登録とアプリの両方を直す | scope の分だけ | idp で scope を外す |
| **B（採用）** | idp は今のまま。アプリが許可簿で決める | アプリだけ | 許可簿の分だけ | アプリの設定を直す。全部止めるなら idp でクライアントを止める |
| C | idp は粗い区分、アプリが細かい判定 | 両方 | 許可簿の分だけ | 両方 |

- 操作の単位はアプリの作りそのもので、アプリを直すたびに変わる。それを idp に写すと、2 か所を同時に揃える運用になる（2026-09-02 に scope を足さないと決めた理由と同じ）。
- 絞れる範囲は A でも B でも同じ。判定するのはどのみちアプリなので、B は「どこに書くか」の違いでしかない。
- nolumiadeck の許可簿と blobshare のバケットという、すでに動いている手本がある。
- C は A と B の手間を両方負う割に、B より狭く絞れるわけではない。

## 影響

- 機械の口を持つアプリは、それぞれ許可簿を持つ（#722）。deploy-repo の `MACHINE_CLIENTS` の各行に、使ってよい操作の欄が増える。
- 「この機械はどのアプリで何ができるか」は、idp を見ても分からない。棚卸しの表（#716）で一覧にする。
- 受け側が増えたら、idp の宛名の登録とアプリの許可簿の両方が要る（宛名は idp、操作はアプリ）。
- このテンプレートは今、機械として呼ばれる口を持っていない（`MACHINE_CLIENT_ID` は呼ぶ側の設定）。#721 で、許可簿つきの機械の口を足すところから始める。
