# ADR-0076: ローカルの認証とトークン

- 日付: 2026-10-30
- 状態: 承認（§8 の「ログアウトは Cookie を消すだけ」と §4 の「発行済みトークンを 1 本ずつ失効させる手段は無い」は ADR-0091 で置き換え）
- 統合した ADR: 旧 ADR-0002（§1）・旧 ADR-0003（§2）・旧 ADR-0026（§3）・旧 ADR-0028（§4）・旧 ADR-0041（§5）・旧 ADR-0038（§6）・旧 ADR-0039（§7）・旧 ADR-0057（§8）・旧 ADR-0058（§9）・旧 ADR-0060（§10）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

この雛形は「IdP が無くても動くアプリの出発点」で、自前の認証（パスワード・TOTP・パスキー）を持つ。
そこへ IdP との SSO（ADR-0077）が後から足され、**入口が 2 つ**（ローカル / SSO）になった。
この ADR は、ローカルの入口そのもの、入口どうしの関係、発行するトークン（JWT の access / refresh）の
置き場所・検証・止め方、そしてローカルの入口を総当たりや乗っ取りから守る仕組みをまとめる。

参照元の photonest は JWT に加えて TOTP・パスキー・Google OAuth・サービスアカウント認証を持っていた。
2026-10-21 の脆弱性確認（task #574・#575・#577）で見つかった穴は §8〜§10 で塞いだ。

## 決定

### §1 認証の基本の範囲

テンプレートの「基本的な認証」にどこまで含めるかを決める。

1. JWT（access / refresh）によるログイン・ログアウト。
2. ユーザー／ロール／権限（scope による認可。中身は ADR-0078）。
3. パスワード変更・パスワードリセット（`email_sender` コンテキスト + SMTP 設定）。
4. 二要素認証（TOTP）・パスキーは §2、外部 IdP との SSO は ADR-0077 で取り込んだ。
   機械（サービスアカウント）の口は ADR-0082 で扱う。

### §2 二要素認証とパスキーは account_security コンテキストに置く

`bounded_contexts/account_security/` に二要素認証（TOTP）とパスキー（WebAuthn）をまとめて置く。
移植元（photonest）の作りは次の 3 点で変える。

1. TOTP 共有鍵は `users` の列ではなく `totp_secrets` テーブル（1 ユーザー 1 行）。
   `confirmed_at` を持ち、**確認できるまで有効にしない**（2 段階登録）。
2. WebAuthn チャレンジは `webauthn_challenges` テーブルに置く（既定の寿命 300 秒）。クライアントへは
   `challenge_id` だけを返し、消費は**削除の成否（1 行消せたか）**で決める。
   登録の完了ではチャレンジの持ち主と現在の利用者の一致も確認する。
3. `TotpAuthenticator` / `WebAuthnRelyingParty` を Domain 層の Protocol として定義し、
   `pyotp` / `webauthn` は Infrastructure の実装に閉じ込める。

パスキーは `residentKey: required` / `userVerification: required` で登録させる。

### §3 認証の強度は入口ごとに決まる。ローカルの入口は丸ごと閉じられる

入口はローカル（パスワード + TOTP、またはパスキー。`LoginService` が検証する）と SSO（IdP が認証し、
こちらは ID トークンを検証するだけ）の 2 つ。自前 idp は ID トークンへ `acr` を常に載せ、予約語
`urn:assay:ac:mfa` / `urn:assay:ac:single` を解釈する（assay の ADR-0043）ので、要求が効いたかをこちらで確かめられる。

1. **認証の強度は入口ごとに決まる**ものとして受け入れ、入口を跨いだ強制はしない。
   SSO で入ってきた利用者にローカルの TOTP を追加で要求しない。代わりに、**どの入口で入ったかを
   監査ログの `reason` に残す**（`method=password` / `method=passkey` / `method=sso`）。
   強い認証を求めるときは、**認可要求の `acr_values` で IdP に要求する**（`OIDC_ACR_VALUES`。既定は空＝要求しない）。
   **要求したら確かめる** —— ID トークンの `acr` が要求のいずれかと一致しなければ `sso_acr_not_satisfied` で断る。
   **`acr` が返ってこない場合も断る。** `OIDC_ACR_VALUES` の値が discovery の `acr_values_supported` に無ければ
   **起動時のログで警告する**。
2. **ローカルの入口を丸ごと閉じられる。** `LOCAL_LOGIN_ENABLED`（既定 `true`）。
   `false` のとき `POST /api/auth/login`・`POST /api/auth/passkey/login`・`POST /api/auth/forgot-password`・
   `POST /api/auth/reset-password` は 403 `local_login_disabled` を返し、ログイン画面はパスワード欄と
   パスキーのボタンを出さない（`GET /api/auth/sso/provider` の応答に載せる）。
3. **ローカルの資格情報を作れるのは、ローカルの入口が開いているときだけ。**
   `LOCAL_LOGIN_ENABLED=false` のとき、パスキー登録・TOTP 有効化・パスワード変更は 403 `local_login_disabled`。
   既に登録済みの資格情報は消さない。
4. **画面では 2 つのパスキーを混ぜない。** アカウント設定の「パスキー」はこのアプリのもの（RP ID は
   アプリのドメイン）だけを指し、その旨を画面の文言に書く。IdP 側のパスキー（RP ID は `identity.nolumia.com`）は
   SSO ボタン（`OIDC_DISPLAY_NAME`）の向こう側にあり、**こちらからは一覧も削除もしない**。

### §4 トークンは httpOnly Cookie だけに置き、応答本文で配らない

**SPA はトークンを持たない。** access / refresh とも httpOnly Cookie で運ぶ。

1. **`localStorage` にトークンを置かない。** ログイン済みかどうかは `GET /api/auth/me` の成否で決める。
2. **refresh トークンも httpOnly Cookie**（`SameSite=Lax`、経路は `/api/auth/refresh` に絞る）。
   `POST /api/auth/refresh` は本文にトークンを取らない。
3. **トークンを応答本文で配らない。** ログイン・更新・SSO の引き換えは Cookie を載せるだけにする
   （`TokenResponse` に `access_token` / `refresh_token` は無い。`SsoSessionResponse` は `redirect_to` だけ）。
4. **API は `Authorization` ヘッダーも受け付け続ける。** Cookie が無ければヘッダーを見る、の順。
   既にトークンを持っている呼び出し元（他アプリ・CI）のため。
5. **CSRF は `SameSite=Lax` + 二重送信トークン。** 更新系（POST / PUT / PATCH / DELETE）にだけ必須とし、読み取りには求めない。

### §5 アクセストークンは DB を引かずに検証する（寿命 5 分）

1. **アクセストークンの検証は署名とクレームだけで行う。** `TokenService.verify_access_token_with_reason` と
   `get_current_principal` は DB を引かない。principal の材料（`sub` / `email` / `username` / `scope` /
   `active_role`、テナントの `tenant`（ADR-0079 §2 決定 2）、`auth_time`（§10））は**すべてトークンに載せる**。
   ⚠ **載せ忘れた項目は、その経路でだけ静かに空になる。** 項目を足すときはクレームにも足す。
2. **寿命は 5 分**（`ACCESS_TOKEN_EXPIRES_SECONDS`、既定 300 秒）。
   ⚠ **この値が「止めたら効くまで」の上限時間そのものになる。** 縮めたいときに触るのはこの設定で、管理画面の項目にもその旨を書いてある。
3. ⚠ **止める判定は更新の 1 点に集約する。** `verify_refresh_token` は DB を引き続ける（`is_active`、IdP からの停止の記録
   （ADR-0077 §3）、パスワード変更の区切り（§8）、止めたテナント（ADR-0079 §2 決定 6））。
   ここが引き締めているから、アクセス側を緩められる。⚠ **ここを緩めると、寿命による上限そのものが消える。**
4. ⚠ **新しいトークンを出す経路は、必ず DB を引く。** 更新（`/api/auth/refresh`）に加え、アクセストークン 1 枚から
   新しいトークンを出せる経路 —— ロールの切り替え（`POST /api/auth/switch-role`）も `get_current_session` が失効を確かめる。
   ⚠ 塞がないと、止められた利用者が 5 分ごとに切り替えを繰り返していつまでも入っていられる。
   `test_a_stopped_session_cannot_mint_new_tokens_by_switching_roles` が固定している。
5. （欠番）
6. ⚠ **資格情報を作り替える経路も DB を引く。** 二要素認証やパスキーの登録・解除は「新しい入り口を作る」操作で、
   `get_settled_principal` が出し直しの経路と**同じ関門**を通す。
   `test_a_stopped_session_cannot_register_a_new_way_in` が固定している。

   | 経路 | DB |
   |---|---|
   | 読むだけ | 引かない |
   | **新しいトークンを出す**（更新・ロールの切り替え） | 引く |
   | **新しい入り口を作る**（二要素・パスキー） | 引く |

   ⚠ **雛形から作ったアプリは、この 3 つ目を必ず見ること。** アプリごとに「入り口を増やす操作」は違う
   （一時パスワードの印、プロジェクトの割り当て、など）。
7. 利用者の行が要る経路は今までどおり引く。`get_current_user` は 1 件引く。⚠ **これは認可の判定ではない** ——
   行そのものを使う経路（プロフィールの更新、連携の状態など）が自分の都合で引いているだけである。

### §6 「ローカルのパスワードが無い」は NULL で表す

**`users.password_hash` は NULL 許容で、`NULL` は「ローカル認証を持たない」を意味する。**
判定は `User.has_local_password` に集める。誰も知らないランダム値で埋めない。

1. **SSO で作る利用者には NULL を入れる。**
2. **パスワードでのログインを断る**（照合する相手が無い）。
3. **パスワード変更を断る**（理由は `invalid_current_password` に揃える。持っていないことを教えると、入り口の有無を外から数えられる）。
4. ⚠ **パスワードリセットを発行しない・通さない。** 応答は宛先が無いときと同じにする。
5. **`/api/auth/me` に `has_password` を載せ、画面は偽なら変更フォームを出さない。**
6. **持たせるのは、管理者が明示的に行ったときだけ** —— 管理者がパスワードを設定する
   （`PUT /api/admin/users/{id}` の `password`）か、招待のリンクで本人に最初のパスワードを決めさせる
   （`password_reset_tokens.purpose = invitation`。ADR-0079 §5 決定 1）。どちらも監査に残る操作である。

### §7 この雛形はローカル口座を意図して持ち、入れる手段を数える

認証系は IdP（assay）側とこのアプリの `account_security` 側の 2 つある（idp の ADR-0049 G1）。
片付け方は「1. SSO 専用にする」か「2. ローカル口座を意図して持つ」の 2 通りで、**この雛形は 2 を選ぶ。**

1. **「入れる手段」を数えて画面に出す。** `GET /api/admin/users` の `entrances`（パスワード / 二要素認証 /
   パスキーの本数 / 結び付いている IdP）。材料は**それぞれのコンテキストに聞く**（パスワードは `users` の列、
   TOTP とパスキーは `account_security`、結び付きは `identity_federation`）。
2. **利用者ごとに「ローカル認証を持たない」を表せる**（§6 の `password_hash`）。アプリ全体の栓は
   `LOCAL_LOGIN_ENABLED`（§3 決定 2）。**この 2 つは別物**で、前者は行ごと、後者はアプリ全体である。
3. ⚠ **この雛形から作ったアプリは、作った時点で 1 か 2 のどちらかを自分の ADR に書く。**
   書いていない状態を「まだ決めていない」として残さない。

### §8 パスワードを変えたら、それより前に始まったログインを終わらせる

更新トークンはサーバーに控えが無いので、何もしなければ、パスワードを変えても前に出した更新トークンが
寿命（既定 14 日）いっぱい使える。

1. 表 `user_session_boundaries`（1 人 1 行・`valid_from`）を持つ。**この時刻より前に出したトークンでは、
   更新も出し直し（ロールの切り替え・資格情報を作り替える口の関門）もさせない。** 判定は IdP からの停止
   （ADR-0077 §3）と同じ `_session_revoked` の 1 か所に置く。`iat` と比べるため、区切りは秒に切り捨てる。
2. 本人の変更・再設定・管理者の付け直しで、`User.end_sessions()` が今の時刻を入れる。
3. 本人が変えたときは、そのセッションだけ新しいトークンを出し直して続ける（ロールと入り口は引き継ぐ）。

### §9 ログインの失敗を宛名ごとに数え、上限を超えたらしばらく断る

deck の ADR-0044 の作りをそのまま持ってきた。

1. 数える単位は**送られてきた宛名**（メールアドレス。大文字小文字と前後の空白は揃える）。実在するアカウントとは結ばない。
2. 窓（`LOGIN_FAILURE_WINDOW_SECONDS`、既定 900 秒）の中で上限（`LOGIN_MAX_FAILURES`、既定 5 回）まで失敗したら、
   `LOGIN_LOCK_SECONDS`（既定 900 秒）のあいだ **429 `too_many_attempts`** で断る（`Retry-After` と
   `retry_after_seconds` で待ち時間を返す）。正しいパスワードでも断る。
3. パスワードの間違い・二要素のコードの間違いは同じ数え上げに入れる。正しく入れたら忘れる。
4. 再設定メールの要求は別の籠で、**成功も数える**（成功しても相手にメールが届くため）。
5. 控えは DB の `login_attempts` に置き、自前の短いセッションで commit する。断り始めたことは監査ログに `login.locked` で残す。
6. 未知の宛名でも、ダミーのハッシュと照合して応答時間を揃える。

### §10 パスキーの追加・削除とメールの変更は、入り直したばかりのときだけ

持ち主の判断（2026-10-21）で、**「直近に実際にサインインしたこと」**を求める。

1. トークンに `auth_time`（最後に**実際に**サインインした時刻）を載せる。入口（パスワード・パスキー・SSO・パスワードの変更）で
   今の時刻にし、**更新・ロールの切り替えでは引き継いで新しくしない**（`SessionCarryOver`）。
   `auth_time` を持たない古いトークンは「ずっと前」とみなす。
2. パスキーの登録の開始・完了・削除と、メールアドレスの変更（表示名だけなら求めない）は、`auth_time` から
   `RECENT_SIGN_IN_SECONDS`（既定 600 秒）以内でなければ 403 `reauthentication_required`。
3. 画面は断られたら知らせてログイン画面へ送る（行き先にいまの画面を持たせ、入り直すと戻る。ADR-0077 §8）。

## 理由

### §1

- パスワードリセットは大半のアプリで要るので、メール送信基盤（`email_sender`）ごと含めたほうが実用性が高い。

### §2

- **共有鍵を別テーブルにする**: 認可の中心である `User` にコンテキスト固有の列を足さずに済む。利用者の削除には `ON DELETE CASCADE` で追随する。
- **2 段階登録**: 1 段階で有効化すると、QR の読み取りに失敗した利用者が自分のアカウントから締め出される。
- **チャレンジを DB に置く**: Gunicorn は既定で複数ワーカー（`--workers=2`）なので、プロセス内の `dict` ではワーカーを
  またいだ瞬間に検証が落ちる。Redis を必須依存にせずに済み、チャレンジは短命で件数も少ない。発行のたびに期限切れを
  掃除するので定期ジョブも要らない。消費を「読んでから消す」にしないのは、同じ assertion を同時に 2 本送られると
  両方が読み終えて 2 本ともトークンを得られるため。
- **`residentKey: required` / `userVerification: required`**: ログインはユーザー名を入力しない経路だけなので、
  discoverable でない資格情報は後から選べない。パスキーで入るとパスワードも TOTP も通らないため、生体・PIN の確認を
  必須にしないと、ロックされていない端末を拾っただけで入れる。
- **ライブラリの型を境界の外へ出さない**: `webauthn` は破壊的変更のある依存（1.x → 3.x で検証 API の形が変わった）。
  追随はアダプタ 1 ファイルで済み、試験も偽の実装へ差し替えられる。

### §3

- **要求したら確かめる（さもなければ要求しない）。** `acr_values` を送って結果を見ないと、IdP 側のポリシーの綴り違い 1 つで
  「MFA を要求したつもりで単要素のログインを受け取る」状態になり、気付けない。既定は空なので、**設定した派生だけが
  fail closed になる**。
- **入口を跨いだ強制はしない。** SSO 経路で TOTP を聞くと、IdP で二要素を済ませた利用者に二重で求めることになる。
  `amr`（RFC 8176）で場合分けする案は、**`amr` が強度を表さない**（`fed` の先で何が使われたかは IdP も知らない）ので採らない。
  判断は IdP の認証ポリシーという既にある仕組みに 1 か所で集める。
- **入口を記録する**のは、IdP 側でアカウントを止めた後に「まだ入れている」ことに気付けるようにするため。値そのもの（メールアドレス・トークン）は載せない（ADR-0075 §1）。
- **閉じるのは「設定」で、「削除」ではない。** テンプレートは IdP を持たない小さなアプリも作る。既定 `true` なら今までどおりのアプリは何も変えなくてよい。
- **合鍵を作らせない（決定 3）。** 決定 2 だけでは、閉じた後に SSO で入った利用者がパスキーを登録でき、設定を戻した瞬間にその鍵が効く。
  **「入口が閉じている＝その入口の鍵は増えない」**を規則にすると、運用側は「閉じた」以上のことを考えなくてよい。
  登録済みのものを消さないのは、開け直したときに全員が締め出されるため。
- **パスキーを画面で分ける。** RP ID が違うので、このアプリから IdP 側のパスキーを触る方法は無い。消せないものを一覧に出さない。

### §4

- **応答本文に載せたままでは httpOnly が意味を持たない。** Cookie は自動で送られるので、XSS は `POST /api/auth/refresh` を
  叩くだけで新しい access トークンを本文から読める。持ち出せなくするには本文から消すところまで要る。
- **ヘッダーを塞ぐ必要は無い。** XSS が奪うのは「保管された値」で、「ヘッダーを送る能力」ではない。危ないのは JS から読める
  場所にトークンを置くことである。Swagger UI は同一オリジンなので Cookie がそのまま付き、curl も CI も Cookie を扱える。
  **受け付ける口を減らすより、配る場所を減らす**。
- **refresh を先に守る。** access は短命だが refresh は長い。発行済みトークンを 1 本ずつ失効させる手段は無い
  （ログアウトでの失効は未対応）ので、持ち出させないことが主な防御になる。
- **`SameSite=Lax` だけでは足りない。** 同一サイト扱いになる相手（サブドメインを取られた場合など）は止めない。
  読み取りに求めないのは、読み取りの CSRF は結果を攻撃者が読めず、守るものが無いため。

### §5

**認可に要る値は、発行の時点で確定している。** 毎回引き直していたのは「発行後に状況が変わったかもしれない」ためだが、
それは**更新のたびに確かめれば足り**、遅れの上限は 5 分になる。OAuth 2.0 / OpenID Connect が前提にしている形でもある
（idp の ADR-0049 I7「アクセストークンを短命にする（受け口が落ちていたときの上限時間になる）」）。
毎回引くと、`users` の 1 件・ロールと権限の遅延読み込み（ロール 1 つにつき 1 本）・失効の照会が認証済みの全リクエストに掛かっていた。

| 採らなかった案 | 理由 |
|---|---|
| 短い TTL のプロセス内キャッシュ | ⚠ ワーカーごとに別のキャッシュを持つので、効くまでの時間がばらつき、説明できない遅れが残る |
| 失効だけを 1 本の軽いクエリにする | リクエストごとに DB を引くこと自体が残る |
| Redis などの共有キャッシュ | 往復は残り、依存が 1 つ増える（この雛形は Redis を前提にしない） |

### §6

- **「無い」は値である。** ランダム値は代用で、代用だと分かるのは書いた人だけになる。列を緩めれば画面も監査も同じ事実を読める。
- **リセットを塞ぐのがいちばんの中身である。** リセットは「本人がメールを受け取れる」ことしか確かめない。SSO でしか入れない
  と決めた利用者に対して、それは誰も操作していないのに認証手段を 1 つ増やす操作になる。持たせるなら管理者が明示的に行う。

| 採らなかった案 | 理由 |
|---|---|
| `credentials`（種別 + 値）テーブルへ出す（idp の ADR-0049 I4 の第 2 案） | 認証の口すべてを書き換える話になる。表したいのは「無い」の 1 点 |
| `LOCAL_LOGIN_ENABLED` で足りるとする | アプリ全体の栓で、「この利用者には無い」は表せない |

### §7

- **雛形は 1 を選べない。** 用途が「IdP が無くても動くアプリの出発点」で、SSO は後から足せる追加の入り口という位置づけ（§3）。
  ⚠ **派生アプリが 1 を選ぶのは自由**で、そのための栓（`LOCAL_LOGIN_ENABLED=false`）がある。
- **2 を選んだ宿題は棚卸し。** 多要素の強制・パスキーの解除は別の認証系どうしなので、それぞれで操作するしかない。
  だが「入れる手段の一覧」は単に無かっただけで、作れば埋まる。
- **数えるのは「開いている口」であって「使われた口」ではない。** 監査ログの入口の記録（§3 決定 1）は事後の記録で、いま何本開いているかは答えない。
- 1 人ずつ引く口（`GET /api/admin/users/{id}/entrances`）は、全員分を並べる棚卸しで画面が利用者の数だけ問い合わせるので採らない。
  IdP 側の多要素は混ぜられない（IdP の管理 API への依存が増える）。⚠ **混ぜられないことが「認証系が 2 つある」の実体**なので、そのまま見せる。

### §8

- 時刻 1 つで「それより前は全部無効」が言える。`users` の列にしないのは、据え付けの移行（`0002`）が `User` のモデルで
  `users` を書くため（列を足すと、それを足す移行より前の段で落ちる）。
- セッションごとの控え（deck の `auth_sessions`）を持てば 1 本ずつ終わらせられるが、表と書き込みが増え、雛形には重い。
- 区切りを切り上げると、区切った直後に同じ秒で出し直した自分のトークンまで断る。切り捨てで通る古いトークンは 1 秒に満たない幅である。
- 署名鍵を利用者ごとに混ぜる案は、検証のたびに DB を引くことになり §5 と相容れない。

### §9

- 実在するアカウントだけを数えると、断られるかどうかで存在が分かる。
- プロセスのメモリではなく DB に置くのは、Gunicorn の複数ワーカー（ワーカーの数だけ試せる）のため。
- 失敗の記録は 401 と一緒に返る（例外で抜ける）ので、リクエストの DB セッションに書くと rollback で消える。だから自前のセッションで commit する。
- 401 に紛れさせないのは、断られていると分からないと正しいパスワードでも弾かれ続け、「忘れた」と誤解して再設定へ流れるため。
- 接続元 IP で数える案は採らない。前段（Cloudflare・nginx）の後ろでは同じ IP に見える人が多く、攻撃側は IP を替えられる。

### §10

- 「今のパスワードを入れる」形は、パスワードを持たない（SSO だけの）利用者がパスキーもメールも変えられなくなる。「入り直したばかり」なら全員に効く。
- 判定はトークンの中だけで済み、DB を引かない（§5）。
- 更新で新しくすると、盗んだ更新トークンを 1 回使うだけで「入り直したばかり」になれる。
- 二要素のコードを求める案は、二要素を設定していない人に効かない。

## 影響

### §1

- メール送信は SMTP 設定（システム設定画面で管理）が前提。未設定時はパスワードリセット API がエラーコードを返す。

### §2

- 依存: `pyotp` / `webauthn` / `qrcode`。QR は SVG で描くので Pillow は不要。マイグレーション `0003_account_security`（3 テーブル）。
- パスキーでログインした場合は TOTP を求めない（所持と生体・PIN の確認を両方必須にしているため）。
- `residentKey: required` を満たせない古い認証器では登録できない。使えないパスキーが出来るより、登録時点で失敗するほうを選ぶ。
- ⚠ `WEBAUTHN_RP_ID` は登録済みパスキーの結び付け先。運用開始後に変えると既存のパスキーはすべて無効になる。
  ドメイン名のみ指定可（IP アドレス不可）なので、開発時は `localhost` で開く。

### §3

- 設定キー `LOCAL_LOGIN_ENABLED` / `OIDC_ACR_VALUES`（設定管理の 3 ファイルすべてに載る）。
- ⚠ **締め出しの経路がある。** `LOCAL_LOGIN_ENABLED=false` で IdP が落ちる、あるいは最後の管理者が IdP 側で止まると、誰も入れなくなる。
  復旧は**保存を消す**（`scripts/unset_setting.py LOCAL_LOGIN_ENABLED`）。DB の設定が環境変数より強い（ADR-0074 §1）ので、
  環境変数では戻らない。手順は `docs/OPERATIONS.md`。最後の管理者を失う操作を防ぐ条件（T4）にも「SSO でしか入れない管理者」を数える必要がある。
- ⚠ **`OIDC_ACR_VALUES` に書ける値は連携先が決める。** 自前 idp なら `urn:assay:ac:mfa` / `urn:assay:ac:single` の 2 つ。
  **予約語を持たない IdP へつなぐ派生では空のままにする** —— 設定すると `acr` が返らず全員が `sso_acr_not_satisfied` で断られる。
- `amr` は強度の判断に使わない。監査ログと画面表示に限る。
- 監査ログの `reason` に入口の語彙（`method=…`）が入る。
- §2 の TOTP・パスキーには「ローカルの入口が閉じているときは登録も止まる」という条件が乗る。

### §4

- ⚠ API を直接叩いて本文からトークンを取り出す呼び出し元は動かない
  （`requests.post(...).json()["access_token"]` の形）。`requests.Session` / `httpx.Client` で Set-Cookie を保持して Cookie で叩く。
  派生アプリは fork なので、取り込むまでは動き続ける。**取り込む前に、自分の機械の呼び出し元を数えておくこと。**
  画面を足している派生では `api.ts` の取り込みが手作業になる。
- Swagger UI の Authorize ボタンは使わない（ブラウザでログインしていれば Cookie が付く）。手元の `curl` は `-c` / `-b` で Cookie を扱う（`docs/OPERATIONS.md`）。
- ログアウトは Cookie を落とすだけで、サーバー側の JWT は寿命まで有効なまま。この決定で良くなるのは「持ち出されなくなる」ことで、「止められる」ことではない（止め方は §5・§8）。
- Android アプリが assay のトークンで API を叩く口は ADR-0081 §1。このアプリのトークンを本文で配らない点は変わらない。

### §5

- ⚠ **停止が効くまで最大 5 分かかる。** ローカルの無効化も IdP からの停止も同じ。
  `test_the_access_token_outlives_the_stop_only_until_it_expires` が**この緩さを明示的に固定している**（消すと、緩んだことに誰も気付けなくなる）。
- ⚠ ロールの切り替えの積集合（ADR-0078 §1）は発行の時点で取るだけなので、外されたロールの権限も最大 5 分残る。発行済みのトークンは切り詰められない。
- 更新の回数は 3 倍（15 分 → 5 分）。DB の仕事は消えずに更新へ移る（5 分に 1 回）。
- `TokenService.session_is_revoked` は出し直しの経路だけが呼ぶ。⚠ **普段の検証では呼ばない。**

### §6

- ⚠ 移行 `0008_password_is_optional` は、どの行がランダム値かを**利用者の行と IdP との結び付きが 60 秒以内に作られたか**で判断して落とした
  （`provision` だけが両方を同じトランザクションで作る）。⚠ **取り違えても入れなくなるだけで、増えることはない**
  （落としすぎた利用者は管理者にパスワードを設定してもらう＝気付ける失敗）。非対称なので落とす側へ倒した。
- ⚠ **知らない DB 方言では移行が何もしない**（SQLite / PostgreSQL / MySQL / MariaDB を見る）。秒差を出す式が方言ごとに違うため。手当ては `docs/OPERATIONS.md`。
- アプリの外から `users` を作るコードは `password_hash` を省略できる。省略は「ローカル認証なし」の意味なので、持たせたい行では明示する。
- IdP との結び付きを外すとき、パスワードの再設定へ誘導して入り口を生やさない（ADR-0077 §5）。

### §7

- `GET /api/admin/users` の応答（一覧・作成・更新）に `entrances` があり、画面（S8 ユーザー管理）に「入れる手段」の列がある。
  表示だけで、ここからは取り上げられない（取り上げ方はそれぞれの口の側にある）。
- ⚠ **ローカルのログインへの多要素の強制はまだ無い。** IdP 側で `require_mfa` を掛けても、こちらのローカルログインは素通しである（未対応）。
- 派生アプリは自分の ADR で 1 / 2 を宣言する。2 を選ぶなら、この §7 を写すのが早い。

### §8

- 手元のアクセストークンは寿命（既定 5 分）まで通る（§5 の引き受けた緩さと同じ）。
- パスワードを変えると、本人の他の端末・タブも次の更新でサインアウトする。
- ログアウトは Cookie を消すだけで、区切りは入れない（入れると全端末のサインアウトになる）。
- 既存の利用者は行が無い（区切り無し）。

### §9

- 宛名を知っている人は、わざと間違えてその人をしばらく締め出せる（妨害）。上限と断る長さは管理画面の設定で変えられる。
  `LOGIN_MAX_FAILURES=0` で数えない（⚠ 本番で 0 にしない）。
- パスキーと SSO のログインは対象外（パスワードもコードも無いので総当たりの的にならない）。
- テナントがあっても宛名はメールアドレスのまま数える（ADR-0079 §4）。

### §10

- サインインから 10 分を過ぎてパスキーを足す・メールを替える人は、入り直しが 1 回要る。
- SSO の入り直しは IdP のセッションが残っていればそのまま通る（IdP 側に入り直しを強いるのは別の話）。
- 二要素認証の設定の開始は対象にしない（パスワードを持つ人だけの口で、解除は今のコードを求める）。
