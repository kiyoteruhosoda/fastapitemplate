# ADR-0010: DB のポートをホストへ公開せず、保守もコンテナ内で完結させる

- 日付: 2026-07-30
- 状態: 承認

## 文脈

`docker-compose.yml` の `db` サービスは、保守用にホストへポートを公開していた。

```yaml
ports:
  - "${DB_BIND_ADDR:-127.0.0.1}:${DB_HOST_PORT:-3307}:3306"
```

既定はループバック（`127.0.0.1`）に絞ってあり、`DB_BIND_ADDR` を書き換えたときだけ
LAN へ開く形だったが、この公開はアプリの動作には一切必要ない。`web` は Docker
ネットワーク内部の `db:3306` へ接続する（`DATABASE_URI` の host は `db`）。
公開ポートの用途は「ホストから `mariadb` クライアントや GUI ツールでつなぐ」保守作業だけで、
それは `docker compose exec db mariadb ...` で代替できる。

一方、公開し続けることには次のコストがある。

- **ホスト側のポートを 1 つ占有する。** stg と prod を同一ホストに並べる運用では
  環境ごとに別の番号（3307 / 3308）を割り当てる必要があり、`deploy.sh` が生成する
  `.env` にも環境固有の値として書き込んでいた。ポート番号は本来
  「コンテナ名・ネットワーク名を環境ごとに分ける」で足りている分離軸ではない。
- **既定の資格情報が開発向けである。** `MARIADB_ROOT_PASSWORD` 等は `.env` 未設定でも
  DB が初期化されるよう既定値を持つ（開発の利便性を優先した設計）。ポートが開いていると、
  `.env` の上書きを忘れた環境で「既定パスワードのまま到達可能な DB」が生まれる。
  ループバック限定でも、ホストに入れる者・ホスト上の他コンテナからは到達できる。
- `DB_BIND_ADDR` という「書き換えると外部公開になる」設定キーが存在すること自体が、
  誤って開ける経路になる。

## 決定

`db` サービスから `ports` を外し、`expose: ["3306"]` だけにする。DB へ到達できるのは
同じ Docker ネットワーク内のコンテナのみとし、保守作業も `docker compose exec` で
コンテナ内から行う。設定キー `DB_BIND_ADDR` / `DB_HOST_PORT` は廃止する。

## 理由

- **アプリの動作に必要な公開ポートは nginx の 1 つだけになる。** 公開面が小さいほど、
  外部リバースプロキシの前段だけを見れば到達経路を把握できる。
- **保守作業に機能低下が無い。** `docker compose exec db mariadb ...` で対話シェル・
  SQL ファイルの流し込み・`mariadb-dump` はすべて実行できる（手順は `OPERATIONS.md`）。
  ホスト側にクライアントを入れる必要も無くなる。
- **環境ごとに調整する値が 1 つ減る。** stg / prod の分離はコンテナ名
  （`DB_CONTAINER_NAME`）とネットワーク名（`DOCKER_NETWORK_NAME`）で足りている。
  `deploy.sh` が生成する `.env` から `DB_HOST_PORT` を落とせる。
- 捨てた代替案:
  - **ループバック限定のまま残す（従来）** — 到達経路が残るうえ、既定の資格情報が
    開発向けである点と組み合わさると「開けたまま忘れる」事故が起きうる。
  - **`profiles` で保守時だけ公開する** — compose の `profiles` はサービス単位であり、
    同じサービスの `ports` だけを出し入れできない。`db` を二重定義することになる。
  - **オーバーライド用の `docker-compose.db-port.yml` を同梱する** — 「必要なときだけ
    足す」形にはなるが、`deploy.sh` は compose ファイルをイメージ内のコピーへ同期する
    設計（配置先での手編集を前提にしない）ため、常設ファイルを増やすと同期対象と
    そうでないファイルが混在する。恒久的に必要になった時点で追加すればよい。

## 影響

- **ホストから直接 DB へつなぐ運用は使えなくなる。** GUI クライアントを一時的に
  つなぎたい場合は、その場限りのポートフォワード用コンテナを立てる
  （手順は `OPERATIONS.md`「DB へホストのツールから一時的につなぎたいとき」）。
  作業が終わったらコンテナを消せば公開ポートも消える。
- 既にデプロイ済みの環境の `.env` には `DB_HOST_PORT` / `DB_BIND_ADDR` の行が
  残っているが、compose が参照しなくなるため**無視される**（`deploy.sh` は既存の
  `.env` を書き換えないので、行が残っていてもデプロイは通る）。次のデプロイで
  ホスト側の 3307 / 3308 は解放される。
- `docker compose exec` を使えるのはホストにログインできる者だけになるため、
  DB への到達権限がホストへのログイン権限と一致する（従来は「ホストに入れる者」と
  「ホスト上の他コンテナ」の両方が到達できた）。
