# ADR-0009: CI は main への push と pull_request でだけ走らせる

- 日付: 2026-07-30
- 状態: 承認

## 文脈

ADR-0006 で必須化した 8 つの品質ゲートは、`push`（`branches: ["**"]`）と `pull_request` の
両方をトリガーにしていた。この組み合わせでは、**PR のあるブランチへ push すると同じコミットが
2 回検証される**。`push` 由来の実行と `pull_request` 由来の実行が別々に立ち上がり、
ジョブが 2 つ（Backend / Frontend）あるためチェックは 4 個並ぶ。内容は完全に同一で、
CI 時間とレビュー画面のノイズがそのまま 2 倍になっていた。

あわせて、連続して push したときに古い実行がキャンセルされず、既に不要になったコミットの
検証が最後まで走り続けていた。

## 決定

`push` の対象を `main` だけに絞り、フィーチャーブランチは `pull_request` 側だけで検証する。
さらに `concurrency` を設定し、PR への連続 push では古い実行をキャンセルする
（`main` はキャンセルしない）。

## 理由

- **重複の原因はトリガーの重なりそのもの**なので、片方の対象を狭めるのが最も素直。
  `main` への push を残すのは、マージ後のコミットが緑であることを記録するため。
- **`concurrency` では重複は消せない。** `push` 由来と `pull_request` 由来の実行は
  `github.ref` もイベント名も異なり、同じグループに入れる自然なキーが無い。
  無理に同一グループへ入れると、どちらが生き残るかが実行順に依存して不定になる。
- `main` を `cancel-in-progress` の対象外にするのは、「どのコミットが緑だったか」を
  後から辿れるようにするため。PR 側は最新のコミットだけが意味を持つのでキャンセルする。
- 捨てた代替案:
  - **`pull_request` をやめて `push` だけにする** — フォークからの PR が検証されなくなる。
  - **`push` 側のジョブを `if` で条件分岐して PR のときスキップする** — ワークフローの
    実行自体は立ち上がるためチェック欄には残り、スキップ判定に PR の有無を知る API 呼び出しが
    必要になる。トリガーで解決できるものを条件式に持ち込む理由がない。

## 影響

- **PR を作っていないブランチへの push では CI が走らなくなった。** PR を作れば
  その時点で全ゲートが走る。手元では `make check` が CI と同じ順序・同じコマンドを流せる。
- タグ push の扱いは変わらない。`branches` を指定したワークフローはタグ push に一致しないため、
  従来の `tags-ignore: ["v*"]` は元々効いておらず、削除した（`v*` タグは `release.yml` の担当）。
- 必須ゲートの中身（ADR-0006 の 8 種）は変えていない。この ADR は ADR-0006 を置き換えるものではなく、
  その実行条件だけを決めるもの。
