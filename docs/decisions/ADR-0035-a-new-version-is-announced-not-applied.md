# ADR-0035: 新しい版は知らせるだけで、入れ替えるのは利用者が押したとき

- 日付: 2026-09-14
- 状態: 承認

## 文脈

この雛形のフロントエンドは SPA（React + Vite）で、Service Worker を持つ
（`vite-plugin-pwa`。オフラインでも殻が出る・PWA として入れられる）。

**デプロイしても、開きっぱなしの画面は古い版のまま動き続ける。** SPA は画面を
描き替えるだけでページを読み込み直さないので、直したはずの不具合がその端末では
そのまま見えている。スマートフォンにインストールした PWA は特にそうで、
**タブを閉じない限り何日でも古い版が動く。**

`vite-plugin-pwa` の `registerType` は 2 つある。

- `autoUpdate`（これまでの設定）: 新しい Service Worker を**黙って**有効にする。
  ⚠ **これは「画面が新しくなる」ことを意味しない。** 差し替わるのは次の読み込みからで、
  既に読み込まれた JavaScript には手が出せない。しかも新しい版が有効になった時点で
  古い資産はキャッシュから消えるため、遅れて読む部品を持つ画面では**古い画面が
  取りに行った先が無い**という壊れ方をしうる。
- `prompt`: 新しい版は**待機したまま**にし、入れ替えの合図を画面へ渡す。

## 決定

**`registerType: 'prompt'` にして、「新しい版があります [再読み込み]」を画面の下に
出す。押されたときだけ入れ替える。**

- 出すのは待機している版があるときだけ。**押されるまで消さない**
  （数秒で消えるトーストは使わない。見ていない間に出て消えると気付けない）。
- 押すと、待機している Service Worker に `SKIP_WAITING` を送り、制御が移ったら
  再読み込みする。
- ⚠ **合図が来ない場合の逃げ道を持つ。** その画面をまだ Service Worker が
  制御していない（登録された直後の初回訪問）と `controllerchange` が起きず、
  押しても何も起きない。2 秒待って、こちらからも読み直す。
- **更新の確認を自分で起こす。** ブラウザが Service Worker の更新を確認するのは
  ページ遷移のときで、**SPA の画面切り替えはページ遷移ではない**。30 分ごとと、
  タブが手前へ戻ったときに確認する（オフライン・取得中・直前に確認済みなら起こさない）。

## 理由

**黙って入れ替えるのは、画面が「今の版」であることを保証しないのに、保証したように
見える。** 利用者から見えるのは「直っていない」だけで、こちらからは「有効になった」
としか見えない。知らせを出せば、**古いまま使っているのか、押さなかったのかが
利用者の側で分かる。**

**入力中の画面を奪わない。** 自動で読み込み直す実装（`autoUpdate` ＋
`onNeedReload` で即 reload）は、フォームを書いている最中に入力を消しうる。
押す操作を挟めば、区切りのよいところで入れ替えられる。

**古い資産が消える壊れ方を避けられる。** `prompt` では新しい版が有効になるのは
押されたあとなので、それまで古い画面は古いキャッシュのまま完結している。

**確認を自分で起こさないと、知らせは出ない。** ここを入れないと `prompt` にした
意味がほぼ無く、「一度閉じて開き直した人にだけ届く知らせ」になる。

## 結果

- 画面の実装は `frontend/src/services/appUpdate.ts`（見張り）と
  `frontend/src/components/AppUpdatePrompt.tsx`（知らせ）に分かれている。
  部品は見張り方を引数で受け取る（Service Worker を登録する副作用を持たないので、
  試験では偽の見張りを渡せる）。
- 文言は `update.available` / `update.reload`（`en.json` / `ja.json`）。
- ⚠ **サーバー側の `Cache-Control` とセット。** `index.html` と `sw.js` に
  `no-cache` が付いていないと、そもそも新しい版に気付けない
  （`presentation/fastapi/routers/spa.py`。ハッシュ付きの `assets/` だけが長期キャッシュ）。
- ⚠ **知らせが出るまでの遅れは最大 30 分**（＋タブを手前に戻したとき）。即時に
  伝えたい種類の変更——互換性の無い API の入れ替えなど——は、この仕組みに頼らない。
- 実ブラウザでの通し確認（制御されているタブ・されていないタブの両方で、押すまで
  古く・押したら新しくなること）は、開発時に Playwright で行った。jsdom には
  Service Worker が無いので、CI の試験は「いつ確認しに行くか」「押したときに何を
  するか」までを見る。
