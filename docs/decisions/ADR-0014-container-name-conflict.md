# ADR-0014: デプロイ時のコンテナ名の衝突は「残骸だけ」を自動で消す

- 日付: 2026-07-30
- 状態: 廃止（ADR-0023 で置き換え）

## 文脈

`deploy.sh` は `docker compose down` でコンテナを落としてから `up` で作り直す。
ところが down が消すのは**このプロジェクトのラベル
（`com.docker.compose.project`）を持つコンテナだけ**で、同じ名前を握った
コンテナが他にいると、次の `up` が

```
Error response from daemon: Conflict. The container name
"/fastapitemplate-init-paths-1" is already in use by container "7754001e8a0e…".
```

で落ちる。名前を握る残骸が生まれる経路は 2 つある。

1. compose 管理外で作られた（プロジェクトラベルを持たない）コンテナ。
   過去の compose ファイルにしか無いサービス名のコンテナも、`--remove-orphans`
   を付けずに down すると残る。
2. 削除処理が途中で止まり、実体は無いのに名前だけ Docker が掴んでいる状態。

どちらも `docker compose ps` には映らない（実際の障害でも診断の `ps -a` は空だった）。
そのため「down は成功しているのに up が名前衝突で落ちる」という、ログだけでは
原因の見えないデプロイ失敗になる。

一方で「同じ名前を握っているコンテナを全部消す」わけにもいかない。stg と prod は
同一ホストで動く前提（ADR-0010）で、`.env` の `DB_CONTAINER_NAME` を書き損じれば
**稼働中の別環境**が名前の持ち主になりうる。

## 決定

`deploy.sh` は、このデプロイが作るコンテナ名を握っている相手を
`com.docker.compose.project` ラベルだけで判定し、**残骸に限って**自動削除する。

| 相手のラベル | 扱い |
|---|---|
| このプロジェクト / ラベル無し / `inspect` もできない | 残骸とみなし `docker rm -f` する |
| 別プロジェクト | 消さずにデプロイを中断し、名前の重複を運用者に知らせる |

## 理由

- **ラベルだけで判定する。** 稼働中かどうか・イメージが何かでは区別できない
  （残骸も動いていることがあり、別環境も止まっていることがある）。「誰の持ち物か」
  を答えられるのは compose のプロジェクトラベルだけ。
- **別プロジェクトは消さない。** 消せばデプロイは通るが、稼働中の stg を黙って
  落としうる。デプロイの失敗より、別環境の停止のほうが取り返しがつかない。
  名前が重複している時点で設定の誤りなので、`.env` を直させるほうが正しい。
- **先回りと事後の両方でやる。** `up` の前に名前を引いて空けておく（1 の経路）。
  ただし 2 の経路は `inspect` にも `ps` にも出ないため先回りできない。`up` の
  失敗メッセージには衝突相手のコンテナ ID が入るので、そこから拾って消し、
  1 度だけやり直す。
- **採らなかった案:**
  - *`down` の後に固定時間 sleep する* — 2 の経路は時間では解けない
    （名前が解放されないまま残る）。
  - *`up` を無条件にリトライする* — 名前を握ったままなので何度やっても同じ結果。
  - *サービスごとに `container_name` を明示する* — 名前が固定されるだけで、
    衝突したときに誰も片付けないという問題は変わらない。
  - *コンテナ名にデプロイごとの接尾辞を付ける* — 衝突は避けられるが、
    `docker compose exec db …`（ADR-0010）のように名前を前提にした運用手順が壊れる。

## 影響

- `docker compose down` は `--remove-orphans` 付きで実行する。過去の compose ファイル
  にしか無いサービスのコンテナは、デプロイのたびに掃除される。
- 別プロジェクトが名前を握っている場合、デプロイは通らない。運用者が各環境の `.env`
  の `DB_CONTAINER_NAME` と環境ディレクトリ名を直すまで解消しない（手順は
  `docs/OPERATIONS.md`）。
- 実体が無いまま名前だけ掴まれている状態は `docker rm -f` でも解けないことがあり、
  その場合は Docker デーモンの再起動が必要になる。スクリプトはそこまでは行わず、
  エラーにその旨を出して止まる（デーモンの再起動はホスト全体に影響するため、
  デプロイスクリプトが独断でやってよい操作ではない）。
