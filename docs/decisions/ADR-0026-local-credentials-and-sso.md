# ADR-0026: 認証の強度は入口ごとに決まる。ローカルの入口は丸ごと閉じられるようにする

- 日付: 2026-09-04
- 状態: 承認

## 文脈

ADR-0025 でローカル認証を残したまま SSO を足すと、入口が 2 つになる。

- **ローカルの入口** — パスワード（+ TOTP）またはパスキー。`LoginService` が資格情報を
  検証し、二要素が有効なアカウントではコードまで確かめる（ADR-0003）。
- **SSO の入口** — IdP が認証を済ませ、こちらは ID トークンを検証するだけ。
  `LoginService` を通らない。

ここから 4 つの問題が出る。

1. **ローカルの第二要素が SSO では効かない。** TOTP を有効にしている利用者でも、
   SSO で入れば TOTP は一度も聞かれない。弱いほうの入口が強いほうを無効化する。
2. **SSO で作られた利用者にはパスワードが無い**（乱数のハッシュ）。その状態で
   ローカルのパスキーを登録できると、**IdP を切っても入れる入口**が残る。
   IdP 側でアカウントを止めても、このアプリには入れたままになる。
3. **利用者からは「パスキー」が 2 種類に見える。** 自前 idp もパスキーを持っている。
   RP ID が違う（アプリのドメイン / `identity.nolumia.com`）ので別物だが、
   画面で区別しないと「登録したはずのパスキーで入れない」と読める。
4. **「SSO だけにする」派生が作れない。** 入口を閉じる手段が無く、IdP に寄せた運用に
   しても、パスワードとパスキーの入口は開いたままになる。

**IdP が何で認証したかは、以前は読めなかった。** 自前 idp は認可要求の `acr_values` を
受け取って本当に強制している（認証ポリシーの `requested_acr` 条件。SSO セッションを
復元するときにも評価し直す）のに、満たしたことを返す口が無く、要求は効くのに効いたことを
確かめる術がなかった。

**この片側だけの状態は 2026-09-04 に idp 側で塞がれた**（assay の ADR-0043）。予約語 2 つ
（`urn:assay:ac:mfa` / `urn:assay:ac:single`）を idp が組み込みで解釈し、ID トークンへ
`acr` を常に載せる。`amr`（RFC 8176）も載るが、**強度の判断には使わせない**と向こうで
決めている（`fed` の先で何が使われたかは idp も知らないため）。本番の discovery は既に
`acr_values_supported` にこの 2 つを公開している。

つまり **要求を送れば、効いたかどうかをこちら側で確かめられる。** その前提で設計する。

## 決定

1. **認証の強度は入口ごとに決まる**ものとして受け入れ、入口を跨いだ強制はしない。
   SSO で入ってきた利用者にローカルの TOTP を追加で要求することはしない。
   代わりに、**どの入口で入ったかを監査ログの `reason` に残す**
   （`method=password` / `method=passkey` / `method=sso`）。
   強い認証を要求したい場合は、**認可要求の `acr_values` で IdP に要求する**
   （`OIDC_ACR_VALUES`。既定は空＝要求しない）。**要求したら確かめる** ——
   ID トークンの `acr` が要求のいずれかと一致しなければ `sso_acr_not_satisfied` で断る。
   **`acr` が返ってこない場合も断る**（要求したのに保証が得られていないため）。
   併せて、`OIDC_ACR_VALUES` に書いた値が discovery の `acr_values_supported` に無ければ
   **起動時のログで警告する**（ADR-0025 の「知らない方式は不備として扱う」と同じ扱い）。
2. **ローカルの入口を丸ごと閉じられるようにする。** `LOCAL_LOGIN_ENABLED`（既定 `true`）。
   `false` のとき `POST /api/auth/login`・`POST /api/auth/passkey/login`・
   `POST /api/auth/forgot-password`・`POST /api/auth/reset-password` は
   403 `local_login_disabled` を返し、ログイン画面はパスワード欄とパスキーのボタンを
   出さない（`GET /api/auth/sso/provider` の応答に載せる）。
3. **ローカルの資格情報を作れるのは、ローカルの入口が開いているときだけ。**
   `LOCAL_LOGIN_ENABLED=false` のとき、パスキー登録・TOTP 有効化・パスワード変更は
   403 `local_login_disabled` を返す。閉じた入口の合鍵を作れないようにする。
4. **画面では 2 つのパスキーを混ぜない。** アカウント設定の「パスキー」はこのアプリの
   ものだけを指し、その旨を画面の文言に書く。IdP 側のパスキーはログイン画面の
   SSO ボタン（`OIDC_DISPLAY_NAME`）の向こう側にあり、**こちらからは一覧も削除もしない**。

## 理由

- **要求したら確かめる（さもなければ要求しない）。** `acr_values` を送って結果を見ないのは、
  IdP 側のポリシーの綴り違い 1 つで「MFA を要求したつもりで単要素のログインを受け取る」
  状態になり、しかもそれに気付けない。既定を空（要求しない）にしてあるので、
  **設定した派生だけが fail closed になる**——`acr` を返さない IdP へつないだまま要求すると
  ログインが通らない。これは正しい挙動で、要求が効いていないのだから通すべきではない。
- **入口を跨いだ強制はしない。** SSO 経路で TOTP を追加で聞くと、IdP 側で既に二要素を
  済ませた利用者に二重で要求することになる。`amr` を見て場合分けする案もあるが、**`amr` は
  強度を表さない**（`fed` の先は IdP も知らない）ので、それを判断材料にすると誤る。
  要求は `acr_values` で前もって出し、結果は `acr` で確かめる。こうすると判断が
  IdP の認証ポリシーという既にある仕組みに 1 か所へ集まる。
- **入口を記録するのは、後から辿れるようにするため。** ログイン成功の監査ログが
  どちらの入口か分からないと、IdP 側のアカウントを止めた後に「まだ入れている」ことに
  気付けない。値そのもの（メールアドレス・トークン）は載せない（ADR-0013）。
- **閉じるのは「設定」で、「削除」ではない。** ローカル認証のコードを消す選択肢も
  あるが、テンプレートは連携先の無い派生（IdP を持たない小さなアプリ）も作る。
  既定 `true` なら、今までどおりのアプリは何も変えなくてよい。
- **合鍵を作らせない（3 の理由）。** 2 だけでは足りない。閉じる前に登録された
  パスキーは残るし、閉じた後でも SSO で入った利用者が登録できてしまえば、
  設定を戻した瞬間にその鍵が効く。**「入口が閉じている＝その入口の鍵は増えない」**
  を規則にすると、運用側は「閉じた」以上のことを考えなくてよい。
  既に登録済みの資格情報は消さない（閉じたときに消すと、開け直したときに
  全員が締め出される）。
- **パスキーを画面で分ける。** RP ID が違う以上、このアプリから IdP 側のパスキーを
  触る方法は無い。「ここで消せないものを一覧に出さない」ほうが、消せると誤解させて
  IdP 側に残り続けるより良い。

## 影響

- **設定キーが 2 つ増える**（`LOCAL_LOGIN_ENABLED` / `OIDC_ACR_VALUES`）。
  設定管理の 3 ファイルすべてを更新する。
- **締め出しの経路ができる。** `LOCAL_LOGIN_ENABLED=false` の状態で IdP が落ちる、
  あるいは最後の管理者が IdP 側で止まると、**誰も入れなくなる**。
  復旧は環境変数で `LOCAL_LOGIN_ENABLED=true` へ戻して再起動する
  （環境変数は DB の設定より優先される）。`docs/OPERATIONS.md` に手順が要る。
  T4（最後の管理者を失う操作を防ぐ）と地続きの話で、そちらの条件にも
  「SSO でしか入れない管理者」を数える必要が出る。
- **`OIDC_ACR_VALUES` に書ける値は連携先が決める。** 自前 idp なら
  `urn:assay:ac:mfa` / `urn:assay:ac:single` の 2 つ（2026-09-04 から本番で公開されている）。
  **予約語を持たない IdP へつなぐ派生では空のままにする** ——設定すると `acr` が返らず
  全員が `sso_acr_not_satisfied` で断られる。既定が空なので、設定しない限り影響は無い。
- **`amr` は判断に使わない。** idp は `amr` も返すが、強度の判定には使わない
  （`fed` の先で何が使われたかは idp も知らないため）。監査ログと画面表示に限る。
- **監査ログの `reason` の語彙が増える。** 既存の絞り込み画面はそのまま使えるが、
  ログイン成功の行の見え方が変わる。
- **`frontend/README.md`** のログイン画面とアカウント設定画面の記述を更新する。
- ADR-0003（TOTP・パスキーを account_security として持つ）は変えない。
  そこへ「ローカルの入口が閉じているときは登録も止まる」という条件が乗る。
