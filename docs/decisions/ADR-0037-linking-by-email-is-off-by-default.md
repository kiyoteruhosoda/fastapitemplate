# ADR-0037: 同じメールアドレスの口座へ黙って寄せない（既定を無効にする）

- 日付: 2026-09-14
- 状態: 承認

## 文脈

初回の SSO ログインで `(issuer, sub)` の結び付きが無いとき、この雛形は
**同じメールアドレスのローカル口座を探して寄せていた**（ADR-0025 の 3 段階のうち 2 段目）。
条件は `email_verified` が真であること。既定は `OIDC_LINK_BY_EMAIL=true` だった。

条件そのものは正しく書かれていた。問題は **`email_verified` の意味が両側で違うこと**である
（idp の ADR-0049 G6）。

- **RP 側の読み方**: 「本人がそのアドレスの所有を証明した」
- **assay の実際**: この値が真になる経路は**自己登録の確認メールだけ**で、
  ⚠ **管理者によるメール変更（MT25）はこの値を維持する**（`update_profile` は
  `email_verified` を触らない）。管理者がログイン識別子としてメールを足すときも
  所有確認は行わない（idp の ADR-0025）。

つまり assay の `email_verified` は **「テナント管理者がそう主張している」**である。
assay 側の決定としては筋が通っているが、RP が前者の意味で読んでいると、
**テナント管理者が付け替えたアドレス 1 つで、このアプリの既存口座へ入れる**ことになる。

そして、その口座が誰のものかを **RP は確かめる術を持たない。**

## 決定

**`OIDC_LINK_BY_EMAIL` の既定を `false` にする。** 値オブジェクト
（`AccountLinkingPolicy.link_by_email`）・設定の既定値・管理画面の既定を揃えて倒す。

開けたときの条件（`email_verified` が真であること）は**そのまま**残す。
開けるかどうかを決めるのは、**つないだ IdP でその値がどう立つのかを確かめた人**である。

## 理由

**安全側がどちらかは、RP には決められない。** IdP ごとに `email_verified` の立ち方は
違い、しかもそれは IdP の設定と運用で後から変わる。**RP が既定で信じてよい値ではない。**

倒す代わりに失われるのは「初回ログインの手間が 1 つ減る」ことだけで、
残るのは `sso_account_not_linked` という**分かる形の失敗**である。逆向きの間違い
（黙って他人の口座へ入る）は**気付けない**。非対称なので、倒すほうを選ぶ。

### 検討して捨てた案

- **assay がメール変更時に `email_verified` を落とす**（idp の ADR-0049 G6 の選択肢 2）。
  MT25 の運用が変わり、**assay を使う全 RP に影響する**。RP 1 本の既定を倒すほうが小さい。
- **主張の出どころをクレームで分ける**（同 選択肢 3）。いちばん筋は良いが、いちばん大きい。
  倒したあとで必要になったら考える。
- **`email_verified` を見るのをやめ、常に寄せる／常に断る。** 常に寄せるのは論外。
  常に断るのは、意味が一致している IdP でも使えなくなる。設定を残して既定を倒す。

## 影響

- ⚠ **既に結び付いている利用者には影響しない。** `federated_identities` に行がある
  相手は 1 段目で決まる。効くのは**これから初めて SSO で入る人**だけである。
- ⚠ **同じメールアドレスのローカル口座がある新規の相手は、ログインできなくなる**
  （`sso_account_not_linked`）。これまでの挙動が要るなら
  `OIDC_LINK_BY_EMAIL=true` を明示する ——**そのとき、つないだ IdP で
  `email_verified` がどう立つのかを確かめること。**
- **本人の操作で結び付ける導線が無い。** idp の ADR-0049 I9 が本筋として挙げているのは
  「本人がログイン済みの状態で、設定画面から連携する」経路である。いまは無いので、
  当面は管理者が `federated_identities` を整えるか、設定を開けることになる。
  導線そのものは ADR-0040 で入った（設定画面から本人が連携する）。
