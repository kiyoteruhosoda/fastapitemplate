# ADR-0095: 一覧 API は limit と offset で受け、entries と total で返す

- 日付: 2026-10-31
- 状態: 承認

## 文脈

`/api/items` などの一覧は全件を返し、画面も全件を前提にしている。件数が増えると DB・応答・画面のどれも重くなる。
ログの検索だけは先に `limit`・`offset`・`total`・`entries` で作ってあった（ADR-0075）。新しい一覧の手本が無い（task #796）。

## 決定

1. **指定は `limit`（既定 50・上限 200）と `offset`（既定 0）。** 共通のスキーマ `PageQueryRequest`（`presentation/fastapi/schemas/pagination.py`）で受ける。
2. **応答は `{"entries": [...], "total": 全件数}`**（`PageResponse[T]`）。範囲を超えた `offset` は空の `entries` と `total` を返す。
3. **上限を超える指定は 422 で断る。** 丸めない。
4. **並びは必ず一意に決める**（最後に `id` を足す）。決まっていないと、ページをまたいで同じ行が 2 回出たり抜けたりする。
5. リポジトリは `find_page(..., page: PageRequest) -> Page[T]`（`shared/domain/page.py`）で返す。見本は `bounded_contexts/example`。
6. **既にある全件の口は、この ADR では変えない。** `/api/admin/users`・`/api/admin/roles` は画面が全件を前提に絞り込みと一括の操作をしている。件数が問題になったときに、画面と一緒に直す。新しい一覧はこの規約で作る。

## 理由

- ログの検索と同じ名前に揃えれば、画面の部品（`logSearch.ts`）と呼ぶ側の覚えることが増えない。
- 丸めると、頼んだより少ないことに呼ぶ側が気付かず、途中で切れた一覧を全部だと思い込む。断れば書いた時点で分かる。ログの検索も API の段では 422 で断っている。

| 採らなかった案 | 捨てた理由 |
|---|---|
| カーソル（続きの札）で送る | 追加が多い一覧には強いが、「n ページ目」と全件数が出せない。雛形の見本には重い。要るアプリはその口だけ足せる |
| `page`・`size` で受ける | ログの検索と名前が割れる |
| 配列を返し、全件数をヘッダーで返す | 型が OpenAPI に載らず、CORS の設定も要る |
| 全件の口を一度に全部直す | 画面の絞り込みと一括の操作を作り直すことになり、問題が起きていない口まで壊す |

## 影響

- ⚠ `GET /api/items` の応答の形が配列から変わる（見本なので、この時点で変える）。
- `total` のために毎回 `COUNT` が 1 本増える。大きな表では索引の効く条件で絞る。
- `offset` は深いページほど遅く、追加や削除でページがずれる。見本の用途では許容する。
