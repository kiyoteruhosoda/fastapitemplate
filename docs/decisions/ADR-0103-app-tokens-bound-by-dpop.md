# ADR-0103: 端末の鍵に結び付けたアプリのトークンは DPoP の証明と一緒にだけ受ける

- 日付: 2026-11-04
- 状態: 承認

## 文脈

アプリ（flutterbase 派生）は assay に直接ログインし、assay のアクセストークンでアプリ向けの口を叩く（ADR-0081 §1）。
トークンは持っているだけで使える（Bearer）ので、端末の外へ写されると別の端末から使える。

assay は DPoP（RFC 9449）に対応した（idp の ADR-0075。task #893）。アプリが Android Keystore の鍵で証明を付けて
トークンを取ると、アクセストークンに `cnf.jkt`（鍵の指紋）が入る。受ける側がその鍵の証明を確かめなければ、
結び付けても意味が無い。

## 決定

1. **`cnf.jkt` のあるトークンは、`Authorization: DPoP <token>` と `DPoP: <証明>` でしか受けない。** `Bearer` で来たら
   401。`cnf` の無いトークンは今までどおり `Bearer` だけ（DPoP を入れていない派生のアプリはそのまま動く）。
2. **証明の確かめは assay と同じ**（idp の ADR-0075 決定 2〜6）: `typ` は `dpop+jwt`、`alg` は ES256、`jwk` は P-256 の
   公開鍵（`d` があれば断る）、署名、鍵の指紋（RFC 7638）が `cnf.jkt` と同じ、`htm` は大文字のメソッド、`htu` は
   **`APP_BASE_URL` ＋パス**（問い合わせと断片は外して比べる。前段の proxy の後ろで `Host` から組み立てない）、
   `ath` はアクセストークンの SHA-256、`iat` は今より 120 秒前〜60 秒後。nonce（`DPoP-Nonce`）は使わない。
3. **`jti` は鍵ごとに 1 回だけ。** `dpop_proof_jtis` に `sha256(jkt ":" jti)` を、受ける幅が閉じるまで残す。重複なら
   挿さない INSERT 1 回で見分ける（同時に 2 本来ても片方だけ）。期限切れは記録するたびに消す。
4. **証明が合わないときは 401 と `WWW-Authenticate: DPoP error="invalid_dpop_proof", algs="ES256"`、本文は
   `{"detail": {"error": "invalid_dpop_proof"}}`。** アプリは応答の `Date` で時計を直して 1 回だけ作り直す。
5. **結び付けたトークンで初めて来た人のプロフィールは、アプリが送る ID トークン（`X-ID-Token`）から読む。** このサーバーは
   鍵を持たないので、そのトークンで assay の `/userinfo` を引けない。ID トークンは署名・発行者・期限と、宛先（`aud`）が
   `APP_CLIENT_IDS` のどれかであることを確かめ、`sub` がアクセストークンと違えば使わない。無ければプロフィール無しで
   進む（メールで寄せる・作るときは ADR-0077 §6 のとおり断る）。

## 理由

- **結び付けたトークンを Bearer でも受けると、写しただけの者が使える**（受け手が確かめなければ結び付けの意味が無い）。
- **nonce を使わない**: 鍵は Keystore から取り出せず、先に作った証明を後で使うにはその端末の中で動いている必要がある。
  その場合はいつでも新しい証明を作れるので、nonce の往復を足しても守りは増えない（idp の ADR-0075 決定 3）。
- **`jti` を DB に覚える**: このアプリは複数のプロセス（gunicorn のワーカー）で動く。プロセスの中に覚えると、
  別のワーカーへ同じ証明を送り直せる。
- **ID トークンからプロフィールを読む**: アプリは同じログインで受け取った ID トークンを持っている。宛先がアプリの
  `client_id` なので、他の RP 向けの ID トークンは持ち込めない。採らなかった案は、アプリに `/userinfo` 宛ての証明を
  もう 1 つ作らせて中継する形（呼ぶたびに署名が 2 回になる）と、assay にプロフィールを問い合わせる機械の口
  （設定が増え、機械のクライアントを持たない派生では使えない）。

## 影響

- 証明 1 つにつき DB の書き込みが 1 回増える（アプリ向けの口だけ）。
- `jti` の記録は要求と同じトランザクションに入るので、要求が例外で巻き戻ると記録も消える。その証明で
  もう一度通せるのは、120 秒以内に同じメソッド・同じ URL・同じトークンで送る同じ要求だけ（失敗した要求の
  やり直し）なので、別のセッションで先に確定させる形にはしない。
- `APP_BASE_URL` が実際に外から見える URL と違うと、DPoP の要求はすべて 401 になる（Bearer は影響を受けない）。
- 派生のアプリは、この版を取り込めば DPoP のトークンを受けられる。アプリ（flutterbase）が DPoP を使い始める前に
  サーバーへ取り込む必要がある（逆順だと、アプリのトークンが 401 になる）。
