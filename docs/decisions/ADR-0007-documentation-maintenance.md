# ADR-0007: 画面仕様・ER 図・ADR・Progress を「変更と同じコミットで更新する」ドキュメントとして固定する

- 日付: 2026-07-30
- 状態: 承認

## 文脈

CLAUDE.md にはドキュメントの役割分担（OPERATIONS / ARCHITECTURE / README /
CHANGELOG）が書かれていたが、次の 2 種類のドキュメントが存在せず、置き場所も
更新義務も決まっていなかった。

- **画面（SPA）の仕様**。ルート・画面遷移・画面ごとの必要 scope・利用者向けの操作手順が
  どこにも書かれておらず、`App.tsx` と `Sidebar.tsx` を読まないと分からない。
- **DB スキーマの全体像**。テーブルが 12 個あり FK も `ON DELETE CASCADE` を含むが、
  関係を把握するにはモデル 6 ファイルとマイグレーション 3 本を追う必要がある。

また、ドキュメントの更新は「重要なら書く」という緩い基準しかなく、
実装だけ進んで記述が古くなるのを止める仕組みが無かった。ADR と `Progress.md` も
運用ルールは書かれていたが、何を ADR にするか・どのタイミングで書くかの基準が
曖昧だった。

## 決定

「現在の仕様」を示す 2 つのドキュメントを追加し、CLAUDE.md に**変更と同じコミットで
更新する義務**として明記する。

| ドキュメント | 内容 | 更新の引き金 |
|---|---|---|
| `frontend/README.md` | 画面遷移図（Mermaid）・画面一覧・画面仕様・操作マニュアル | 画面の追加・削除、ルート変更、遷移変更、必要 scope の変更、操作手順の変更 |
| `docs/ER.md` | ER 図（Mermaid）・テーブル定義・モデリング規約 | テーブル・カラム・リレーション・制約の変更 |

あわせて CLAUDE.md に以下を明文化する。

- **タスク管理**: `Progress.md` を唯一のタスク一覧とし、着手前に行を追加、状態を進め、
  完了時に削除する（「✅完了」の状態を作らない）。完了報告の前に更新する。
- **設計判断**: 選択肢のある決定は必ず `docs/decisions/ADR-NNNN-*.md` に残す。
  対象の例、採番規則（最大値 + 1、欠番と重複を作らない）、承認済み ADR は
  書き換えず新しい ADR で置き換える、実装と同時に追加する。

## 理由

- **図はコードから自動生成しない。** ER 図・遷移図の自動生成（`eralchemy` 等）は
  ツールの追加と CI 上の実行環境を要求する一方、「なぜこのテーブルが FK を持たないか」
  「どの画面がどの scope を要求するか」といった読み手が必要とする情報を出せない。
  手書き + 更新義務のほうが情報量あたりの費用が低い。
- **Mermaid を使う。** GitHub がそのまま描画するため画像ファイルの再生成が不要で、
  差分がテキストとしてレビューできる。
- **API 仕様は書かない。** 既存ルール（Swagger UI / `openapi.json` が唯一の出所）を
  維持し、`frontend/README.md` は「どの画面がどのエンドポイントを使うか」だけを持つ。
  リクエスト・レスポンスの形を二重に書くと必ず乖離する。
- 検討した代替案:
  - **ドキュメントを増やさず docstring に寄せる**: 画面の遷移とスキーマ全体像は
    複数ファイルにまたがるため、1 か所にまとまった図が要る。却下。
  - **CI で乖離を機械検証する**（ルート一覧と README の差分チェック等）: 有効だが、
    「操作手順」「テーブルの意味」のような自然言語部分は検証できず、
    形式的な項目だけを守らせる仕組みになる。まずは更新義務を明文化し、
    機械検証は必要になった時点で別 ADR とする。

## 影響

- 画面またはテーブルを変更する作業には、対応するドキュメントの更新が含まれる。
  レビューでは差分に該当ファイルが含まれているかを見る（現時点では機械検証しない）。
- `docs/ER.md` と `frontend/README.md` は**コードに追従する側**であり、正本ではない。
  食い違ったときはモデル・マイグレーション・`App.tsx` が正しい。
- ADR の採番規則を明文化したため、以後 `NNNN` の欠番・重複はレビューで指摘できる。
