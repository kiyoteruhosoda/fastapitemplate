# ADR-0070: 機能の権限はトークンで、資源 1 件ずつの可否は DB で確かめる

- 日付: 2026-10-30
- 状態: 承認
- 関連: ADR-0002（scope で認可する）・ADR-0041（アクセストークンは DB を引かずに確かめる）・ADR-0047（グループ）・ADR-0061/0062（テナント）

## 文脈

ADR-0041 で、アクセストークンの `scope` に利用者の権限コードを載せ、確かめるときは DB を引かないと決めた。
権限が増えるとトークンが膨らむのではないか、という懸念が出た。

大きなクラウドの作りを比べた。

| | 何を書くか | 階層 | トークンに載るもの |
|---|---|---|---|
| Azure RBAC | 操作名（`Microsoft.Compute/virtualMachines/read`）を束ねたロールを、**どこに**（管理グループ → サブスクリプション → リソースグループ → 資源）与えるか | ロールに継承は無い。「どこに」の側が上から下へ効く | 身元とグループ程度。グループも JWT では 200 件で打ち切り、超えたら Graph で引かせる |
| AWS IAM | 操作名（`s3:GetObject`）・資源・条件の JSON ポリシー | ロールに継承は無い。組織の上限（SCP）・権限境界・資源側のポリシーが重なる | 権限は載らない。毎回サーバー側で評価する（セッションのポリシーだけ 2,048 文字まで載る） |

どちらも、細かい可否は**トークンに入れずにサーバー側で**決めている。トークンに入れているのは、数が増えない粗い区分だけである。

このテンプレートの scope は機能単位（`item:view` / `item:manage` …）で、今は 15 個・約 250 バイトしかない。
機能単位である限り、Cookie の 4KB に届くのは 100 個前後になってからで、派生アプリ 1 本でそこまで増えることはまず無い。
膨らむのは「このメモはこの人が編集できる」のような**資源 1 件ずつの可否**を scope に入れたとき（`note:42:edit`）で、
これは資源の数だけ増える。

派生アプリでは、グループ（ADR-0047）を共有の範囲に使うことが見込まれている。そうなったときの書き方の見本が無かった。

## 決定

1. 認可を 2 段に分ける。
   - **機能を使えるか**（何ができるか）は、トークンの `scope` で確かめる。DB は引かない（ADR-0041 のまま）。
   - **この 1 件を扱えるか**（どれに対してか）は、持ち主・所属などの**データで、リクエストのたびに DB で**確かめる。
2. `scope` に資源の ID や資源ごとの可否を入れない。グループの所属もトークンに入れない。
3. 読めない資源には 404 を返す（在ることを教えない）。読めるが変えられない資源には 403 を返す。
4. 画面は 2 段を両方見る。機能のボタンは scope で、行ごとのボタンはサーバーが返す可否（`can_change`）と scope の両方で出し分ける。
5. 見本として、共有メモ（`bounded_contexts/notes`）を置く。
   - 機能の scope は `note:view`（読む）と `note:write`（書く）。
   - メモ 1 件の可否は、持ち主なら読めて変えられる、共有先のグループの一員なら読むだけ、と決める。
   - 共有先に選べるのは、自分が入っているグループだけ。

## 理由

- Azure と AWS は、どちらも資源ごとの可否をトークンに載せていない。Azure は、グループの所属を載せる形で実際にトークンの大きさの上限に当たっている。
- 機能単位の scope は数が増えず、確かめるのに DB が要らない。ADR-0041 の利点（DB の調子に左右されない）はそのまま残る。
- 資源ごとの可否は、もともとデータそのものである。持ち主の列や所属の表を引けば決まるので、トークンへ写す意味が無い。
  写すと、グループを抜けても寿命が切れるまで読めてしまう。DB で見れば、次のリクエストから効く。
- 一覧は SQL で絞る（テナントの全部を読んでから 1 件ずつ篩うことはしない）。1 件の可否は、ドメインのエンティティ（`Note.readable_by` / `changeable_by`）が答える。
  同じ決まりを 2 か所に書くことになるが、一覧と 1 件が食い違えば統合試験が落とす。

採らなかった案:

| 案 | 捨てた理由 |
|---|---|
| 資源ごとの可否を scope に入れる（`note:42:edit`） | 資源の数だけトークンが膨らむ。外したことが寿命まで効かない |
| 全部を DB で確かめる（ADR-0041 を戻す） | 機能単位の判定まで毎回 DB に頼ることになる。今の規模では負荷は問題にならないが、得るものも無い |
| トークンにはロール名だけを載せ、ロール→権限の表をアプリのメモリに持つ | 権限が 100 個に近づいたときの逃げ道として残す。今は要らない |
| テナント管理者（`owner`）にはどのメモも読ませる | 見本では入れない。個人のメモを管理者が読めると困る用途がある。要るアプリは、別の機能の scope（例 `note:moderate`）を足し、エンティティの決まりで両方を見る |

## 影響

- 派生アプリで「誰の・どの範囲の」資源かを分けたいときは、`bounded_contexts/notes` の形に倣う。
  エンティティに可否を答えさせ、ユースケースで確かめ、一覧はリポジトリが SQL で絞る。
- 所属を引くための DB の読み取りが、資源を扱うリクエストのたびに 1 回増える（自分のグループの一覧。主キーと索引で引ける）。
- 権限が 100 個に近づいたら、決定の「採らなかった案」の 3 つめ（ロール名だけを載せる）を新しい ADR で検討する。
