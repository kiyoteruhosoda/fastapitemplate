# ADR-0065: テナント管理者は招待で指名し、システム管理者はパスワードを知らない

- 日付: 2026-10-22
- 状態: 承認

## 文脈

ADR-0061 決定 7 は「テナントを登録するとき、システム管理者が最初のテナント管理者（の招待）を
決める」とした。同じ ADR は「システム管理者はテナントの中身を見られない」ことを、運用の約束では
なく権限の形で保証すると決めている。

いちばん簡単なのは、システム管理者が初期パスワードを決めてテナント管理者を作る形である。
しかしそれでは、システム管理者がそのパスワードでテナント管理者として入れてしまい、中身を
見られない約束が崩れる。

ほかにも決めることがある。

- SSO のテナントでは、指名した人は IdP で入ってくる。メールアドレスで既存の利用者へ寄せるのは
  既定で閉じている（ADR-0037）ので、指名した席に結び付かない
- テナントの削除は、家族・組織のデータを丸ごと消す。押し間違い 1 回で消えてよいか
- システム管理者どうしの付け外しを、どの権限で許すか

## 決定

1. **指名は「席を作って招待する」。** システム管理者はメールアドレスと表示名だけを決める。
   席はそのテナントの `owner` で、パスワードを持たない（ADR-0038）。本人には招待のメールが
   届き、リンクから自分でパスワードを決める（`password_reset_tokens.purpose = invitation`、
   有効 7 日）。⚠ リンクは応答にも画面にも出さない。
2. **SSO のテナントでは、席はその IdP で初めて入ったときにも受け取れる。** 入り口を 1 つも
   持たない利用者（パスワードも IdP との結び付きもパスキーも無い）は「指名された席」で、
   検証済みのメールアドレスが一致すれば、寄せる設定（`OIDC_LINK_BY_EMAIL`）とは別に結び付ける。
   入り口を持っている利用者は席ではないので、今までどおり寄せる設定に従う。
3. **テナントの削除は、止めてからでないとできない**（409 `tenant_not_suspended`）。画面では
   短い名前を打たせてから消す。消すのは人・中身・自作のロールで、監査ログは残す。消す表は
   表の宣言（ADR-0062）から機械的に決める。
4. **テナントの外側の API は `/api/system/*`。** テナントの台帳は `tenant:manage`、システム
   管理者どうしの付け外しは `system:manage`。足すときは招待（決定 1 と同じ）、自分は外せず、
   有効なシステム管理者を 0 人にはできない。
5. システム管理者が指名した事実は、対象の利用者のテナントの監査ログにも残る（ADR-0062 決定 5）。

## 理由

- **招待にする**: システム管理者がパスワードを知らない形でなければ、中身を見られない約束は
  権限の形にならない。招待のリンクを応答に載せないのも同じ理由。
- **SSO の席の受け取り**: 席には誰の入り口も無いので、結び付けても誰かの口座を奪うことには
  ならない。メールを止めてある環境でも、SSO のテナントなら指名が届く。
  ⚠ assay の `email_verified` は「テナント管理者がそう主張している」の意味（ADR-0037）なので、
  受け取れるのは、そのテナントの IdP がそのメールアドレスを名乗らせた人である。
- **止めてから消す**: 止めるのは戻せる。消すのは戻せない。2 段にすると、押し間違いでは消えない。

### 検討して捨てた案

- **初期パスワードを決めて渡す**: 上の理由で取らない。
- **既存の利用者をテナント管理者に上げる口をシステム管理者に持たせる**: テナントの中の人事に
  外から手を入れることになる。管理者が居なくなったときの立て直しは、新しい席の指名で足りる。

## 影響

- メールを止めてある環境で、SSO を使わないテナントを作ると、指名した人に入り口が届かない
  （画面に「送れなかった」と出る）。メールの設定を済ませてから指名し直す。
- 招待のリンクは本人のメールにだけ届く。届かなかったときの再送は、指名し直し（新しい席）になる。
