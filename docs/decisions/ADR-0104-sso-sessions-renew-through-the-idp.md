# ADR-0104: SSO で入ったログインはリフレッシュトークンを持たず、切れたら画面を出さずに IdP へ問い合わせる

- 日付: 2026-11-04
- 状態: 承認
- 関係: ADR-0076 §4（トークンは Cookie）・§5（検証は DB を引かない）・§10（入り直したばかり）、ADR-0077 §3（IdP からの停止）・§9（ログイン画面の prompt=none）、ADR-0091（控えと振り替え）・ADR-0101（延長の設定）・ADR-0102（止めた記録の長さ）。**パスワード・パスキーで入ったログインには何も変えない**

## 文脈

assay のログイン状態は、結び付けの有無で長さが変わり、端末の登録を取り消すと終わる（task #875・#887・#872）。ところが各アプリは SSO で入ったあと、自分でリフレッシュトークン（既定 14 日・使うと延びる）を持つ。Cookie をまとめて盗まれると、assay のログイン状態が終わっても、アプリのリフレッシュトークンから 14 日使われる（task #888）。

## 決定

1. **SSO で入ったログインには、リフレッシュトークンとログアウトの札を出さない。** `refresh_sessions` の行も作らず、アクセストークンに `rsid` を載せない。出すのはアクセストークン（`ACCESS_TOKEN_EXPIRES_SECONDS`。既定 5 分）だけ。
2. **この仕組みより前に出した SSO のリフレッシュトークンは、更新の口で断る**（401・控えを消し・札の Cookie を落とす）。SSO で入り直したときも札の Cookie を落とす。
3. **切れたら、画面が見えない枠（iframe）で `GET /api/auth/sso/renew` を開く。** そこから IdP へ `prompt=none` で往復し（往復状態の `purpose` は `renew`）、戻り（`/callback`）は引き換え券をその場で換えて Cookie を載せ、結果の頁 `GET /api/auth/sso/renewed?result=renewed|declined|failed` へ送る。画面は枠の行き先（同じオリジン）を読む。枠の中でスクリプトは動かさない。
4. **続けるのは入り直しではない。** 手元に残った期限切れのアクセストークンから、利用者・アクティブロール・サインインした時刻・パスキーの印を往復状態へ写し、**同じ人が戻ってきたときだけ**引き継ぐ。ロールはまだ持っているときだけ。読むのは署名・発行者・宛先を確かめ、期限は 30 日（`RENEWAL_CARRY_SECONDS`）まで見逃す。そのため SSO のアクセストークンの Cookie はトークンより長く（30 日）残す。手元にトークンが無ければ新しいログインとして入る。
5. **別の人が戻ってきたら続けない**（`declined`）。IdP の「入っていない・許可が無い」も `declined`。往復が壊れた・IdP と話せない・時間切れ（15 秒）は `failed`。どちらも画面はログイン画面へ送る（行き先は `redirect_to`）。
6. **続けられなかったときの書きかけは、sessionStorage に書くたびに写しておく**（画面の `useSessionDraft`）。戻ってきて同じ画面を開けば残っている。サインアウトで全部消す。
7. **枠に入れてよいのは自分のオリジンだけ。** `/renew`・続ける往復の `/callback`・結果の頁は `X-Frame-Options: SAMEORIGIN` と `frame-ancestors 'self'`。ほかの応答は今までどおり `DENY`・`'none'`。画面の CSP には `frame-src 'self' https://*.<発行者の親ドメイン>` を足す（枠の中の往復は発行者 `identity.` からログイン画面 `assay.` へ移るので、発行者 1 つでは足りない）。
8. **続ける往復はタブをまたいで 1 本ずつ**（Web Locks）。順番を待つ間にほかのタブが続けていれば（`/api/auth/me` が通れば）枠を開かない。往復状態の Cookie は 1 つなので、同時に走らせると先の往復が必ず失敗する。
9. **入口の 401（パスワード違い・二要素の不足など）では続けない。** 続けるのは `authentication_required` と `invalid_token` の 401 だけ。サインアウトした印（`ssoSignedOut`）があるときも問い合わせない。断られたらこのタブの「試した」印を付け、ログイン画面の自動の試し（ADR-0077 §9）を重ねない。
10. **続ける往復の成功は監査に積まない**（利用者を作った・結び付けたことだけ積む）。5 分ごとに積まれ、本当のログインが埋もれる。アプリログには残す。
11. IdP からの停止の記録を残す長さは、リフレッシュトークンの期間とアクセストークンの寿命の長いほう（ADR-0102 の最低限に足す）。

## 理由

- **何を塞ぐか**: Cookie を盗まれても、5 分を過ぎると IdP のログイン状態（結び付け・端末の登録・取り消し）に従う。端末の登録を取り消すと、その端末のアプリは次の問い合わせ（5 分以内）で止まる（task #888 AC4）。
- **iframe を主にする**: 画面が切り替わらず、書きかけも残る。DBSC（task #887）は W3C の草案（2026-09-08 版 §8.3・§8.5）で、iframe からの要求でも更新される（要求を出したオリジンが assay と同じか、`allowed_refresh_initiators` に合えば）。
- **結果は URL で渡す**: `postMessage` を使うと結果の頁にスクリプトが要り、CSP の `script-src 'self'` のまま頁を足すことになる。同じオリジンの枠の URL なら何も要らない。
- **引き換え券をその場で換える**: 枠の中で SPA を起こさずに済む。券の検証（1 回限り）は今の口と同じものを通る。
- **パスワード・パスキーのログインはそのまま**: 問い合わせる先が無い。本番の派生アプリは `LOCAL_LOGIN_ENABLED=false`。
- **アクセストークンは 5 分のまま**: 設計書の「15 分」は今の値の書き違いだった。短いほうが停止が早く効き、問い合わせは画面に出ない。

| 採らなかった案 | 捨てた理由 |
|---|---|
| リフレッシュトークンを短くする（1 時間など） | 盗まれてからその長さは使われる。IdP の取り消しも効かない |
| 全画面の往復だけにする | 5 分ごとに画面が切り替わり、書きかけが消える。予備として残す（ログイン画面の prompt=none） |
| 枠の結果を `postMessage` で返す | 結果の頁にスクリプトが要る（上の理由） |
| 期限切れのトークンを読まず、画面がロールを送る | 画面の値は信じられない。署名付きのトークンなら改竄できない |
| 続けるたびに監査へ成功を積む | 1 日に数百行になり、ログインの記録が読めなくなる |

## 影響

- SSO で入ったログインの長さは IdP のログイン状態で決まる（`REFRESH_TOKEN_EXPIRES_SECONDS`・`REFRESH_TOKEN_SLIDING_ENABLED` は SSO には効かない）。
- 画面を閉じていた間に IdP のログイン状態が終わっていれば、開いた時点でログイン画面になる（今までは 14 日続いた）。
- サインアウトはアクセストークンの Cookie を落とすだけになる（SSO で入ったログインには終わらせる控えが無い）。
- IdP（assay）は `prompt=none` の往復を `*.nolumia.com` の枠の中で通す必要がある（idp 側の task #888）。iframe がブラウザに止められても、401 のあとログイン画面の自動の試しで全画面の往復になる。
- ⚠ 派生アプリには取り込んでいない（task #889）。取り込むときは `establish_session`・`token_service`・SSO の口（`/renew`・`/renewed`・`/callback` の `renew`）・`security_headers` の `frame-src`・画面の `api.ts`・`silentRenewal.ts`・`sessionEnded.ts`・`useSessionDraft` を一緒に入れる。
