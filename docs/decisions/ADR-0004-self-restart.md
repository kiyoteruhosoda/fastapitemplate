# ADR-0004: 起動時にしか読まれない設定は、DB 経由の再起動要求で反映する

- 日付: 2026-07-29
- 状態: 承認

## 文脈

システム設定は管理画面から保存でき、`settings` の DB 上書きキャッシュを捨てれば
即時反映される。しかし一部の設定はアプリケーションファクトリ（`create_app`）で
一度だけ評価されるため、保存しても効かない。

- `LOG_LEVEL` / `LOG_TO_DATABASE` — `setup_logging()` が起動時に一度だけ読む
- `CORS_ALLOWED_ORIGINS` — `CORSMiddleware` の登録時に確定する

保存しても何も変わらないのに画面上は成功と出る、という状態だった。

## 決定

1. 設定定義に `restart_scopes` を持たせ、保存 API の応答で「どの設定の反映に
   どのサービスの再起動が要るか」を返す。
2. 再起動は DB（`system_settings` の `app.restart_request`）に要求を置き、各
   プロセスが監視スレッド（`RestartWatcher`）で拾って**自分自身を終了**させる。
   復帰は Docker の `restart: unless-stopped` に任せる。
3. 既存の `POST /api/admin/maintenance/shutdown` は削除し、
   `POST /api/admin/system/restart` に一本化する。

## 理由

- **DB 経由にする**: 管理 API を処理したプロセスと、再起動すべきプロセスは別。
  Gunicorn は複数ワーカーで動き、将来サービスを分ければ別コンテナになる。DB に
  置けば、コンテナへ docker socket をマウントせずに全プロセスへ届く。
- **時刻ではなく token の変化で判定する**: 「保存時刻が起動時刻より後なら再起動」
  にすると、アプリコンテナと DB の時計がずれている環境で再起動ループに陥る。
  起動時に読んだ token と違うかどうかだけを見る。
- **スコープごとに要求を保持する**: 単一レコードを上書きすると、ポーリング間隔
  （既定 10 秒）の内側に 2 件入ったとき、先の要求を読む前に消える。本テンプレート
  のサービスは `web` だけだが、ワーカーを足したときに壊れない形にしておく。
- **`maintenance/shutdown` を消す**: あれは自プロセスへ SIGTERM を送るもので、
  Gunicorn 配下ではワーカーが 1 つ落ちてアービターが同じ環境で作り直すだけ。
  設定は反映されない。「終了方法はプロセス構成で変わる」という知識を
  `build_process_terminator()` に集約し、入口も 1 つにする。

## 影響

- 再起動要求から実際の再起動まで最大 10 秒（ポーリング間隔）かかる。応答が
  返った時点ではまだ再起動していない。
- コンテナが `restart` policy 無しで動いている場合、終了したまま戻らない。
  `docker-compose.yml` の `web` は `restart: unless-stopped`。
- `TESTING` のときウォッチャーは起動しない（テストが自分を落とさないため）。
