# ADR-0003: 二要素認証とパスキーを account_security コンテキストとして取り込む

- 日付: 2026-07-29
- 状態: 承認（ADR-0002 の「TOTP・パスキーは含めない」を置き換える）

## 文脈

ADR-0002 では、テンプレートを薄く保つため TOTP・パスキーを除外し、必要になった
時点で photonest から移植する方針とした。実際に必要になったため取り込む。

移植元（photonest）には次の課題があった。

- 二要素認証の共有鍵が `user.totp_secret` 列で、ユーザーの集約に混ざっている。
- パスキーのチャレンジがプロセス内の `dict`（`_challenge_cache`）。単一プロセス
  でしか動かず、コード中のコメントにも「本番では Redis 等へ移行すること」と
  残っていた。本テンプレートは Gunicorn `--workers=2` が既定のため、そのままでは
  ワーカーをまたいだ瞬間に検証が落ちる。
- パスキーの登録・認証が `webauthn` ライブラリの型に直接依存しており、Domain と
  Infrastructure の境界がない。

## 決定

`bounded_contexts/account_security/` として新しいコンテキストを作り、二要素認証
（TOTP）とパスキー（WebAuthn）をまとめて置く。移植元の設計は次の 3 点で変える。

1. TOTP 共有鍵は `users` の列ではなく `totp_secrets` テーブル（1 ユーザー 1 行）。
   `confirmed_at` を持ち、**確認できるまで有効にしない**（2 段階登録）。
2. WebAuthn チャレンジは `webauthn_challenges` テーブルに置く。クライアントへは
   `challenge_id` だけを返し、1 回で消費する。
3. `TotpAuthenticator` / `WebAuthnRelyingParty` を Domain 層の Protocol として
   定義し、`pyotp` / `webauthn` は Infrastructure の実装に閉じ込める。

## 理由

- **共有鍵を別テーブルにする**: 認可の中心である `User` に、コンテキスト固有の
  列を足さずに済む。ユーザー削除時は `ON DELETE CASCADE` で追随する。
- **2 段階登録**: 1 段階で有効化すると、QR の読み取りに失敗した利用者が自分の
  アカウントから締め出される。確認できるまで「登録手続き中」に留める。
- **チャレンジを DB に置く**: Redis を新たな必須依存にせずに複数ワーカーへ対応
  できる。チャレンジは短命（既定 300 秒）で件数も少なく、DB の負担にならない。
  発行のたびに期限切れを掃除するため、定期ジョブも要らない。
- **ライブラリ型を境界の外へ出さない**: `webauthn` は破壊的変更のある依存
  （実際に 1.x → 3.x で検証 API の形が変わっている）。境界を切っておくと、
  追随はアダプタ 1 ファイルの修正で済む。テストも偽の実装へ差し替えられる。

## 影響

- 依存が増える: `pyotp` / `webauthn` / `qrcode`。QR は SVG で描くため Pillow は不要。
- マイグレーション `0003_account_security` を追加（3 テーブル）。
- パスキーでログインした場合は TOTP を要求しない。パスキー自体が所持と
  （多くの端末では）生体・PIN を伴う強い認証であり、重ねる設計は採らない。
- `WEBAUTHN_RP_ID` は登録済みパスキーの結び付け先。運用開始後に変更すると
  既存のパスキーはすべて無効になる。
