# ADR-0077: IdP（SSO）との連携

- 日付: 2026-10-30
- 状態: 承認
- 統合した ADR: 旧 ADR-0025（§1）・旧 ADR-0033（§2）・旧 ADR-0036（§3）・旧 ADR-0037（§4）・旧 ADR-0040（§5）・旧 ADR-0042（§6）・旧 ADR-0043（§7）・旧 ADR-0055（§8）・旧 ADR-0066（§9）・旧 ADR-0068（§10）（2026-10-30 に統合。元の文面は git の履歴にある）

## 文脈

この雛形はローカルの認証（パスワード・TOTP・パスキー。ADR-0076）を持ったまま、外部 IdP との
SSO を**追加の入口**として持つ。派生（nolumiawiki・rewardpointsweb・photonest）が同じ判断を
3 回別々に書き、3 回目で食い違ったので、良い部分を集めて雛形へ戻した。主な連携先は自前の
IdP（assay）で、idp の ADR-0049 が挙げた RP 側のギャップ（G4〜G7・I2・I5〜I9）をここで塞いでいる。

決めることは、往復の作り（§1）、IdP とのサインアウト・停止のやり取り（§2・§3・§7）、
IdP の利用者とこのアプリの利用者の結び付け（§4・§5・§6）、ログイン画面の振る舞い（§8〜§10）。
入口ごとの認証の強度と `LOCAL_LOGIN_ENABLED` は ADR-0076 §3、ローカル口座を意図して持つことは
ADR-0076 §7、テナントごとの連携先は ADR-0079 §4 が決める。

## 決定

### §1 OIDC 認可コードフロー（PKCE）で入る

置き場所は `bounded_contexts/identity_federation/`。

1. **認可コードフロー + PKCE（`S256`）。** 経路は `GET /api/auth/sso/provider`
   （ボタンを出すか）→ `GET /api/auth/sso/login`（送り出し）→
   `GET /api/auth/sso/callback`（戻り）→ `POST /api/auth/sso/token`（引き換え）。
   ID トークンは JWKS の公開鍵で署名を検証し、発行者・対象者・`nonce` まで確かめる。
   エンドポイントは discovery（`/.well-known/openid-configuration`）で引き、
   **文書が名乗る `issuer` が引きに行った先と一致すること**を確かめる。
   **往復の状態（`state` / `nonce` / `code_verifier`）は署名付き Cookie で運ぶ**
   （HS256・`HttpOnly`・`SameSite=Lax`・10 分）。サーバー側には控えを持たない。
   戻りを処理したら、成功でも失敗でも Cookie は落とす。
2. **連携先の発行者とクライアント ID はテナントの行（`tenants.issuer` / `client_id`）が正本**
   （ADR-0079 §4）。設定（`OIDC_*`）に残すのはテナントをまたいで同じもの（クライアントの鍵・
   戻り先・要求する強度・名乗り方）で、`OIDC_ISSUER` / `OIDC_CLIENT_ID` は既定のテナントを作るときの
   初期値。設定は環境変数でも管理画面でも入る。
3. **コールバックは 1 回限りの引き換え券だけを URL に載せ**、SPA が
   `POST /api/auth/sso/token` で引き換える。引き換えはトークンを httpOnly Cookie に載せるだけで、
   応答本文（`SsoSessionResponse`）は `redirect_to` だけ（ADR-0076 §4）。券は SHA-256 にして
   **テーブル**（`sso_login_tickets`）へ保存し、寿命は既定 60 秒（`OIDC_LOGIN_TICKET_TTL_SECONDS`）。
   期限切れは発行のたびに掃除する。
4. **結び付けの鍵は `(issuer, sub)`**（`federated_identities`）。無ければ、`OIDC_LINK_BY_EMAIL` が
   真のときに限り**検証済みの**メールアドレスで既存のローカル口座へ寄せ（既定は寄せない。§4）、
   それも無ければ `OIDC_AUTO_PROVISION` が真なら作る。「受け入れてよい相手か・寄せてよいか」は
   `AccountLinkingPolicy`、「作ってよいか・どのロールを与えるか」は `ProvisioningPolicy` /
   `RoleAssignment` が持つ。指名された席（入り口を 1 つも持たない利用者）の受け取りは
   ADR-0079 §5 決定 2。
5. **クライアント認証は `client_secret_basic`（既定）と `private_key_jwt` の 2 方式**で、
   `OIDC_CLIENT_AUTH_METHOD` で選ぶ。**知らない値は既定へ落とさず「不備」**として扱う
   （SSO が無効になり、ログイン画面にボタンが出ない）。

**ローカル認証は残し、SSO は追加の入口にする。** 既定は **`OIDC_ENABLED=false`**
（何も設定しなければ SSO は無い）、**`OIDC_AUTO_PROVISION=false`**。
機械が入ってくる口は ADR-0082 が決める。

### §2 サインアウトを IdP まで通すかはアプリが決める（既定は通さない）

`POST /api/auth/logout` はこのアプリのセッションを終わらせるだけで、IdP の SSO セッションには
触れない（そのため、サインアウトした直後に「SSO で入る」を押すと名乗り直さずに入れる）。
IdP の SSO セッションは**その IdP を使う全アプリで共有**されている。

1. **`OIDC_RP_LOGOUT_ENABLED`（既定 `false`）。** 無効のとき画面は遷移しない。
2. 有効のときだけ、画面はアプリのサインアウトを終えてから `GET /api/auth/sso/logout` へ遷移し、
   そこが IdP の `end_session_endpoint`（RP-Initiated Logout 1.0）へ送り出す。戻り先は
   `GET /api/auth/sso/signed-out`。`OIDC_POST_LOGOUT_REDIRECT_URI` が空なら `APP_BASE_URL` から
   組み立てる（`OIDC_REDIRECT_URI` と同じ作法）。IdP から戻ったら `?signed_out=1` を付けて
   ログイン画面へ返し、画面は `login.signedOut` を出す。
3. **通せない場面は失敗にしない。** 設定が無効・SSO が使えない・IdP が `end_session_endpoint` を
   出していない・discovery が引けない、のどれもログイン画面へ返すだけにする。
4. **`GET /api/auth/sso/logout` は同一サイトからの遷移だけ通す**（`Sec-Fetch-Site`）。
   ヘッダーごと無い場合は通す。`id_token_hint` は送らず、`client_id` + `post_logout_redirect_uri`
   の組で名乗る。画面の判断材料は `GET /api/auth/me` の `rp_logout_enabled`。

### §3 IdP で止めた利用者は、このアプリでも止まる（back-channel logout の受け口）

`POST /api/auth/sso/backchannel-logout` を**設定なしで常に受ける**。セッションを消すのではなく
**「止まった」を記録して、次に出し直そうとしたときに弾く**。§2 とは向きが逆（こちらは IdP から
届く話）で、混同しない。

1. 届いた `logout_token` を JWT として確かめる（署名・発行者・対象者・`exp` / `iat` 必須）。
   そのうえで「ログアウトの通知であること」を確かめる ——`events` にイベントがあり、
   `nonce` が**無く**、`sub` か `sid` があり、`jti` がある。どの連携先の鍵で確かめるかは
   トークンの `iss` で選び、登録の無い発行者は断る（ADR-0079 §4 決定 2）。
2. `federated_session_revocations` に 1 行残す（`jti` が主キー ＝ 再送は重複で弾く）。
   `sid` がある通知はそのセッションだけ、無い通知はその利用者のすべてに効く。
3. このアプリのトークンに `fed_iss` / `fed_sub` / `sid` / `fed_iat`（セッションが**始まった**時刻）を
   刻み、**新しいトークンを出す経路**（更新・ロールの切り替え）と資格情報を作り替える経路で
   記録と突き合わせる（ADR-0076 §5 決定 3・4・6）。手元のアクセストークンは寿命（5 分）まで通る。
4. ローカルのログインで発行したトークンには何も刻まない ＝ 停止の伝播は届かない。

**新しい設定項目は作らない。** 通知を送るかは IdP 側の登録（`backchannel_logout_uri`）が決める。

### §4 同じメールアドレスの口座へ黙って寄せない（既定を無効にする）

1. **`OIDC_LINK_BY_EMAIL` の既定は `false`。** 値オブジェクト（`AccountLinkingPolicy.link_by_email`）・
   設定の既定値・管理画面の既定を揃える。
2. 開けたときの条件（`email_verified` が真であること）はそのまま残す。開けるかどうかを決めるのは、
   **つないだ IdP でその値がどう立つのかを確かめた人**である。

⚠ assay の `email_verified` は「本人が所有を証明した」ではなく**「テナント管理者がそう主張している」**
である（真になるのは自己登録の確認メールだけだが、管理者によるメール変更（MT25）はこの値を維持し、
管理者がログイン識別子としてメールを足すときも所有確認は無い）。

### §5 結び付けるのは入っている本人（設定画面から連携する）

設定画面（`/profile/security`）の区画から、このアプリで入っている本人が IdP の往復を通って
結び付ける。誰と誰を結ぶかを、メールアドレスではなく 2 つの認証の結果で決める。

1. **連携は「入っている状態で始め、戻ってきて完了する」。** `POST /api/auth/sso/link/start` で
   往復を始め、戻りは**ログインと同じ** `GET /api/auth/sso/callback` で受ける。
   ⚠ **戻り先の URI は 1 つに保つ。** どちらの後始末をするかは往復状態（署名付き Cookie）の
   `purpose` で決める。⚠ **目的をクエリで渡さない**（戻りの URL を書き換えるだけで、ログインの
   往復を連携に化けさせられる）。`purpose` を持たない Cookie はログインの往復として読む。
2. **始めるのは XHR、遷移するのは画面自身。** `POST /link/start` は 303 を返さず、認可要求の URL を
   JSON で返し、画面が `location.assign` する。認証が切れていれば 401 を返せ、`CsrfMiddleware` の
   守りもそのまま効く。
3. **結び付ける相手は往復を始めた利用者。** 往復状態に `user_id` を入れ、戻ってきたときの
   セッションと突き合わせる。違えば `sso_link_session_mismatch` で断る。
4. **既に埋まっている結び付きは断る。**
   - その `(issuer, subject)` が**別の利用者**のものなら `sso_identity_taken`（付け替えは横取りになる）。
   - その利用者に**同じ IdP の別の `subject`** が既にあるなら `sso_already_linked`（解除してから結び直す）。
   - 同じ相手をもう一度結んだ場合は断らない。
5. **解除は「入り口が残るときだけ」通す。** `DELETE /api/auth/sso/link`。残る入り口が無ければ
   `sso_last_entrance` で断る。⚠ **数えるのはパスワードとパスキーで、二要素認証は数えない。**
   ⚠ **数えるのは呼び出し側（Presentation 層）**で、ユースケースは `has_other_entrance` を受け取るだけ
   （`account_security` コンテキストへ境界を越えて引きに行かない）。

連携の状態は `GET /api/auth/sso/link` で返す。どのテナントの連携先を使うかは入っている利用者の
テナント（ADR-0079 §4 決定 2）。

### §6 写しは IdP を正とする。メールアドレスは鍵ではない

1. **写しはログインのたびに上書きする。** `FederatedUserDirectory.refresh_profile` を、既に
   結び付いている相手のログインで毎回呼ぶ。⚠ **ぶつかる値は書かない** ——`users.email` /
   `users.username` の一意（メールは同じ席の中で一意。ADR-0079 §4 決定 3）に当たる値は、その項目だけ
   見送って記録に残す（値は残さない）。⚠ 画面（`PUT /api/auth/me`）で名前とメールを直せるが、
   IdP で入る利用者が直しても次のログインで上書きされる（「RP では編集させない」は未対応で
   `docs/Progress.md` に置く）。
2. **メールアドレスは、要るところでだけ要る。** `ClaimsMapping.apply` は `email` が無くても通し、
   `FederatedUser.email` は `str | None`。断るのは「無いと決められない場面」——初回にメールで寄せる
   ときと、利用者を作るとき——だけ。既に結び付いている相手は `sub` で引けるので入れる。
   表示名が取れないときは `sub` を使う。
3. **グループからロールは引かない。** `RoleAssignment` は `group_to_roles` を持たず、
   `OIDC_GROUPS_CLAIM` / `OIDC_ROLE_MAPPING` の設定も無い。残るのは `OIDC_DEFAULT_ROLES` と
   `OIDC_ROLE_SYNC`。⚠ **`OIDC_ROLE_SYNC` を真にすると、引き直すのは既定のロールだけなので、
   管理画面で足したロールが毎回のログインで消える**（既定は偽）。どちらもテナントの中のロールしか
   付けない（ADR-0079 §3）。

### §7 IdP で止まった人は、定期的に聞き直して SSO の入口だけ止める（定期照合）

§3 の受け口は通知が届いたときにしか効かないので、**毎時 assay に名簿を聞き、止まった人・消えた人の
SSO のセッションを §3 と同じ記録で失効させる。利用者そのもの（`users`）には触らない。**
定期実行の足回りは ADR-0075 §3。

1. **聞く先と、状態ごとの扱い。**

   ```
   GET {OIDC_ISSUER}/admin/applications/self/users?subs=<結び付いている sub を 100 件ずつ>
   Authorization: Bearer {MACHINE_CLIENT_ID で client_credentials ＋ resource={issuer}/admin}
   ```

   | `state` | こちらの扱い |
   |---|---|
   | `allowed` | 触らない |
   | `blocked` | その利用者の **SSO のセッションをすべて失効**（`federated_session_revocations` に `sid` の無い行） |
   | `unknown` | 同じく失効 ＋ **結び付き（`federated_identities`）を外す** |
   | 知らない値・名簿に無い | 触らない |

   - ⚠ **経路にアプリを書かない。** どのアプリの名簿かは、名乗ったサービスアカウントから assay が決める
   - ⚠ **`is_active` を落とさない。** ローカルの入口は残る。SSO の新しいログインは assay 自身が断る
   - ⚠ **戻せば戻る。** 失効の記録は「その時刻より前に始まったセッション」にしか効かない（§3）
   - 照合するのは `OIDC_ISSUER` のテナントだけ。ほかのテナントの停止は §3 の通知で届く
2. **⚠ 引けなかったら何もしない。** 404・5xx・タイムアウト・トークンが取れない、のどれも
   「全員辞めた」ではない。止めてよいのは `200` の中身に基づくときだけ。⚠ **403 は
   「サービスアカウントがまだアプリに結び付いていない」（準備待ち）**なので、warning にせず
   info を 1 行残して見送る。
3. **⚠ 全員が `unknown` なら何もしない。** 結び付きが 2 件以上あって返ってきた全員が `unknown` なら、
   結び付きを外さず見送る（warning）。発行者の取り違えやアプリの付け替えでもこの形で返り、
   結び付きは本人の操作でしか作り直せない（§5）。1 件だけのときは通常どおり扱う。
4. **同じ失効を何度も書かない。** 失効の `jti` を **`(issuer, sub, 最後に SSO で入った時刻)`** から
   決める。同じログインには毎時・ワーカーの数だけ走っても行は 1 本。戻って入り直し、また止められた
   ときは新しい行になる。2 つのワーカーが同じ行を書いてぶつかったら、その周回は巻き戻して見送る。
5. **名乗りは `MACHINE_CLIENT_ID`。** assay で**このアプリのサービスアカウント**として登録した
   `client_id`（ログイン用の `OIDC_CLIENT_ID` とは別の登録）。鍵は `OIDC_PRIVATE_KEY_FILE` /
   `OIDC_PRIVATE_KEY_KID` を共有し、⚠ **方式は常に `private_key_jwt`**。**空なら照合は走らない。**
   ⚠ 名前に用途を書かない（`RECONCILE_…` にしない）。

### §8 サインインの往復で行き先（経路とクエリ）を落とさない

1. `RequireAuth` はログイン画面へ送るとき、今の経路とクエリを `?redirect_to=` に載せる
   （着地から来たときは付けない）。
2. ログイン画面はその値を絞って（`services/returnTo.ts`）SSO の入口
   （`GET /api/auth/sso/login?redirect_to=`）へ渡し、パスワード・パスキーで入ったときもそこへ遷移する。
3. 絞る規則はサーバの `RedirectTarget.parse` と同じ（自サイト内の絶対パスだけ）。加えてサーバが
   受け取る上限の 255 文字を超えるものは着地へ倒す。行き先は IdP の認可要求には載せず、サーバ側の
   往復状態に入れる。

### §9 IdP で入っていれば、ログイン画面でボタンを押させない

1. ログイン画面は、条件がそろえば**入口を描く前に** `GET /api/auth/sso/login?prompt=none` へ画面遷移する。
   サーバーは認可要求に `prompt=none` を付け、往復状態（Cookie）に「試した往復」と書く。
   iframe は使わない（上の階の画面遷移だけ）。
2. IdP で入っていれば code が返り、ふつうの SSO と同じ道（引き換え券 → `/login/sso`）で入る。
   行き先（`redirect_to`。§8）もそのまま使う。
3. 試した往復の戻りが `login_required`・`consent_required`・`interaction_required`・
   `account_selection_required` なら、**失敗として記録せず**、`?sso_silent=declined&redirect_to=…` で
   ログイン画面へ戻す。画面はエラーを出さずにふつうの入口を出す。
4. 試さないとき（`frontend/src/services/silentSso.ts`）:
   - サインアウトした後（`localStorage` の印。ほかのタブでも試さない）
   - このタブで一度試した後（`sessionStorage` の印。ただし §10）
   - URL に `redirect_to` 以外のもの（`sso_error`・`signed_out`・`sso_silent` など）が付いているとき（ただし §10）
   - SSO が無効なとき・印を書けないブラウザ

   どちらの印も、どの入口でも入れたら消す（次に期限が切れたときはまた試す）。
5. IdP では通ったがアプリ側で断られたとき（口座が無い・止められている等）は、`?sso_error=<コード>` で出す。

### §10 黙って断られた後でも、再読み込みしたらもう 1 回確かめる

1. ログイン画面が**本人の再読み込みで開かれたとき**（`PerformanceNavigationTiming.type === 'reload'`）は、
   このタブで試した印と `sso_silent` の印があっても、もう 1 回だけ黙って確かめる。
2. 再読み込みでも試さないもの: サインアウトの印・`redirect_to` / `sso_silent` 以外のクエリ
   （`sso_error`・`signed_out` など）・印を置けないとき。
3. 試すかどうかはログイン画面を開いたときに 1 回だけ決める（§9 と同じ）。

## 理由

### §1

- **逆輸入であって新規設計ではない。** 2 つの派生が同じ形へ独立に収束し、片方は本番で動いていた。
  ただし 1 つを丸写しせず、部分ごとに良い方を採った。

  | 部分 | 採る | 理由 |
  |---|---|---|
  | 層の分け方・ポリシーの持ち方・README | nolumiawiki | 機能として上位集合（プロビジョニング・`private_key_jwt`）。処理が presentation に寄っていない |
  | 「受け入れてよいか・寄せてよいか」 | rewardpointsweb | `AccountLinkingPolicy` として値オブジェクトに切り出してある |
  | **往復状態の持ち方** | **photonest** | 署名付き Cookie 1 つで済み、テーブルが 2 つ減る |
  | 引換券の置き場所 | nolumiawiki | photonest は状態ストア（Redis）が要る |

  photonest の App Link 向けの引き渡し（`handover.py`）は雛形には過剰なので採らない。
- **経路は `/api/auth/sso/*`。** 3 つのうち 2 つがこれで、`oidc` はプロトコルの名前でしかない。
- **PKCE は常に付ける**（`plain` は使わない）。秘密を持つクライアントでも認可コードの横取りを防ぐ。
  暗黙フローはトークンが URL を通り、履歴・Referer・アクセスログに残る。
- **引き換え券にする。** トークンを URL に載せると履歴・Referer・アクセスログに残る。
- **往復状態は Cookie に入れる。** 表に控えを置く形は全員で 1 つの表を共有するので、`state` を
  知っている相手なら誰でも戻りを完了でき、攻撃者が始めた認可要求の URL を踏ませると**被害者は
  攻撃者としてログインした状態**になる（ログイン CSRF）。`state` / `nonce` / `code_verifier` を
  まるごと署名付き Cookie に入れれば、Cookie が無ければ照合対象そのものが無いので 1 つの仕組みで
  塞がる。署名鍵は内蔵 JWT と同じで、中身は読めるが書き換えられない。`SameSite=Strict` にはできない
  ——IdP からの戻りは別サイトからの GET の画面遷移で、`Strict` では Cookie が送られない。
- **券だけは表に置く。** 雛形に Redis 依存を持ち込みたくなく、複数ワーカーではメモリでは成立しない。
  券は短命で件数も少ない。
- **鍵は `sub`、メールアドレスは手掛かり**（idp の ADR-0049 I2）。メールアドレスは変わり得る。
- **`private_key_jwt` を最初から入れる。** `client_secret` はどこに置いても平文の写しが増える
  （管理画面から入れた値は `system_settings` に平文で残る）。秘密鍵方式なら設定に載るのは在り処だけ。
  既定を `client_secret_basic` にしたのは、秘密鍵方式に対応しない IdP へつなぐ派生もあるため。
- **`OIDC_ENABLED=false` を既定に。** 雛形は連携先を知らない。設定が空のまま有効になると、起動は
  するがログインだけが失敗する。
- **`OIDC_AUTO_PROVISION=false` を既定に。** IdP がテナント共用のとき、真は「IdP に口座がある人は
  全員このアプリに入れる」を意味する。安全側へ倒し、開けたい派生が開ける。

### §2

**ローカル口座を持つアプリでは無効が正しい。** `end_session_endpoint` が消すのは全アプリで共有された
IdP のセッションで、片方のサインアウトがもう片方の次回の SSO ログインに効く（他アプリの既存の
セッションは切れない）。利用者が頼んでいない副作用である。有効にする価値があるのは 2 つの形 ——
**SSO でしか入れないアプリ**（`LOCAL_LOGIN_ENABLED=false`。通さないとサインアウトが成立しない）と
**共有の端末で開くもの**。

- **`id_token_hint` は送らない。** 雛形は検証した後の ID トークンを保持しない。保持するなら必要に
  なったアプリで別に決める。
- **判断材料は `/me` で返す。** 画面に焼き込むと設定を変えた後に食い違う。`/provider` はログイン画面
  のためのもので、サインアウトの経路から引くと往復が 1 つ増える。⚠ **`/me` が返すのは設定であって、
  この画面がどう入ったかではない。** パスワードで入った利用者のサインアウトでも IdP のセッションを
  落とすが、真にするのは上の 2 つの形だけなので問題にならない。ローカル口座を持つアプリで真にしない。
- **`Sec-Fetch-Site` を見る。** この口は未認証で全アプリ共有のセッションを変える。守らないと、よその
  頁が `<img src="…/api/auth/sso/logout">` を置くだけで利用者を他アプリからも締め出せる。⚠ **IdP の
  確認画面をあてにしない**（`id_token_hint` が無いときの確認は *SHOULD* で、assay は挟まない）。
  CSRF トークンにしないのは、ここが画面遷移で `<a href>` で開ける性質を保ちたいから。ヘッダーを
  付けないのは古いブラウザだけなので、無ければ通す。

### §3

- **記録で弾く形にしたのは、消せるものが無いため。** トークンはサーバーに控えが無い。記録は
  リフレッシュトークンの寿命だけ持てばよい。
- **比べるのはセッションが始まった時刻である。** `iat` は秒までしか持たず、止めた直後の同じ秒に
  入り直した利用者を巻き添えにする。⚠ **`iat` は出し直すたびに新しくなるので、`iat` で見ていると
  更新を 1 回通すだけで停止をすり抜けられる。**
- **`jti` で再送を弾く。** 弾かずに毎回記録すると、古い通知の再送で「いま生きているセッション」を
  落とせる。
- **`nonce` を持つものを断るのは、それが ID トークンだから。** 両者を分けるのはこの 1 点だけで、
  見落とすと正規に受け取った ID トークンを送り返すだけで他人のセッションを落とせる。

| 捨てた案 | 理由 |
|---|---|
| 設定で開閉する（§2 と同じ形） | 停止が届かない状態を既定にすることになる。登録しなければ 1 通も来ないので、常に開けておく実害が無い |
| サーバー側にセッション表を持ち、通知で消す | トークンの持ち方そのものを変える話になる |
| `sub` だけで失効させ `sid` を見ない | 同じ利用者の別の端末まで落ちる |
| `Form()` で本文を受ける | `python-multipart` が要る。1 項目のために依存を増やさず、本文を自分で読む |

### §4

**安全側がどちらかは、RP には決められない。** IdP ごとに `email_verified` の立ち方は違い、IdP の
設定と運用で後から変わる。倒して失うのは初回ログインの手間 1 つで、残るのは `sso_account_not_linked`
という**分かる形の失敗**である。逆向きの間違い（黙って他人の口座へ入る）は気付けない。
assay 側で `email_verified` を落とす案は assay を使う全 RP に影響し、主張の出どころをクレームで分ける
案はいちばん大きいので採らない。

### §5

**判断材料は往復を始める時点で全部揃っている**（いまセッションを持っていること）。戻りでやることは
「始めたときの決定をそのまま実行してよいか」の確認だけになる。

| 捨てた案 | 理由 |
|---|---|
| 連携専用の戻り先 URI | IdP のクライアント登録が 2 本になり、⚠ 登録漏れが「連携のときだけ通らない」形で出て、原因がこちらのコードに見える |
| `GET /link/start` で 303 | 認証が切れていたときに出せるものが無い |
| 管理画面から結び付ける | 管理者の目視に委ねることになり、メールで寄せるのと同じ弱さが残る |
| 解除で入り口が無くなるならパスワード再設定へ誘導 | パスワードを持たない利用者にリセットで入り口を生やし、ADR-0076 §6 で閉じた経路を開け直す |

戻りで今のセッションを見て決めると、サインアウト → 別の利用者でログイン、を挟むだけで結び付け先が
ずれる（決定 3）。

### §6

**鍵は `(iss, sub)`** なので、メールアドレスは前提条件ではない。前提にしていたから、出さない IdP と
つなげなくなっていた。**正本が IdP にある項目は来るたびに書き直す** ——書き直さないなら、それは写しでは
なく初回にコピーしただけの別の値になる。**権限は RP が持ち、IdP は配らない**（idp の ADR-0049 I6）。
assay は `groups` を発行しないので、引く側を残すと**効かない設定が、効くと思って触られる。**

- 写しの更新でぶつかったらログインを断る案は採らない。⚠ 向こうの都合でこちらが入れなくなり、直せる
  のは IdP 側の管理者だけになる。
- `users.email` を NULL 許容にする案は影響が広すぎる（一意制約・通知・パスワードリセット）。

### §7

- **SSO の入口だけ止めるのは、この雛形が入口を 2 系統持つから**（ADR-0076 §7）。IdP が認証して
  いたのは SSO の入口で、ローカル口座はこのアプリの管理者が持ち主である。§3 と**同じ範囲**に揃えると、
  届いたときと取りこぼしたときで止まる範囲が違う、が起きない。
- **失効の記録を使い回す**ので、止める仕組みを 2 つ持たずに済み、「止めたら効くまで」の上限も
  アクセストークンの寿命（5 分）のまま変わらない。記録は時刻で効くので、戻す操作も要らない。
- **全件を毎回聞く。** 名簿の口の差分（`updated_since`）には外された割り当てが出ない。

| 捨てた案 | 理由 |
|---|---|
| `is_active = False` にする（nolumiawiki の形） | ローカルのパスワードまで止まり §3 と範囲が食い違う。戻すにも管理者の手が要る |
| `LOCAL_LOGIN_ENABLED` で分ける | 画面の設定 1 つで照合の意味が変わり、切り替えた時点で止まっている人の扱いが決まらない |
| `unknown` の人を削除する | 作成者・更新者の記録が切れる。止めるのと消すのは別 |
| 毎周回、新しい `jti` で書く | 止まったままの人 1 人につき、リフレッシュトークンの寿命（14 日）のあいだ毎時・ワーカー数ぶん行が積もる |
| 照合専用の設定（`SSO_RECONCILE_CLIENT_ID`） | nolumiawiki で作って消した |

### §8

- クエリ名はサーバの入口がすでに受けている `redirect_to` に揃えた。
- 長すぎる値をそのまま渡すと入口が 422（JSON）を返して画面が止まる。行き先を失うほうが、
  サインインできないよりましである。
- 行き先を IdP の認可要求に載せないので、クエリに秘密を含む経路でも IdP へ持ち出さない。

### §9

- **サーバーの往復状態に「試した」を書く**のは、ボタンで始めた往復の `login_required` まで黙って
  飲み込まないため。クエリの印だけで決めると、URL を書き換えて失敗を隠せる。
- **サインアウトの印を `localStorage` に置く**のは、サインアウトが既定で IdP の SSO を切らない（§2）
  から。印が無いと、ログイン画面を開いた瞬間に入り直してしまう。タブを開き直しても効かせたい。
- **試した印を `sessionStorage` に置く**のは、ループ止めはそのタブだけに効けば足りるから。戻りの URL
  にも `sso_silent` を付けるので、印が消えても行き来は 1 往復で止まる。
- iframe で裏から確かめる形は採らない。第三者 Cookie の扱いに左右され、CSP の `frame-ancestors` も
  開けることになる。

### §10

- 断られて戻る `/login?sso_silent=declined` への遷移は再読み込みではない（`navigate`）ので、断られ
  続けてもループにはならない。
- 再読み込みは本人の操作なので、「別のタブで入ったから、もう一度見てほしい」という意思として扱う
  （Tracker・WBS で「Assay に入ったのに再読み込みしても入れない」と報告があった）。
- タブへ戻っただけ（フォーカス）で試すと、入っていない人はタブを切り替えるたびに IdP へ往復するので
  採らない。

## 影響

### §1

- **テーブルが 2 つある**（`federated_identities` / `sso_login_tickets`）。往復状態を Cookie に
  したので `sso_login_sessions` は無い。券の掃除は発行のたびで、定期ジョブは持たない。
- **Cookie を落とすブラウザでは SSO でログインできない**（照合対象が存在しない）。
- **設定キーが約 20 ある**（`OIDC_*`）。足すときは設定管理の 3 ファイルすべてを更新する。
- **`httpx` が実行時の依存**（discovery・トークン交換・UserInfo）。
- **画面**: SSO コールバック（`/login/sso`）と、ログイン画面のボタン。
- **SSO で作った利用者にパスワードは無い**（ADR-0076 §6）。
- **IdP 側のクライアント登録が要る。** assay では管理 API（`POST /admin/clients`）で登録し、
  リダイレクト URI に `<APP_BASE_URL>/api/auth/sso/callback` を入れる。
- ⚠ **`private_key_jwt` を使う場合、秘密鍵を read-only で渡し、ファイルとディレクトリの両方で
  コンテナの実行 gid が通ること。** 通っていないと、起動も設定画面も通るのに利用者が IdP から
  戻ってきた瞬間だけ落ちる（起動時に一度読んでログへ出す）。
- photonest は経路名が違う（`/api/auth/oidc/*`）。寄せるときは IdP 側の登録済みリダイレクト URI を
  差し替えるか、旧経路を残す。

### §2

- ⚠ **有効にしたら `post_logout_redirect_uri` を IdP へ登録すること。** 未登録でもエラーにならず
  **IdP 自身の完了ページで止まる**ので、漏れは「戻ってこない」という形でしか出ない。
- 「このアプリだけ毎回名乗り直させたい」なら、認可要求の `prompt=login` のほうが副作用が無い。
- 単一ログアウト（全アプリのセッションを落とす）は別の話で、§3 の受け口と IdP 側の登録が要る。
- ⚠ `?signed_out=1` を画面が出さないと、期限切れで飛ばされたのと見分けが付かない。

### §3

- `sso_login_tickets` に `issuer` / `subject` / `session_id` / `session_started_at` の 4 列がある
  （券からトークンへ入り口を引き継ぐため）。
- `federated_session_revocations` の掃除は通知を受けるたびに行う（期限切れの行を消す）。定期ジョブは要らない。
- ⚠ **新しいトークンを出す口は、入り口（`fed_*` / `sid`）をそのまま引き継ぐ義務を負う。** 落とすと、
  そのトークンだけ停止が効かなくなる。いまの口は更新とロールの切り替えの 2 つ。
- **IdP 側に `backchannel_logout_uri` の登録が要る**（手順は `docs/OPERATIONS.md`）。
- ⚠ **いまの assay は「利用者を止めた」ときには通知を送らない**（送るのはログアウトのときだけ）。
  管理者による停止は §7 の定期照合と短命のアクセストークン（ADR-0076 §5）で届く。

### §4

- ⚠ **既に結び付いている利用者には影響しない**（`federated_identities` の行で決まる）。
- ⚠ **同じメールアドレスのローカル口座がある新規の相手は `sso_account_not_linked` で断られる。**
  本人は §5 の設定画面から結び付けられる。寄せる挙動が要るなら `OIDC_LINK_BY_EMAIL=true` を明示し、
  **つないだ IdP で `email_verified` がどう立つのかを確かめること。**

### §5

- 経路は `GET /link`・`POST /link/start`・`DELETE /link`。`GET /callback` はログインと連携の両方を受ける。
- 監査ログは `sso_identity.linked`（ログイン中の自動結び付けと同じ種類）と `sso_identity.unlinked`。
- 画面の区画は SSO が無効な環境では出ない。
- ⚠ **まだ結び付いておらず、ローカルの入口も無い人**（このアプリで利用者を作らない構成）は、
  管理者に頼むしかない。

### §6

- `FederatedUser.email` は `str | None`。`groups` は持たない。
- ⚠ 消えた設定（`OIDC_GROUPS_CLAIM` / `OIDC_ROLE_MAPPING`）が配り先に残っていても、値は黙って
  無視される（効いていなかったので振る舞いは変わらない）。
- ⚠ IdP で入る利用者が画面で名前を直しても、次のログインで上書きされる。

### §7

- 設定は `MACHINE_CLIENT_ID` が 1 つ。テーブルは増えない。
- ⚠ **有効にするには assay 側の 2 手が要る**: サービスアカウントを登録（`client_credentials` ＋
  このアプリの公開鍵）し、アプリの詳細画面の「このアプリの名乗り」に結び付ける（`docs/OPERATIONS.md`）。
- ⚠ サービスアカウントは assay のテナントごとに要るので、1 つの設定では 1 テナントしか聞けない（ADR-0079 §4）。
- 最後の管理者の歯止めは持たない。利用者を止めないので締め出しが起きない。
- これは**こちらから assay を呼ぶ**名乗りで、機械がこのアプリへ入ってくる口（ADR-0082）とは別の話。
- 派生へ配るときは、自分の入口の形で「止める」の意味を決め直す。SSO 専用のアプリでも、この形のまま
  で実質は止まる（新しいログインは assay が断る）。

### §8

- 派生アプリは 3 か所（`App.tsx` の `RequireAuth`、`LoginPage.tsx`、`services/returnTo.ts`）を取り込む。
- 古い版の画面を Service Worker が持っている端末では、新しい版に入れ替わるまで直らない。

### §9

- ログイン画面を開くと、条件がそろうときは一瞬 IdP へ出て戻る（画面には「読み込んでいます」だけが出る）。
- 監査ログの「SSO ログイン失敗」には試して断られた分を積まない（アプリログに
  `sso_silent_login_declined` が出る）。
- 雛形から作ったアプリへは、各リポジトリの入口を読み直して手で当てる（nolumiatask #645）。

### §10

- IdP から出ている人がログイン画面を再読み込みすると、IdP への往復が 1 回増える。
